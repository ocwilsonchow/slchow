Frontend 的 **regression tests** 保护用户早已依赖的行为：表单仍然可以提交、draft 在请求失败后仍然保留、login flow 在 refactor 之后仍然会落到正确位置。

<br />

- 它们不是为了追逐 coverage 百分比。
- 在**仍能证明行为、成本最低的那一层**拦截 regression——**Vitest**、**React Testing Library**，或 **Cypress**。

<br />

---

## 1. 测什么、在哪里测

按 **blast radius** 排优先顺序，而不是按写测试有多容易。

<br />

| Layer | Tool | Use when |
| --- | --- | --- |
| Unit | Vitest | Pure logic、reducers、parsers、URL/state helpers |
| Component | Vitest + React Testing Library | Interaction contracts：click → state → text/role |
| Integration-ish | Vitest + RTL + MSW | 搭配 mocked network 的 page sections |
| E2E | Cypress | 跨 routes 与 auth 的完整 critical journeys |

<br />

- 聚焦金钱、auth、数据丢失路径、高流量入口流程，以及曾经上线过的 bug。
- 略过一次性 chrome 与纯视觉 polish。
- 在**仍能证明行为、成本最低的那一层**拦截 regressions。
- 如果结果必须依赖 **real browser** 与 **real navigation** 才可信，就用 Cypress；否则留在 Vitest。
- **Failure：** 同一件事在每一层都证明一次。

<br />

## 2. 用 Vitest 与 RTL 拦截 Unit 与 Component Regressions

测 component regressions 时，测**用户可观察的结果**。

<br />

```tsx
import { render, screen } from "@testing-library/react"
import userEvent from "@testing-library/user-event"
import { describe, expect, it, vi } from "vitest"

import { DraftForm } from "./draft-form"

describe("DraftForm", () => {
  it("keeps draft when network fails", async () => {
    const user = userEvent.setup()
    const onSubmit = vi.fn().mockRejectedValue(new Error("network"))

    render(<DraftForm initialValue="hello" onSubmit={onSubmit} />)

    await user.clear(screen.getByRole("textbox", { name: /draft/i }))
    await user.type(screen.getByRole("textbox", { name: /draft/i }), "updated")
    await user.click(screen.getByRole("button", { name: /save/i }))

    expect(await screen.findByRole("alert")).toHaveTextContent(/could not save/i)
    expect(screen.getByRole("textbox", { name: /draft/i })).toHaveValue("updated")
    expect(screen.getByRole("button", { name: /save/i })).toBeEnabled()
  })

  it("disables save while a submit is in flight", async () => {
    const user = userEvent.setup()
    let resolveSubmit!: () => void
    const onSubmit = vi.fn(
      () =>
        new Promise<void>((resolve) => {
          resolveSubmit = resolve
        })
    )

    render(<DraftForm initialValue="hello" onSubmit={onSubmit} />)

    await user.click(screen.getByRole("button", { name: /save/i }))

    expect(screen.getByRole("button", { name: /save/i })).toBeDisabled()

    resolveSubmit()
    expect(await screen.findByRole("button", { name: /save/i })).toBeEnabled()
  })
})
```

<br />

- 用 **role** 与 accessible name 查询，用 `userEvent` 驱动 UI，并 assert 用户接下来能看到或做到什么。
- 用它保护的 regression 来命名测试。`keeps draft when network fails` 对未来读者的帮助，远大于 `handles error`。
- 当 component 变得难以测试时，抽出 pure logic——formatting、validation、URL building——并对这些 functions 做 unit-test。把 component test 留在 wiring 与 interaction。
- **Failure：** assert internal state、CSS class lists，或 private function calls。

<br />

```ts
import { describe, expect, it } from "vitest"

import { getNextDraftStatus } from "./draft-status"

describe("getNextDraftStatus", () => {
  it("returns error without clearing the draft value", () => {
    expect(
      getNextDraftStatus({
        value: "updated",
        result: { ok: false, reason: "network" },
      })
    ).toEqual({
      value: "updated",
      status: "error",
      message: "Could not save",
    })
  })
})
```

### Testing Custom Hooks

当复杂 state logic 不需要 UI 时，用 `renderHook` 与 `act` 直接测 hook。

<br />

```tsx
import { renderHook, act } from "@testing-library/react"
import { describe, expect, it } from "vitest"

import { usePagination } from "./use-pagination"

describe("usePagination", () => {
  it("advances to the next page", () => {
    const { result } = renderHook(() => usePagination({ total: 50, perPage: 10 }))

    expect(result.current.page).toBe(1)

    act(() => {
      result.current.next()
    })

    expect(result.current.page).toBe(2)
  })
})
```

<br />

- 这能证明 state transitions，而不必 mount 不必要的 DOM。

<br />

### Type-Safe Test Data

对行为来说，优先用 **deterministic fixtures**，而不是宽泛的 snapshots。

<br />

```ts
type Note = { id: string; title: string; status: "draft" | "published" }

export function buildNote(overrides?: Partial<Note>): Note {
  return {
    id: "test-id",
    title: "Default Title",
    status: "draft",
    ...overrides,
  }
}

// Usage in a test:
// const publishedNote = buildNote({ status: "published" })
```

<br />

- Snapshots 对某些 serialization 场景有用，但当契约是「用户仍然能从失败的 save 里恢复」时，它们是弱的 regression 信号。
- 用 TypeScript 的 `Partial<T>` 建立 type-safe data factories，而不必在每个测试里重复大型 objects。

<br />

### Test Async States Explicitly

多数 data-driven components 不只成功态：initial 或 empty、loading、success、error、retry 或 recovery。

<br />

```tsx
import { HttpResponse, http } from "msw"
import { server } from "../test/server"
import type { Note } from "@/types"

it("retries after the first request fails", async () => {
  const user = userEvent.setup()
  let attempts = 0

  server.use(
    http.get("/api/notes", () => {
      attempts += 1

      if (attempts === 1) {
        return HttpResponse.json(
          { message: "Temporary failure" },
          { status: 503 }
        )
      }

      // TypeScript enforces that this matches the Note[] type
      return HttpResponse.json<Note[]>([
        { id: "1", title: "Regression playbook", status: "published" }
      ])
    })
  )

  render(<NotesList />)

  expect(await screen.findByRole("alert")).toHaveTextContent(
    /could not load notes/i
  )

  await user.click(screen.getByRole("button", { name: /retry/i }))

  expect(
    await screen.findByRole("link", { name: /regression playbook/i })
  ).toBeVisible()
})
```

<br />

- Regression 常常活在这些 states 之间的 **transition**。
- **MSW** 把测试留在 HTTP boundary，同时让每个 response 都是 deterministic。
- 这个测试证明失败是可见的、retry 仍然可能，以及后来的 success 会替换 error——而不必知道 component 用的是 `fetch`、query library，还是 custom hook。

## 3. 用 Cypress 保护 Critical-Path E2E

Cypress 保护的是那些只有搭配 routing、auth 与真实 page shell 才存在的 journeys。

<br />

```ts
// cypress/support/index.d.ts
declare global {
  namespace Cypress {
    interface Chainable {
      loginAs(email: string): Chainable<void>
    }
  }
}

// cypress/support/commands.ts
Cypress.Commands.add("loginAs", (email) => {
  cy.request("POST", "/api/test/login", { email })
})
```

<br />

```ts title="cypress/e2e/create-note.cy.ts"
describe("create note", () => {
  beforeEach(() => {
    cy.loginAs("writer@example.com")
    cy.seedNotes([])
  })

  it("creates a note and lands on the detail page", () => {
    cy.visit("/notes/new")

    cy.findByRole("textbox", { name: /title/i }).type("Regression playbook")
    cy.findByRole("textbox", { name: /body/i }).type(
      "Protect high-value behavior at the cheapest reliable layer."
    )
    cy.findByRole("button", { name: /publish/i }).click()

    cy.location("pathname").should("match", /\/notes\/.+/)
    cy.findByRole("heading", { name: /regression playbook/i }).should(
      "be.visible"
    )
  })
})
```

<br />

- 把这套 suite 保持很小：通常 **三到七条** journeys——sign in、完成核心产品任务、sign out 或到达一个耐久的 success state。
- Seed fixtures，让测试不依赖 production content。Assert URL、heading、success message——而不是沿途每一个 CSS class。
- 通过 API 或 task 控制 **authentication**；expiry 重要时 freeze **time**；等待 named request 或可见结果；每个测试隔离 records；优先用 roles 与 labels（只有在没有面向用户的 selector 时才用 test ID）。
- 当 UI contract 不必靠完整 browser 就能证明时，edge cases 属于 Vitest。Cypress 赚回成本的地方，是 false green 会把坏产品送上线的那些路径。
- **Failure：** 单一测试 sign in、改 settings、create a note、search、delete，再 sign out。在耐久边界切开 journeys。永远不要等待任意 timeout。

<br />

## Takeaway

Frontend regression testing 最好当成一套 **triage system**。

<br />

- 在成本最低、仍然可靠的那一层保护高价值行为，从真实 failures 增长 coverage，并把 Cypress 保持够薄，让红掉的 build 仍然有意义。
- 当某件事坏过一次，确保 suite 第二次会抓住它——最好用几个月后读起来仍然像 **product promise** 的测试名称。
- 修 bug 时 **先写会失败的测试**，并确认它因正确原因失败，再套上 fix。这个习惯背后的设计方式——对可观察的 UI 行为做 Red, Green, Refactor——见 [Frontend Engineering 中的 Test-Driven Development](/notes/test-driven-development-in-frontend)。
- 本地跑 focused tests，PRs 上跑 unit/component suite，merge 前跑 critical E2E journeys。
- **Failure：** 把 flake 常态化。如果测试随机失败，先 quarantine，再修或删。第三次才过的测试，仍然是 flaky test。略过 pixel-perfect visual diffs、穷尽的 E2E edge cases，以及对 framework internals 的 assertions。Manual exploratory testing 仍然重要。
