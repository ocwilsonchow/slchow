四年前，我以为 frontend engineering 就是把设计变成精致的界面。Production 教会我要把目光放在 component 之外：架构、数据新鲜度、可靠性、交付，以及可衡量的用户结果，都是这份工作的一部分。

<br />

以下指标是项目成果，不是通用基准。重要的是技术决策与可观察结果之间的联系。

<br />

## 成果一览

- **Architecture：** page load 加快 80%、search latency 降低 90%，PageSpeed 高于 90。
- **Web performance：** LCP 低于 0.5 秒，CLS 低于 0.1。
- **Mobile reliability：** 上线后 crash-free sessions 超过 99.5%。
- **Delivery：** 以 SST 将 build 与 deployment 时间缩短超过 50%。

<br />

## 四堂课

1. **架构层面的改变胜过局部优化。** 调整 React tree 之前，先衡量整条路径。
2. **Caching 是 freshness policy。** 静态内容、编辑更新，以及可变数据，各有不同的生命周期。
3. **可靠性是面向用户的。** 掉帧、内存增长、加载失败与 crash，打断的是同一段旅程。
4. **交付系统是产品的一部分。** 共用基础与更安全的 releases，会跨团队累积效益。

  <AccordionItem value="caching">
    <AccordionTrigger>2. 让 cache 匹配数据</AccordionTrigger>
    <AccordionContent>
      一个 content platform 需要快速的公开页面、即时的编辑更新，
      以及交互式 workspaces。单一 cache strategy 无法同时服务这三者。

      - 预先 generate 核心页面与最新的 **100 篇文章**
      - 按需 generate long-tail content
      - 当 Strapi 发布时，按 tag invalidate 受影响的页面
      - 在 server 上 prefetch 可变的 workspace 数据，然后 hydrate **TanStack Query**
      - 在 query keys 中纳入 organization 与 URL filters，以避免 tenant 或 search 碰撞

      Content site 达到 **LCP 低于 0.5 秒**、**CLS 低于 0.1**，以及
      PageSpeed 高于 **90**。Hydration 改善了交付；authorization 仍然
      属于 API 之后。
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="reliability">
    <AccordionTrigger>3. 拿掉用户看不见的工作</AccordionTrigger>
    <AccordionContent>
      对于一个图片密集的 React Native membership app，我们：

      - 用 **FlashList** 回收长列表
      - 调整 rendering windows，而不是急于 mount 全部内容
      - freeze 非活跃屏幕，并延迟 mounts
      - cache 远程图片，并避免过大的 assets
      - 只在 native-thread execution 有帮助时使用 **Reanimated**

      发布后仍持续进行 device profiling 与 **Sentry** monitoring。应用
      维持超过 **99.5% crash-free sessions**，给了我们具体的
      reliability baseline，而不是上线当天的主观感觉。
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="delivery">
    <AccordionTrigger>4. 改善 frontend 如何交付</AccordionTrigger>
    <AccordionContent>
      横跨 **15+ React 与 React Native applications**，重复的摩擦变成了
      delivery risk。我们投入于：

      - 用 **Radix**、**Tailwind CSS** 与可重用 hooks 建立共用 primitives
      - 在 **Storybook**、**Fumadocs** 与 MDX 中提供示例与指引
      - 以 **Cypress** 覆盖关键 journeys
      - 用 **SST** 将基础设施与 deployment configuration 写成代码

      SST 将 build 与 deployment 时间缩短了 **超过 50%**。这 15+
      个 applications 是作品集背景，不是 design-system 影响力的证明；那
      需要 adoption、duplication、onboarding 与 regression metrics。

## 「Senior」对我现在的意义

- 衡量 **用户旅程**，而不只是 component render time。
- 让 **架构对准瓶颈**，即使它落在 frontend repository 之外。
- 建模 **freshness 与 ownership**，而不是被动地加 caches。
- 用真实的 reliability signals **在发布后运营产品**。
- 通过共用基础、tests 与更安全的 delivery，改善 **下一位工程师** 的路径。
