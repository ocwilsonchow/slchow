Frontend 的 **regression tests** 保護用戶早已依賴的行為：表單仍然可以提交、draft 在請求失敗後仍然保留、login flow 在 refactor 之後仍然會落到正確位置。

<br />

- 它們不是為了追逐 coverage 百分比。
- 在**仍能證明行為、成本最低的那一層**攔截 regression——**Vitest**、**React Testing Library**，或 **Cypress**。

<br />

---

## 1. 測什麼、在哪裡測

按 **blast radius** 排優先順序，而不是按寫測試有多容易。

<br />

| Layer | Tool | Use when |
| --- | --- | --- |
| Unit | Vitest | Pure logic、reducers、parsers、URL/state helpers |
| Component | Vitest + React Testing Library | Interaction contracts：click → state → text/role |
| Integration-ish | Vitest + RTL + MSW | 搭配 mocked network 的 page sections |
| E2E | Cypress | 跨 routes 與 auth 的完整 critical journeys |

<br />

- 聚焦金錢、auth、資料遺失路徑、高流量入口流程，以及曾經上線過的 bug。
- 略過一次性 chrome 與純視覺 polish。
- 在**仍能證明行為、成本最低的那一層**攔截 regressions。
- 如果結果必須依賴 **real browser** 與 **real navigation** 才可信，就用 Cypress；否則留在 Vitest。
- **Failure：** 同一件事在每一層都證明一次。

<br />

## 2. 用 Vitest 與 RTL 攔截 Unit 與 Component Regressions

測 component regressions 時，測**用戶可觀察的結果**。

<br />

```tsx
import { render, screen } from "@testing-library/react"
import userEvent from "@testing-library/user-event"
import { describe, expect, it, vi } from "vitest"

import { DraftForm } from "./draft-form"

describe("DraftForm", () => {
  it("keeps draft when network fails", async () => {
    const user = userEvent.setup()
    const onSubmit = vi.fn().mockRejectedValue(new Error("network"))

    render(<DraftForm initialValue="hello" onSubmit={onSubmit} />)

    await user.clear(screen.getByRole("textbox", { name: /draft/i }))
    await user.type(screen.getByRole("textbox", { name: /draft/i }), "updated")
    await user.click(screen.getByRole("button", { name: /save/i }))

    expect(await screen.findByRole("alert")).toHaveTextContent(/could not save/i)
    expect(screen.getByRole("textbox", { name: /draft/i })).toHaveValue("updated")
    expect(screen.getByRole("button", { name: /save/i })).toBeEnabled()
  })

  it("disables save while a submit is in flight", async () => {
    const user = userEvent.setup()
    let resolveSubmit!: () => void
    const onSubmit = vi.fn(
      () =>
        new Promise<void>((resolve) => {
          resolveSubmit = resolve
        })
    )

    render(<DraftForm initialValue="hello" onSubmit={onSubmit} />)

    await user.click(screen.getByRole("button", { name: /save/i }))

    expect(screen.getByRole("button", { name: /save/i })).toBeDisabled()

    resolveSubmit()
    expect(await screen.findByRole("button", { name: /save/i })).toBeEnabled()
  })
})
```

<br />

- 用 **role** 與 accessible name 查詢，用 `userEvent` 驅動 UI，並 assert 用戶接下來能看到或做到什麼。
- 用它保護的 regression 來命名測試。`keeps draft when network fails` 對未來讀者的幫助，遠大於 `handles error`。
- 當 component 變得難以測試時，抽出 pure logic——formatting、validation、URL building——並對這些 functions 做 unit-test。把 component test 留在 wiring 與 interaction。
- **Failure：** assert internal state、CSS class lists，或 private function calls。

<br />

```ts
import { describe, expect, it } from "vitest"

import { getNextDraftStatus } from "./draft-status"

describe("getNextDraftStatus", () => {
  it("returns error without clearing the draft value", () => {
    expect(
      getNextDraftStatus({
        value: "updated",
        result: { ok: false, reason: "network" },
      })
    ).toEqual({
      value: "updated",
      status: "error",
      message: "Could not save",
    })
  })
})
```

### Testing Custom Hooks

當複雜 state logic 不需要 UI 時，用 `renderHook` 與 `act` 直接測 hook。

<br />

```tsx
import { renderHook, act } from "@testing-library/react"
import { describe, expect, it } from "vitest"

import { usePagination } from "./use-pagination"

describe("usePagination", () => {
  it("advances to the next page", () => {
    const { result } = renderHook(() => usePagination({ total: 50, perPage: 10 }))

    expect(result.current.page).toBe(1)

    act(() => {
      result.current.next()
    })

    expect(result.current.page).toBe(2)
  })
})
```

<br />

- 這能證明 state transitions，而不必 mount 不必要的 DOM。

<br />

### Type-Safe Test Data

對行為來說，優先用 **deterministic fixtures**，而不是寬泛的 snapshots。

<br />

```ts
type Note = { id: string; title: string; status: "draft" | "published" }

export function buildNote(overrides?: Partial<Note>): Note {
  return {
    id: "test-id",
    title: "Default Title",
    status: "draft",
    ...overrides,
  }
}

// Usage in a test:
// const publishedNote = buildNote({ status: "published" })
```

<br />

- Snapshots 對某些 serialization 場景有用，但當契約是「用戶仍然能從失敗的 save 裡恢復」時，它們是弱的 regression 信號。
- 用 TypeScript 的 `Partial<T>` 建立 type-safe data factories，而不必在每個測試裡重複大型 objects。

<br />

### Test Async States Explicitly

多數 data-driven components 不只成功態：initial 或 empty、loading、success、error、retry 或 recovery。

<br />

```tsx
import { HttpResponse, http } from "msw"
import { server } from "../test/server"
import type { Note } from "@/types"

it("retries after the first request fails", async () => {
  const user = userEvent.setup()
  let attempts = 0

  server.use(
    http.get("/api/notes", () => {
      attempts += 1

      if (attempts === 1) {
        return HttpResponse.json(
          { message: "Temporary failure" },
          { status: 503 }
        )
      }

      // TypeScript enforces that this matches the Note[] type
      return HttpResponse.json<Note[]>([
        { id: "1", title: "Regression playbook", status: "published" }
      ])
    })
  )

  render(<NotesList />)

  expect(await screen.findByRole("alert")).toHaveTextContent(
    /could not load notes/i
  )

  await user.click(screen.getByRole("button", { name: /retry/i }))

  expect(
    await screen.findByRole("link", { name: /regression playbook/i })
  ).toBeVisible()
})
```

<br />

- Regression 常常活在這些 states 之間的 **transition**。
- **MSW** 把測試留在 HTTP boundary，同時讓每個 response 都是 deterministic。
- 這個測試證明失敗是可見的、retry 仍然可能，以及後來的 success 會替換 error——而不必知道 component 用的是 `fetch`、query library，還是 custom hook。

## 3. 用 Cypress 保護 Critical-Path E2E

Cypress 保護的是那些只有搭配 routing、auth 與真實 page shell 才存在的 journeys。

<br />

```ts
// cypress/support/index.d.ts
declare global {
  namespace Cypress {
    interface Chainable {
      loginAs(email: string): Chainable<void>
    }
  }
}

// cypress/support/commands.ts
Cypress.Commands.add("loginAs", (email) => {
  cy.request("POST", "/api/test/login", { email })
})
```

<br />

```ts title="cypress/e2e/create-note.cy.ts"
describe("create note", () => {
  beforeEach(() => {
    cy.loginAs("writer@example.com")
    cy.seedNotes([])
  })

  it("creates a note and lands on the detail page", () => {
    cy.visit("/notes/new")

    cy.findByRole("textbox", { name: /title/i }).type("Regression playbook")
    cy.findByRole("textbox", { name: /body/i }).type(
      "Protect high-value behavior at the cheapest reliable layer."
    )
    cy.findByRole("button", { name: /publish/i }).click()

    cy.location("pathname").should("match", /\/notes\/.+/)
    cy.findByRole("heading", { name: /regression playbook/i }).should(
      "be.visible"
    )
  })
})
```

<br />

- 把這套 suite 保持很小：通常 **三到七條** journeys——sign in、完成核心產品任務、sign out 或到達一個耐久的 success state。
- Seed fixtures，讓測試不依賴 production content。Assert URL、heading、success message——而不是沿途每一個 CSS class。
- 透過 API 或 task 控制 **authentication**；expiry 重要時 freeze **time**；等待 named request 或可見結果；每個測試隔離 records；優先用 roles 與 labels（只有在沒有面向用戶的 selector 時才用 test ID）。
- 當 UI contract 不必靠完整 browser 就能證明時，edge cases 屬於 Vitest。Cypress 賺回成本的地方，是 false green 會把壞產品送上線的那些路徑。
- **Failure：** 單一測試 sign in、改 settings、create a note、search、delete，再 sign out。在耐久邊界切開 journeys。永遠不要等待任意 timeout。

<br />

## Takeaway

Frontend regression testing 最好當成一套 **triage system**。

<br />

- 在成本最低、仍然可靠的那一層保護高價值行為，從真實 failures 增長 coverage，並把 Cypress 保持夠薄，讓紅掉的 build 仍然有意義。
- 當某件事壞過一次，確保 suite 第二次會抓住它——最好用幾個月後讀起來仍然像 **product promise** 的測試名稱。
- 修 bug 時 **先寫會失敗的測試**，並確認它因正確原因失敗，再套上 fix。這個習慣背後的設計方式——對可觀察的 UI 行為做 Red, Green, Refactor——見 [Frontend Engineering 中的 Test-Driven Development](/notes/test-driven-development-in-frontend)。
- 本地跑 focused tests，PRs 上跑 unit/component suite，merge 前跑 critical E2E journeys。
- **Failure：** 把 flake 常態化。如果測試隨機失敗，先 quarantine，再修或刪。第三次才過的測試，仍然是 flaky test。略過 pixel-perfect visual diffs、窮盡的 E2E edge cases，以及對 framework internals 的 assertions。Manual exploratory testing 仍然重要。
