**Remix** 這個名字不再指向單一產品。2026 年講 "Remix vs Next.js"，其實是兩個問題：Next.js 對上 **React Router Framework Mode**（Remix v2 的 React successor），以及 **Remix 3** 還算不算同一場比較。

這篇 note 對準 **Next.js 16.3.2** App Router 與 **React Router 8.3.0**。Remix v2 已 end of life。Remix 3 是丟掉 React 的 beta。Next.js 的 rendering model 見 [深入理解 Next.js](/notes/understanding-next-js-in-depth)。Cache 詞彙見 [System Design 裡的 Caching](/notes/caching-in-system-design)。

<br />

## Pattern Map

| Name | Status | 是什麼 |
| --- | --- | --- |
| Remix v2 | End of life | React meta-framework。併入 React Router v7。React Router v8（2026 年 6 月）起不再有 security updates。 |
| React Router v8 Framework Mode | Production | Loaders、actions、nested routes、SSR / SPA / SSG。Remix v2 的官方 upgrade path。 |
| Remix 3 | Beta | 全新、**非 React** 的 framework：zero-dependency、bundler-free、model-first，建立在 Web APIs 上。沒有從 Remix v2 的 migration。 |
| Next.js 16.3 | Production | RSC-first 的 React platform。Turbopack、Cache Components、Instant Navigations。 |

<br />

Shopify 的 React Router team 在 [v8 announcement](https://remix.run/blog/react-router-v8) 講過：Remix v0–v2 是 React Router 的 feature branch。那些 ideas 併回去了。Remix 這個 brand 現在是另一個 full-stack JavaScript project。

**若要比較 React framework，比的是 Next.js 16.3 與 React Router 8 Framework Mode。** Remix 3 是另一個 category。

<br />

## 1. Philosophy

**Next.js** 是 batteries-included 的 React platform。它擁有 compiler（Turbopack）、React Server Components 實作、caching、images、fonts、metadata，以及 —— 在 Vercel 上 —— runtime。Programming model 是：預設在 server render、少送 JavaScript、用 `'use cache'` 明確 cache。

**React Router Framework Mode** 是 Vite-based 的 React framework，貼近 web platform。Routes 是 export `loader` / `action` / component 的 modules。Data 是 `Request` / `Response` / `FormData`。Progressive enhancement 是預設：`<Form>` 沒有 JavaScript 也能用。你也可以把 React Router 當 library（Declarative 或 Data mode），而不是完整 framework。

**Remix 3** 丟掉 React。UI 是 imperative handles 與 DOM mixins，不是 hooks。目標是一個 cohesive 的 `remix` package：server、router、data、UI、tests。

<br />

| | Next.js | React Router 8 | Remix 3 |
| --- | --- | --- | --- |
| Bet | React 的 server/client model 加上真正的 cache | HTTP、nested routes、automatic revalidation | 沒有 React 的 web platform |
| Default UI | Server Components | Client React + SSR | Imperative handles，不是 hooks |
| Grain | Platform | 可以當 framework 的 router | Zero-dependency full stack |

<br />

**Failure:** 把 Remix 3 當成「我 React app 的下一版 Remix」。沒有 upgrade path。Remix v2 的延續是 React Router。

## 2. Rendering

### Next.js — RSC + Cache Components + Instant Navigations

App Router 是 RSC-first。Pages 與 layouts 預設是 Server Components，除非加 `'use client'`。那個 boundary 的 React 側見 [React 19 新功能](/notes/react-19-new-features)。

開 `cacheComponents: true`（下一個 major 的方向）之後，rendering 是 **Partial Prerendering**：

- Static / `'use cache'` UI 變成 **static shell**（HTML + RSC payload），CDN 可以直接 serve。
- Uncached / request-time work（`cookies()`、`headers()`、live DB）在 `<Suspense>` 後面 stream。
- Direct visits 與 client navigations 應該要 instant，因為 shell 已經在 client。

16.3 的 **Instant Navigations**（`cacheComponents` + `partialPrefetching`）是把這套產品化：partial prefetch 可重用的 App Shell、DevTools 的 Instant Insights、Playwright 的 `instant()` helper，以及更好的 ISR —— unknown params 立刻拿到 shell，再在背景 upgrade。

<br />

```ts title="next.config.ts"
import type { NextConfig } from "next"

const nextConfig: NextConfig = {
  cacheComponents: true,
  partialPrefetching: true,
}

export default nextConfig
```

<br />

不開這些 flags 時，你仍在用較舊、較 implicit 的 fetch-cache / `revalidate` model。Team 在把 apps 推向明確的 `'use cache'`。

### React Router — classic SSR（RSC 仍 experimental）

Default Framework Mode 是 **SSR + nested route modules**。Navigation 時，client 為變更中的 routes fetch loaders；React hydrate document。你也可以：

- SPA mode（沒有 SSR）
- Build time pre-render 選定的 URLs
- Mix：pre-render `/` 與 `/blog`，其餘 SSR

RSC 以 **`unstable_reactRouterRSC`** 存在（Vite plugin + experimental `@vitejs/plugin-rsc`）。你可以 export `ServerComponent`、用 `'use client'` / `'use server'`、從 loaders 回 RSC。SPA mode、pre-rendering、custom build entries 在 preview 裡尚未完整。這**不是** production default。

**實際差異：** Next.js 的 RSC 故事成熟，而且是預設。React Router 的是 opt-in，仍 unstable。今天就要 production RSC，選 Next.js 較安全。

<br />

## 3. Routing

**Next.js** 是 `app/` 的 file-system routing：

- `app/blog/[slug]/page.tsx` → `/blog/:slug`
- Nested `layout.tsx` wrap children，sibling navigations 不會 remount
- Special files：`loading.tsx`、`error.tsx`、`not-found.tsx`、`route.ts`、`proxy.ts`（前身是 `middleware.ts`）
- Parallel routes、intercepting routes、route groups `(marketing)`
- 16.x 的 `params` 與 `searchParams` 是 **async**
- 16.3 的 **root params**（`next/root-params`）讓任何 Server Component 讀 `[lang]`，不必 prop drilling

**React Router** 用 route config（`routes.ts`）加上 route modules。Nested routes 是 first-class，比 Next 的 App Router 更早：

<br />

```ts title="app/routes.ts"
import { index, route } from "@react-router/dev/routes"

export default [
  index("./home.tsx"),
  route("products/:pid", "./product.tsx"),
]
```

<br />

Layouts 是帶 `<Outlet />` 的 parent routes。你拿到 type-safe `href()`、從 route module 生成的 `./+types/product`（params 與 loader data），也可以把 file conventions 與 programmatic config 混用。

**Tradeoff：** Next.js routing 比較「丟一個檔就有 URL」，外加 marketing/app patterns（intercepting routes、parallel slots）是 React Router 對不上的。React Router routing 更明確、更彈性（library vs framework），歷史上更強的是 **nested data loading** —— parent 與 child loaders 平行跑；child UI 等自己的 loader。

<br />

## 4. Data loading

這是日常最大的差異。

### Next.js — 在 component tree 裡 fetch

<br />

```tsx
async function ProductInfo({
  params,
}: {
  params: Promise<{ slug: string }>
}) {
  const { slug } = await params
  const product = await getProduct(slug) // 常搭配 'use cache'
  return <h1>{product.name}</h1>
}
```

<br />

Data 活在 Server Components。用 `<Suspense>`、`React.cache()`、`'use cache'` 加上 `cacheLife` / `cacheTag` 組合。沒有 route-level `loader`。若 parent await 了 child 也需要的 data，waterfall 是真的 footgun。

Route Handlers（`app/api/hello/route.ts`）給 HTTP APIs（`GET` / `POST` / …）。它們與 page data 分開。

### React Router — loaders 與 route 放一起

<br />

```tsx title="app/product.tsx"
import type { Route } from "./+types/product"
import { fakeDb } from "../db"

export async function loader({ params }: Route.LoaderArgs) {
  return fakeDb.getProduct(params.pid) // 從 client bundle 剝掉
}

export default function Product({ loaderData }: Route.ComponentProps) {
  return <h1>{loaderData.name}</h1>
}
```

<br />

- `loader` 在 server 跑（initial load **以及** client navigations）
- `clientLoader` 在 browser 跑；兩者可以並用
- Nested routes **平行** load；不必等 parent 結束 child 才開始
- Serialization 對齊 RSC-serializable types（為未來 RSC migration 預留）

**Mental model：** Next.js：「UI 是 data boundary。」React Router：「route 是 data boundary。」React Router 對 form-heavy CRUD 更簡單。Next 在你要 per-component streaming、partial cache、同一頁 mixed static/dynamic 時更強。

**Failure:** 在 Next.js Server Component 裡對獨立 data 做 sequential `await`。兩個都先 start，再用 `Promise.all`。獨立 work 的 sequential `await` 是你自己引入的 waterfall。這是 React/Next 的 contract，不是 React Router 的問題 —— RR sibling routes 的 loaders 本來就 overlap。

<br />

## 5. Mutations

### Next.js — Server Actions

<br />

```tsx
async function updateTitle(formData: FormData) {
  "use server"
  await db.update(/* ... */)
  revalidateTag("posts", "max") // 16.x: two-arg API
}
```

<br />

Actions 是你可以傳進 Client Components 的 functions。Revalidation 是 **手動**（`revalidateTag`、`revalidatePath`、`updateTag`）。你自己選要 invalidate 什麼。彈性大，也容易弄錯。

從 client 達得到的 Server Action 是 **externally callable entry point**。Arguments 是 hostile input，即使 TypeScript 說不是。見 [Next.js 裡的 Security](/notes/security-in-next-js)。

### React Router — route `action` + automatic revalidation

<br />

```tsx title="app/project.tsx"
import type { Route } from "./+types/project"
import { Form } from "react-router"
import { fakeDb } from "../db"

export async function action({ request }: Route.ActionArgs) {
  const formData = await request.formData()
  return fakeDb.updateProject({ title: formData.get("title") })
}

export default function Project({ actionData }: Route.ComponentProps) {
  return (
    <Form method="post">
      <input type="text" name="title" />
      <button type="submit">Submit</button>
    </Form>
  )
}
```

<br />

Action 結束後，**頁面上所有 active loaders 再跑一次**。UI 與 data 同步，不必跳 cache-tag 編舞。`useFetcher` 可以 mutate 而不 navigation。`clientAction` 在 browser 跑。

這仍是 Remix 的殺手鐧。Admin UIs、settings、CRUD —— 任何「POST 然後顯示新鮮 data」—— React Router 儀式較少。Next.js Server Actions 比較適合 mutation 是掛在 component 上的 function、而不是 route，以及你要 RSC 式的 progressive rendering 包住結果。

<br />

## 6. Caching

**Next.js 16.3** 擁有 React 生態裡最有野心的 cache：

| Primitive | Role |
| --- | --- |
| `'use cache'` | Cache function 或 component；args 成為 cache key |
| `cacheLife('hours')` | Freshness profile（`stale` / `revalidate` / `expire`） |
| `cacheTag` + `revalidateTag(tag, profile)` | On-demand invalidation |
| `'use cache: private'` | 依 cookie/header；活在 browser prefetch |
| `'use cache: remote'` | Durable shared store（serverless 需要；預設是 in-memory） |
| Partial Prefetching | App Shells 的 client cache |
| ISR + Cache Components | Unknown params：instant shell，然後 background fill |

<br />

舊的 implicit `fetch` cache 造成多年困惑。新 model 是 **預設 dynamic，你說 cache 才 cache**。代價：你必須學會 directives，並把 async work 放到 Suspense 後面。

**React Router** 沒有這種 first-party data cache。工具是 loader responses 上的 HTTP `Cache-Control`、CDN caching、以及你自己的 store。Pre-rendering 在 build time cache HTML/data。Mutation 之後的 revalidation 是「再跑 loaders」，不是「invalidate tag X」。

若產品是 content site、marketing 加 docs、或仍想要 CDN-fast shells 的 personalized app，Next.js 的 cache 是很大的優勢。若產品大多是 per-request authenticated data，React Router「不要 cache，只 revalidate loaders」更簡單，也比较難射自己的腳。

**Failure:** 把 `cookies()` 放在 Next.js layout 頂層，然後怪整條 route 變 dynamic。把 runtime read 推到 `<Suspense>` 後面（或 `'use cache: private'`），shell 才能 prerender。React Router 沒有這個 footgun，因為它不會假裝頁面是 static，除非你 pre-render 它。

<br />

## 7. Forms、progressive enhancement、要不要 JavaScript？

**React Router：** 真正的 `<form method="post">`（經 `<Form>`）即使 JavaScript 沒載入也會 post 到 action。Pending UI（`useNavigation`、`useFetcher.state`）是 additive。這是 Remix 最初的 thesis，現在仍然成立。

**Next.js：** Server Actions 理論上沒有 JavaScript 也能用（POST 到特殊 endpoint），但預設 DX 假設 hydrated client：`'use client'` forms、`useFormStatus`、`useOptimistic`。Progressive enhancement 做得到，但不是木頭的紋理。

公開、對 resilience 敏感的表面 —— 爛網路上的 e-commerce checkout、政府表單、content sites —— React Router 仍贏。Next.js 16.3 experimental 的 `useOffline`（讓 navigations/actions pending 再 retry）從 SPA-resilience 側處理類似問題，不是「zero JS」那一側。

## 8. Bundler、compiler、DX

| | Next.js 16.3 | React Router 8 |
| --- | --- | --- |
| Bundler | **Turbopack default** | **Vite 7+** |
| Dev memory | 相對早期 16.x 最多少 90% RAM（disk cache + eviction） | Vite 一貫的低 overhead HMR |
| Builds | Filesystem cache；有人報 ~5.5× 的 repeat CI builds | Vite；普遍快，較少「framework cache」 |
| Typecheck | `next build` 可用 **TypeScript 7**（native） | `react-router typegen` + `tsc` |
| React Compiler | Turbopack 裡 experimental 的 **Rust** compiler | 你在 Vite 接什麼就是什麼 |
| SSR throughput | Native Node streams；最多約 22% 更多 req/s | 經 adapters 的標準 SSR |
| Type safety | `PageProps<'/store/[slug]'>`、typed `href` | 從 route module 生成的 `./+types/*` |
| AI tooling | `node_modules` 裡的 versioned docs、`AGENTS.md` | v8 附帶的 agent skills |

<br />

Turbopack 不再是「未來」；它是 default。Vite 仍是更 portable、plugin-rich、「這就是一個 Vite app」的體驗。React Router Framework Mode 是 Vite plugin。Next.js 是自己的 compiler pipeline。React Compiler 內部見 [深入理解 React Compiler Internals](/notes/react-compiler-internals)。

v8 baselines：**Node 22.22+**、**React 19.2.7+**、**Vite 7+**、ESM-only。`react-router-dom` 沒了；DOM APIs 從 `react-router/dom` 來。Middleware **預設開啟**。Next.js 16 把 `middleware.ts` 改名成 **`proxy.ts`**。

<br />

## 9. Deployment 與 batteries

**Next.js** 任何能 `next start` 的 Node 都能跑。Image optimization 需要 `sharp`。Self-hosting 行得通；ISR、Cache Components、多 instance cache consistency 需要額外基礎設施（shared cache handler、CDN）。

- **在 Vercel 上最好：** Fluid Compute、ISR、image/font optimization、Cron、preview deploys。
- **在別處比以前好：** Build Adapters API 在 16.2 穩定；有官方 Netlify/Cloudflare 路徑。Cloudflare 仍不如 React Router 長年的 Workers adapter 那麼 native。

**React Router** 天生 runtime-agnostic：Node、Bun、Deno、Cloudflare Workers、Netlify、Vercel、Fly、你的 Express server。Loaders 講 `Request` / `Response`。Portability 仍是它贏，尤其 Workers / edge。

Next.js 出貨更多產品面：`next/image`、`next/font`、metadata / Open Graph、`next/link` prefetch、Route Handlers、`after()`、`connection()`、draft mode。React Router 出貨 web primitives —— sessions 與 cookies（`createCookieSessionStorage`）很好 —— 其餘你自己選。

Ecosystem 引力仍偏向 Next.js：更多職缺、更多 templates、更多 integrations。React Router 的 hiring pool 較小，但 Remix v2 → RR 的 upgrade path 是 Shopify 用 codemods 寫過的那條。

**Failure:** 把 Remix v2 app migrate 到 Next.js「為了保住 Remix」。Data layer（loaders vs Server Components）是 rewrite。React Router 8 才是延續。

<br />

## 10. Remix 3

Remix 3 在 React 意義上 **不是** Next.js 的替代。它：

- 不用 React
- 避開 hooks；用 `Handle`、`handle.update()`、DOM mixins
- 想要 zero dependencies、沒有 bundler
- 為人 **以及** LLMs 設計（skills 在盒裡、一個 package）
- 是 beta；APIs 每週在動
- **沒有** 從 Remix v2 的 upgrade path

把它當 greenfield experiment，放在新的 web-standard stacks 那一桶，而不是「我 React app 的下一版 Remix」。Scaffold 用 `npx remix@next new`。

<br />

## 11. Side by side

| Dimension | Next.js 16.3 | React Router 8 Framework |
| --- | --- | --- |
| Identity | Full React platform | Multi-strategy router + Vite framework |
| Default UI model | RSC + Client Components | Client React + SSR（RSC experimental） |
| Data | 在 Server Components 裡 fetch | `loader` / `clientLoader` |
| Mutations | Server Actions；手動 revalidate | `action`；自動 revalidate 所有 loaders |
| Cache | `'use cache'`、PPR、ISR、prefetch | HTTP / CDN / prerender |
| Forms without JS | 做得到，不是預設 | 預設 |
| Nested parallel data | 你自己結構 | Built in |
| File routing | 有，convention-heavy | Config + modules（optional FS） |
| Bundler | Turbopack | Vite 7 |
| Images / fonts / OG | Built in | BYO |
| Hosting | Vercel 最好；別處有 adapters | 任何 JS runtime |
| RSC in production | 是，預設 | Unstable preview |
| SPA option | 做得到；不是紋理 | First-class mode |
| Legacy | Pages Router 仍在 | Remix v2 / RR v6 EOL |
| Complexity | 碰到 cache / RSC 就高 | 較低，直到你需要 RSC / cache |

<br />

## 12. How to choose

**選 Next.js 16.3，若你：**

- 要 RSC、streaming、mixed static/dynamic pages 當預設
- 在意 CDN-fast shells、ISR、Instant Navigations
- 要 images、fonts、metadata、以及巨大的 ecosystem
- 部署到 Vercel（或能接受帶 cache handler 的 self-host Node）
- 在做 content + app hybrids、AI UIs、帶 personalization 的 marketing sites

**選 React Router 8 Framework Mode，若你：**

- 2023–2024 會選 Remix
- 要 loaders/actions、nested routes、「POST 然後全部刷新」
- 需要 Cloudflare Workers、Bun、或自訂 Node server，不想跟 adapters 打架
- 要 progressive enhancement 與較小的 conceptual surface
- 偏好 Vite，或可能先 SPA 再加 SSR
- 正在 migrate 現有 Remix v2 app（這是官方路徑）

**留在 Remix v2：** 不要。它是 EOL。升到 React Router 7/8。

**只在這種情況選 Remix 3：** 你在開一個非 React 的 experiment，並且接受 beta churn。

它們不再是兩個對等的「data API 不同的 React meta-frameworks」。Next.js 加碼 React 的 server architecture 與真正的 cache/prefetch runtime。Remix 的 React 故事變成 React Router，加碼 HTTP、nested routes、以及自己 revalidate 的 mutations。Remix 這個 brand 現在是非 React 的賭注。

最新細節見 [Next.js 16.3](https://nextjs.org/blog/next-16-3)、[Cache Components](https://nextjs.org/docs/app/getting-started/caching)、[React Router modes](https://reactrouter.com/start/modes)、[data loading](https://reactrouter.com/start/framework/data-loading)、[actions](https://reactrouter.com/start/framework/actions)、[upgrading from Remix](https://reactrouter.com/upgrading/remix)，以及 [Remix 3](https://remix.run/)。
