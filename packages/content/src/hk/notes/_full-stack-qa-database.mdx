## Database

<Accordion type="single" collapsible>
  <AccordionItem value="db-btree">
    <AccordionTrigger>1. B-Tree index 內部怎麼工作，為什麼它讓 equality 與 range lookups 變快？</AccordionTrigger>
    <AccordionContent>

      - Postgres 上的預設 index 是 **B-Tree**：一棵由 pages 組成的 balanced tree，通常 8KB。Internal pages 持有 separator keys 與 child pointers。Leaf pages 持有被 index 的 values 加上 heap tuple pointers，這些 leaves 按 key 順序串起來，所以一段 range 可以往前走，不必爬回 root。
      - **Equality：** 從 root 往下走，每一層讀一頁，直到含有該 key 的 leaf。Fanout 很大，所以即使大表，高度通常也只有三或四 —— 幾次 page reads，不是 heap scan。
      - **Range：** 用同樣的方式找到第一個 matching leaf，然後跟 sibling links。`BETWEEN`、有序的 inequality、indexed column 上的 `ORDER BY`，以及 `LIMIT`，都可以騎這次 walk。它不是 hash index。Hash 只幫 equality。Inserts、key updates 與 deletes 維護這棵樹。
      - 用 `EXPLAIN` 證明 access path。如果 column 被包在 function 裡、type 對不上、或 predicate 跳過了 composite key 的最左 columns，B-Tree 幫不上。Planner 選擇：[SQL 核心概念](/notes/core-sql-concepts)。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-composite-index">
    <AccordionTrigger>2. Composite index `(tenant_id, status, created_at)` 上，哪些 queries 能用它？解釋 leftmost-prefix matching。</AccordionTrigger>
    <AccordionContent>

      - `(tenant_id, status, created_at)` 是一把排好序的 key，不是三棵獨立的 indexes。**Leftmost-prefix matching** 的意思是：planner 只能在 predicate 仍是這把 key 的 prefix 時走這棵樹，更早的 columns 上等值，才能在更晚的 column 上做 range。
      - 能用它的 queries：`tenant_id` 上等值；`tenant_id` 加 `status`；三個都有 —— `tenant_id` 與 `status` 上等值，再在 `created_at` 上 range 或 sort。這段 range **只有** 前面的 columns 都是 equality 時才成立。
      - 跳過 `tenant_id`、只濾 `status`，不是一段連續的 slice。Postgres 18 的 **skip scan** 在缺 leading column 時仍能探測 B-Tree，但只在那一列 **low cardinality** 時 —— 它替代不了把 `tenant_id` 放第一位。
      - Keyset pagination：重複的 `created_at` 會 skip 或 repeat，除非 cursor 帶一條 unique tail —— `(tenant_id, status, created_at, id)`。`EXPLAIN` 仍得把條件顯示成 `Index Cond`，而不是 scan 之後的 filter。同一個思路：[SQL 核心概念](/notes/core-sql-concepts)。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-seq-scan">
    <AccordionTrigger>3. 讀這份 query plan：什麼時候 sequential scan 其實比 index scan 更對？</AccordionTrigger>
    <AccordionContent>

      - Plan 寫著 `Seq Scan on orders` 再加一個 `Filter`，預設不是 bug。Planner 是 cost-based。當按順序讀 heap 比穿過 index 再跳到隨機 heap pages 更便宜時，sequential scan 就是對的選擇。
      - 重要的是 **row counts**，不是 node 名字。**小表：** 幾頁 heap 再加上一棵 index 是多餘的活。**Low selectivity：** predicate 命中大多數 rows —— `status = 'active'` 佔 90% —— index scan 變成對幾乎整張表的隨機讀。
      - **這條 query 本來就要表的大部分。** 沒有選擇性 `WHERE` 的 aggregations，常常就該 seq-scan。Index 找出很多 pages、Postgres 想按 heap 順序拜訪時，bitmap heap scan 是中間地帶。**過期 stats：** `ANALYZE` 滯後會讓 seq scan 看起來「錯了」。`EXPLAIN (ANALYZE, BUFFERS)` 對照的是接近 production 的 counts，不是 50 行的 fixture。
      - `SET enable_seqscan = off` 不是 production 修法。該修的是 predicate、index 形狀、或那一列的 correlation。[SQL 核心概念](/notes/core-sql-concepts)：故意的 seq scan 仍是一份合法 plan。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-ignored-index">
    <AccordionTrigger>4. 給出 Postgres 忽略你 index 的四個原因（function on column、type mismatch、low selectivity、leading-wildcard LIKE）。</AccordionTrigger>
    <AccordionContent>

      - **Function on the column。** `WHERE lower(email) = $1` 用不了 `email` 上的 B-Tree。修法是 `lower(email)` 上的 expression index，或存 canonical form 再比 equality。把 timestamp 包進 `date_trunc`、或在 `WHERE` 裡 cast，是同一類陷阱。
      - **Type mismatch。** 讓 parameter type 與 column 對齊。常見失手是 `id::text = $1`（function 打在 indexed 那一側）對上 `$1::uuid`。
      - **Low selectivity。** `status` 上的 index，95% 的 rows 都是 `'active'`，等於一本指向幾乎整張 heap 的目錄。Planner 正確地偏向 sequential scan。Partial indexes —— `WHERE status = 'open'` —— 才是給稀有 slice 做 index 的方式。
      - **Leading-wildcard `LIKE`。** `LIKE '%acme%'` 走不了 column 上的 B-Tree。`LIKE 'acme%'` 可以，前提是相容的 collation 或 `text_pattern_ops`。Contains-search 的工具是 `pg_trgm` 與 GIN index。如果 predicate 是 `Filter` 而不是 `Index Cond`，這棵 index 只是裝飾。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-gin">
    <AccordionTrigger>5. 什麼時候該伸手拿 GIN 而不是 B-Tree —— 例如 JSONB containment 或 full-text search？</AccordionTrigger>
    <AccordionContent>

      - Lookup 是「這個 value 含不含這個 key」，而不是「沿著這列有序走」時，才用 **GIN**。B-Tree 存的是 sortable scalars。GIN 是 inverted index：每個 token、array element、或 JSONB key 指向含有它的 rows。Writes 更重。
      - **JSONB containment：** `WHERE metadata @> $1::jsonb` 是教科書式的 GIN query。`jsonb_ops` 是預設；只要 containment，`jsonb_path_ops` 更小。**Full-text：** `to_tsvector(...) @@ to_tsquery(...)` 要的是 `tsvector` 上的 GIN（或 GiST）。**Arrays：** overlap 與 membership 是 GIN 的地盤。**Trigram contains：** 帶 `pg_trgm` 的 leading-wildcard `LIKE`。
      - GIN 的 updates 更貴，給不了 document 上的 `ORDER BY`，JSONB 頻繁 churn 還會 bloat。Tenant-scoped 的 JSONB column，hot equality path 上的 `tenant_id` 仍該放進 B-Tree。
      - GIN 替代不了 `(tenant_id, created_at)`。有序 pagination 仍走 B-Tree。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-normalization">
    <AccordionTrigger>6. 簡要解釋 1NF–3NF，再給一個刻意 denormalize 才是對的 case。</AccordionTrigger>
    <AccordionContent>

      - **1NF：** atomic cells，沒有 repeating groups。三個 NDCs 不該塞進一個 text column 再在 app 裡拆。一張 line-item table 才是 repeating group 的正確做法。
      - **2NF：** 非 key 的 attributes 依賴 **整把** composite key。如果 key 是 `(order_id, sku)` 而 `customer_email` 住在 line 上，那封 email 屬於 `orders`。**3NF：** 沒有傳遞依賴。`department_id` 決定 `department_name`；沒有理由就把名字抄到每一筆 order 上。（ZIP **並不能** 唯一決定 city —— 那個例子是 folklore。）
      - **刻意 denormalize** 在 read path 才是事故時才對。藥房 dashboard 要看每個 tenant 的 fills-per-day，不該每次 page load 都 join `prescription_fills` 到 `prescriptions` 再到 `patients`。一行按 `(organization_id, day)` keyed 的 `fill_stats_daily`，從 write path 或 job 維護。
      - Update anomaly 被接受，write 有人負責：trigger、一次更新兩邊的 transaction，或可重跑的 rebuild job。當 `EXPLAIN` 說 join 是乘積時再 denormalize，normalized tables 仍是 source of truth。完整地圖：[System Design 裡的 Data Modeling](/notes/data-modeling-in-system-design)。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-isolation">
    <AccordionTrigger>7. 走一遍四個 isolation levels，以及各自擋住的 read phenomena（dirty、non-repeatable、phantom）。Postgres 預設是什麼？</AccordionTrigger>
    <AccordionContent>

      - **Dirty read：** 另一個 transaction 未提交的 write 可見。**Non-repeatable read：** 讀了一行，另一個 transaction 提交了對該行的 update，第二次讀看到 values 變了。**Phantom：** 再跑一次 predicate，出現了第一次結果裡沒有的新 rows。
      - 經典 SQL：**Read Uncommitted** 三種都允許。**Read Committed** 只擋住 dirty reads。**Repeatable Read** 擋住 dirty 與 non-repeatable；教科書定義裡 **phantoms 仍被允許**。**Serializable** 三種都擋住。
      - **Postgres 預設是 Read Committed。** 它實際上不會 dirty-read —— 因為 MVCC，`READ UNCOMMITTED` 被當成 Read Committed。**Postgres 的 Repeatable Read 是 snapshot isolation**，snapshot 之後才 commit 的 rows 不可見。這擋住了教科書裡的 phantom-read case。它 **擋不住** write skew。**Serializable** 用 SSI：盯著 cycle，abort 其中一個 session，帶上必須 retry 的 serialization failure。
      - Production 裡常見立場：大多數 request transactions 用 Read Committed，inventory 用一條 atomic `UPDATE`，只有本來會 write-skew 的短 transactions 才上 Serializable。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-long-tx">
    <AccordionTrigger>8. 為什麼 long-running transactions 在 production 裡危險（lock contention、vacuum bloat）？</AccordionTrigger>
    <AccordionContent>

      - 長 transaction 不是「一條慢 query」。它是 **locks，加上在 Repeatable Read 或 Serializable 下持有到 `COMMIT` 的 snapshot**。**Read Committed** 下 snapshot 是 statement-scoped；危險仍是一個 `idle in transaction` 的 session 握著 locks 或一個已分配的 XID。
      - **Lock contention。** `UPDATE`、`SELECT ... FOR UPDATE`、以及某些 `ALTER`，在 transaction 活著期間握著 row 或 table locks。別的 sessions 排隊。真正的問題常常是：一個 session 開了 transaction，然後等下游 HTTP call。`pg_stat_activity` 裡的 `idle in transaction` 就是那支槍。
      - **VACUUM bloat。** Autovacuum 收不回對某個 transaction 的 snapshot 仍可見的 dead tuples。最老的 `xmin` horizon 托住垃圾。Tables 與 indexes 變大，cache hit ratio 下降，長 transaction 終於結束後，同一批 queries 照樣更慢。Replica 上，`hot_standby_feedback` 能讓一條長的 read-only query 造出同樣的 horizon。
      - Transactions 保持極短，絕不在裡面等網絡，batch updates 拆成各自的 commits，設 statement timeout 與 idle-in-transaction timeout，盯 `n_dead_tup` 加上最老 transaction 的年齡。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-deadlocks">
    <AccordionTrigger>9. 兩個 transactions 之間 deadlock 怎麼發生，什麼 coding practices 能防住？</AccordionTrigger>
    <AccordionContent>

      - Deadlock 是兩個 sessions 互相等。Transaction A 更新了 row 1，然後等 row 2。Transaction B 已經更新了 row 2，然後等 row 1。Postgres 偵測到 cycle，用 `40P01` abort 其中一個 transaction。輸的那方必須 retry。
      - 不只兩行。Deadlock 可以牽進 foreign-key check、unique index insert，或一邊鎖住 parent order、另一邊先鎖住 child fill。形狀一樣：**不一致的 lock order**。
      - 做法：**按穩定順序鎖 rows**（id 從低到高，包括 triggers）；**把 transaction 做短** —— 不要在 `BEGIN` 裡面打 Stripe；**優先一條 statement**（`UPDATE inventory SET qty = qty - 1 WHERE ...`）；work queues 用 **`FOR UPDATE SKIP LOCKED`**；**碰到 `40P01` 就 retry**，帶 backoff。
      - 兩個 features 摸到重疊的 rows，lock order 就是 API 的一部分，跟 unique constraints 同一等級。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-n-plus-one">
    <AccordionTrigger>10. 怎麼發現並修掉 N+1 queries —— joins、batching、DataLoader 式 patterns？</AccordionTrigger>
    <AccordionContent>

      - N+1 是 parent list 一條 query，然後每個 child 再一條。一頁二十張 prescriptions 變成二十一次 round trips。ORMs 把它藏起來：循環裡的 `prescription.patient` 看起來像讀欄位。如果 request latency 隨 page size 線性漲，先當 N+1，直到 traces **數清** queries。DataLoader caches 是 **per request 且 per tenant**。
      - **一條 join。** 一條 statement：prescriptions 加 patients，同一個 `FROM` / `JOIN`。「至少有一條」用 `EXISTS`，不要 join 再加 `DISTINCT` —— [SQL 核心概念](/notes/core-sql-concepts)。
      - **Batching。** 先 load 這一頁 prescriptions，收集 patient ids，然後 `WHERE id = ANY($1)` 一次。在記憶體裡縫起來。這就是 DataLoader pattern：一個 tick 裡 coalesce keys，發一條 `IN` query，memoize。把每個 child row cache 起來，cold path 上仍是 N 次 lookups。先 batch。
      - GraphQL 裡，DataLoader 防止 resolvers 一不小心 N+1。Hono handlers 裡直接寫 join 或 `inArray`。把 pool 調大不是 N+1 的修法。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-for-update">
    <AccordionTrigger>11. 比較 SELECT ... FOR UPDATE 與 version-column optimistic lock。高 contention 的 inventory decrement 該用哪個？</AccordionTrigger>
    <AccordionContent>

      - **`SELECT ... FOR UPDATE`** 是 pessimistic。讀這一行，鎖握到 commit，再寫。另一個想要這一行的 session 等待。適合必須先讀幾行再計算的時候。`SKIP LOCKED` 是 queues 的變體。
      - **Version column** 是 optimistic。讀 `version`，寫 `WHERE id = $1 AND version = $2`，再 bump version。更新零行表示別人贏了；retry。Low contention 下 locks 更少。High contention 下變成 retry storm。
      - **高 contention 的 inventory decrement** 不是好的 optimistic-lock 問題。適合的是一條 atomic statement：`UPDATE inventory SET qty = qty - 1 WHERE sku = $1 AND qty >= 1 RETURNING qty`。回了一行表示 decrement 發生了。沒有 row 表示缺貨。
      - 業務規則寫不成那個 `WHERE` 時，`FOR UPDATE` 仍贏。Optimistic versioning 贏在很少碰撞的 documents。Flash-sale 流量下的 inventory，是 pessimistic 或 atomic-update 的 case。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-pooling">
    <AccordionTrigger>12. 為什麼 connection pooling 重要，PgBouncer 的 transaction mode 與 session mode 差在哪？</AccordionTrigger>
    <AccordionContent>

      - 一條 Postgres connection 是一個 **backend process**，不是便宜的 socket。App fleet 40 個 tasks 乘 20 條 connections，流量尖峰之前就是 800 個 backends。Database 在 CPU 還閒著時就倒在 connection count 上。**Pooling** 把許多 client sessions 複用到更少的 server connections 上。
      - **PgBouncer session mode** 把一條 server connection 釘在 client 上，直到整個 client session 結束。Session 功能可用：prepared statements、session `SET`、temp tables、session-level advisory locks、`LISTEN`。Client 斷開之前，backend 不會在 clients 之間 reuse。
      - **Transaction mode** 在 `COMMIT` 或 `ROLLBACK` 時歸還 server connection。這才是 fan-out 下真正 **reuse** backends 的 mode —— 超額需求排隊。SQL `PREPARE`、session `SET`、temp tables、以及 **session advisory locks** 會洩漏或消失。Protocol-level 的 named prepares 在 transaction mode 裡也能用，如果 PgBouncer 的 `max_prepared_statements` 開著（1.21+）。
      - **`SET LOCAL`** 與 transaction-scoped 的 `set_config(..., true)` 是安全的，因為它們在 commit 時死去 —— 這就是 RLS tenant context 屬於 transaction 內部、不屬於 session 的原因。Production 預設是 transaction mode，tenant GUCs 保持 transaction-local，不要開著 transaction 再等網絡，同時握著借來的 backend。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-zero-downtime">
    <AccordionTrigger>13. 設計一次 zero-downtime migration：給 1 億行的 table 加一列帶 default 的 NOT NULL column。為什麼 indexes 要用 CONCURRENTLY？</AccordionTrigger>
    <AccordionContent>

      - 現代 Postgres 裡，帶 **non-volatile** 常量的 `ALTER TABLE ... ADD COLUMN ... DEFAULT` 是一次 **catalog change**。Default 存在 metadata 裡，讀舊 rows 時才套上。新 rows 在 insert 時拿到。`now()` 是 **STABLE**，不是 VOLATILE，仍能走這條 fast-default path。`gen_random_uuid()` 是 volatile，會 rewrite，所以不是 1 億行上的 fast-path default。
      - **`NOT NULL` 仍需要 rollout。** Catalog default 並不表示 `NOT NULL` 該跟同一條 statement 打在一張巨大的 table 上。對已存的 values，按 **batches** backfill，每一批自己的 transaction，然後 `CHECK (col IS NOT NULL) NOT VALID`，`VALIDATE CONSTRAINT`，再 `SET NOT NULL`。Postgres 12+ 上，已經 validated 的 check 可以跳過第二次全表 verification。
      - **`CREATE INDEX CONCURRENTLY`** 是 index 這一側的對應物。普通 `CREATE INDEX` 會拿一把 **擋住 writes** 的鎖，直到整棵建完。1 億行上那就是一次 outage。`CONCURRENTLY` 用更弱的 locks、掃兩遍。它不能跑在 transaction 裡面，失敗時會留下必須 drop 的 invalid index。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-offset">
    <AccordionTrigger>14. 為什麼 OFFSET 100000 會變慢，keyset (cursor) pagination 在 SQL 層面怎麼修？</AccordionTrigger>
    <AccordionContent>

      - `OFFSET 100000` 慢，是因為 Postgres 仍要 **找到並丟掉** 那 100000 行。`LIMIT` 在那之後才生效。第 500 頁不是 seek 到一個書籤；它是「沿著排好序的結果走，直到扔掉 100000 行，再回傳下 20 行。」成本隨頁碼漲。深頁在 concurrent inserts 下還會 skip 或 repeat。
      - **Keyset pagination** seek 到已經回傳的最後一行。Sort key 必須 unique —— `(created_at, id)` —— 否則同一 timestamp 的兩行會 skip 或 duplicate：`WHERE (created_at, id) < ($cursor_created_at, $cursor_id) ORDER BY created_at DESC, id DESC LIMIT 20`。
      - 有 `(created_at DESC, id DESC)` 上的 index，或 tenant-scoped 的 `(tenant_id, created_at DESC, id DESC)`，這是從 cursor **之後** 開始的 index range，不是從表頭走起。
      - `OFFSET`「只為了頁碼」不該出現在 hot path。Planner 該在那把 tuple 上顯示 `Index Cond`，而不是 `Seq Scan` 加一個巨大的 offset。同一套 seek：[SQL 核心概念](/notes/core-sql-concepts)。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-replication">
    <AccordionTrigger>15. Streaming replication 怎麼工作，read-replica lag 會給 read-your-writes 帶來什麼 bugs？</AccordionTrigger>
    <AccordionContent>

      - Streaming replication 是 WAL shipping。Primary 把 changes 寫進 write-ahead log。WAL sender 把這些 records stream 到 replica。Replica replay 它們。常見的 **asynchronous** 配置裡，primary 上的 `COMMIT` 在 replica flush 或 replay 那次 commit 之前就回傳。只有 **`remote_apply`** 表示隨後打到那台 replica 的 read 能看見這次 write。Sync commit 買到的是 durability；它不會自動給 query-visible lag 設上界。
      - Replica 是一台 **replay machine**，不是第二台 primary。它很適合 read-mostly 流量與 failover。剛 commit 的 write 必須被看見的 read，不該送到這裡。
      - **Read-your-writes bugs：** 一次 `INSERT` 然後被轉到 replica 的 `GET` 回傳 404 —— 用戶 retry，寫出 duplicate。Inventory 在 primary 上 decrement 了，從 replica 列出的庫存往回閃。對著 replica 做 uniqueness checks 是 stale 的。
      - Production 預設：對剛 mutate 的 request **session stickiness** 打到 primary，或一條「read your writes」規則 —— 這次 session 寫過之後，短窗口內走 primary。Lag 是 async replication 的契約，application 必須遵守。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-partition-shard">
    <AccordionTrigger>16. Partitioning vs sharding：各自解決什麼問題，一張 table 什麼時候「夠大」該 partition？</AccordionTrigger>
    <AccordionContent>

      - **Partitioning** 仍是一台 Postgres。一張 table 拆成 child partitions —— `created_at` 上的 range、某個 status 上的 list、`organization_id` 上的 hash —— app query 的是 parent。贏在運維：每個 partition 自己 autovacuum，一個月的 fills 用 `DROP TABLE` 丟掉，**partition pruning** 讓帶日期邊界的 query 碰不到舊 partitions。Failure domain 仍是一台 primary、一條 WAL stream、一套 backup 故事。
      - **Sharding** 是多台 databases。按一把 key 路由 —— tenant，或 patient id 的 hash —— 到不同 primaries。這才是 **writes 與 storage** 撐過一台機器的方式。Cross-shard joins、unique constraints、transactions 變成 application 的問題。Sharding 是這一步：一台 primary 扛不住 write load 或 disk，並且存在一把幾乎從不需要 cross-shard 工作的 key。完整地圖：[System Design 裡的 Sharding](/notes/sharding-in-system-design)。
      - **夠大該 partition** 不是一句 row-count 口號。Partition 是在 vacuum、bloat、或 bulk delete 成為事故時，並且存在一把 queries 真正會 constrain 的 **stable partition key** —— 通常是時間。幾千萬行的窄 rows 不 partition 也可以。一張 200 萬行的 patients table 不是「為了 scale」去 partition 的。先 indexes 與 archival。完整地圖：[System Design 裡的 Data Modeling](/notes/data-modeling-in-system-design) 與 [SQL 核心概念](/notes/core-sql-concepts)。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-oltp-olap">
    <AccordionTrigger>17. OLTP vs OLAP：為什麼要把 Postgres 資料 pipe 進 Redshift，而不是在 primary 上跑 analytics？</AccordionTrigger>
    <AccordionContent>

      - **OLTP** 是 primary 的工作：大量小的 reads 與 writes、indexed point lookups、短 transactions、normalized tables。**OLAP** 正好相反：掃一大片、aggregate、group，也許把 facts hash-join 到 dimensions。Row-store Postgres 能做那份活。那份活仍不該放在 primary 上。
      - 對 fills 的 sequential scan **會趕走熱的 OLTP pages**。Hash aggregates 與 sorts 跟 `UPDATE inventory` 搶。一份 20 分鐘的 report 精神上就是長 transaction：它握著 snapshot，拖住 vacuum，把 checkout 需要的同一批 tables 撐胖。
      - Warehouses 是 columnar、compressed、為寬 scans 建的。Postgres 是為剛剛寫下的那一行建的。
      - **Read replica** 是輕量運維報表的中間地帶。它仍 replay 每一次 primary write，仍用 row store。它適合「這個 tenant 今天的 fills」，不適合去年的 SKU affinity。CDC 或 nightly unload 進 Redshift，把 analytics 硬體從 OLTP commit path 隔開。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-rls">
    <AccordionTrigger>18. 比較 Postgres Row-Level Security 與 application-level tenant filtering。各自的 failure modes 是什麼？</AccordionTrigger>
    <AccordionContent>

      - Application filtering 是每條 query 上的 `WHERE organization_id = $1`。**RLS** 是同一條規則貼在 table 上，由 Postgres 對 app 連上的 role 強制執行。**兩邊都要。** RLS 是 defense in depth；它不是寫 ambient queries 的許可證。契約：[用 Hono、Better Auth、Drizzle 與 Postgres RLS 打造 Multi-Tenant 後端](/notes/multi-tenant-backend-drizzle-hono-better-auth)。
      - **App-level failure modes：** 新的 list endpoint 忘了 filter。Admin script 或 JOIN 用了錯的 alias。Background job 沒有 session，按 primary key 跨 tenants load。Bug 是靜默的：回傳了另一個 tenant 的 rows。
      - **RLS failure modes：** 沒有 `FORCE ROW LEVEL SECURITY` 時的 **table owner bypass**；**`SECURITY DEFINER`** functions 以 owner 身份跑；**missing tenant GUC** —— 如果 policy 把缺 setting 當成「允許」，忘了 `set_config` 就是 fail-open；**`BYPASSRLS`**、superuser、以及 `TRUNCATE`（RLS 管不到）。Unique 與 FK checks 也繞過 row filters，所以 unique indexes 仍按 tenant 收窄。
      - `WHERE` 仍寫在 Drizzle 裡。忘了 filter 不能變成一次 cross-tenant 事故；RLS 讓這句話保持為真。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-soft-delete">
    <AccordionTrigger>19. Soft delete vs hard delete：對 unique constraints、indexes（partial indexes）、以及 data-retention compliance 意味著什麼。</AccordionTrigger>
    <AccordionContent>

      - **Soft delete** 是 `deleted_at timestamptz`（或一個 flag），每次 read 加上 `WHERE deleted_at IS NULL`。**Hard delete** 是 `DELETE`，這一行沒了。
      - **Unique constraints。** `email` 上的 unique index 仍看得到 soft-deleted rows。離開的 patient 在 purge 之前不能用同一封 email 再註冊。修法是 **partial unique index**：`(organization_id, email) WHERE deleted_at IS NULL` 上 unique。忘了 partial predicate，就是「已刪除」用戶把 unique key 鎖死到永遠的方式。
      - **Indexes。** 一張滿是 tombstones 的 table 上整棵 B-Tree，浪費空間與 cache。**Partial indexes** 覆蓋 hot path —— `WHERE deleted_at IS NULL` —— 如果 admin undelete UI 真的會查 deleted slice，再單獨一棵 index。
      - **Retention 與 compliance。** Soft delete 不是 erasure。如果要求是「刪掉個人資料」，一個 `deleted_at` flag 在 purge job hard-delete 或 anonymize 之前都算失敗，而且 backups 仍握著舊行。`deleted_at` 是產品上的 undo。Retention 是 purge policy 加上 backups。

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="db-design-pharmacy">
    <AccordionTrigger>20. Design exercise：multi-tenant 藥房系統的 schema —— prescriptions、不可變 audit trail、以及快的 per-tenant reporting。</AccordionTrigger>
    <AccordionContent>

      - Isolation 從 [用 Hono、Better Auth、Drizzle 與 Postgres RLS 打造 Multi-Tenant 後端](/notes/multi-tenant-backend-drizzle-hono-better-auth) 開始：shared schema，每一行 tenant-owned 的 row 上有 `organization_id`，RLS 加上顯式 filters，runtime role 不是 table owner，`FORCE RLS`。
      - **Core tables。** Tenant-owned：`patients`、`prescribers`、`medications`、`prescriptions`、`prescription_fills`。每一張都有 `organization_id NOT NULL`、FKs、以及 tenant-scoped uniqueness —— `(organization_id, mrn)`、`(organization_id, rx_number)`。Hot indexes 是 leftmost-prefix：work queues 用 `(organization_id, status, created_at)`。Prescriptions 是一台 state machine；簽過的 Rx 不會被靜默覆蓋。Inventory decrement 是那條 atomic `UPDATE ... WHERE qty >= 1`。
      - **不可變 audit。** `audit_events` 對 `app_user` 只給 `INSERT` 與 `SELECT` —— 沒有 `UPDATE` 或 `DELETE`。那是 **對該 role** 的 append-only，不是物理定律：table owner、superuser、或 DDL 仍能改寫。要 tamper-evidence，加一個單獨的 writer role、hash chaining 或 WORM export，並且沒有 ORM update path。`(organization_id, created_at)` 上 B-Tree；只有搜尋會鑽進 `payload` 時才在上面放 GIN。
      - **快的 per-tenant reporting。** Fills 不在 primary 上為 dashboards aggregate。`fill_stats_daily (organization_id, day, fill_count, ...)` 是 denormalized read model。重的 analytics 去 replica 或 warehouse。只有 vacuum 或丟掉舊資料成為事故時，才按月 partition fills，不是因為這張 table 存在。

    </AccordionContent>
