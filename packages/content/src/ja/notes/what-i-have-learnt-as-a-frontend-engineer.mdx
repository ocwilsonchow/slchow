4 年前、私は frontend engineering とはデザインを洗練された UI に変えることだと思っていた。本番環境は、component の外側も見るよう教えてくれた。アーキテクチャ、データの鮮度、信頼性、デリバリー、そして測定可能なユーザー成果——これらすべてが仕事の一部だ。

<br />

以下の指標はプロジェクト成果であり、普遍的なベンチマークではない。重要なのは、technical decision と観察可能な結果とのつながりだ。

<br />

## 成果の概要

- **Architecture：** page load **80%** 高速化、search latency **90%** 削減、PageSpeed **90** 超。
- **Web performance：** LCP **0.5 秒未満**、CLS **0.1 未満**。
- **Mobile reliability：** リリース後 **99.5% 超** の crash-free sessions。
- **Delivery：** **SST** により build および deployment 時間を **50% 以上** 短縮。

<br />

## 4 つの教訓

1. **アーキテクチャの変更は、局所最適化に勝る。** React tree を調整する前に、経路全体を測る。
2. **Caching は freshness policy である。** 静的コンテンツ、編集更新、可変データには、それぞれ異なるライフサイクルがある。
3. **信頼性はユーザー向きである。** フレーム落ち、メモリ増加、読み込み失敗、クラッシュ——いずれも同じジャーニーを中断する。
4. **デリバリーシステムはプロダクトの一部である。** 共有基盤とより安全な release は、チーム横断で効果が積み上がる。

      最大の効果は上流にあるかもしれない。参照：[Browser における Critical Rendering

  <AccordionItem value="caching">
    <AccordionTrigger>2. cache をデータに合わせる</AccordionTrigger>
    <AccordionContent>
      ある content platform には、高速な公開ページ、即時の編集更新、
      そしてインタラクティブな workspaces が必要だった。単一の cache strategy では三者を同時に満たせない。

      - コアページと最新 **100 記事** を事前 generate
      - long-tail content はオンデマンドで generate
      - Strapi 公開時に tag 単位で影響ページを invalidate
      - 可変 workspace データを server で prefetch し、**TanStack Query** で hydrate
      - query keys に organization と URL filters を含め、tenant や search の衝突を防ぐ

      content site は **LCP 0.5 秒未満**、**CLS 0.1 未満**、
      PageSpeed **90 超** を達成した。Hydration はデリバリーを改善したが、
      authorization は依然として API の背後に属する。
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="reliability">
    <AccordionTrigger>3. ユーザーが見えない仕事を取り除く</AccordionTrigger>
    <AccordionContent>
      画像が多い React Native membership app では、次を行った：

      - **FlashList** で長いリストをリサイクル
      - すべてを eager mount するのではなく rendering windows を調整
      - 非アクティブな画面を freeze し、mount を遅延
      - リモート画像を cache し、過大な assets を避ける
      - native-thread execution が効く箇所だけ **Reanimated** を使用

      リリース後も device profiling と **Sentry** monitoring を継続した。アプリは
      **99.5% 超** の crash-free sessions を維持し、
      ローンチ当日の印象ではなく、具体的な reliability baseline を与えてくれた。
    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="delivery">
    <AccordionTrigger>4. frontend の ship の仕方を改善する</AccordionTrigger>
    <AccordionContent>
      **15 以上の React および React Native applications** にわたり、繰り返される摩擦が
      delivery risk になっていた。次に投資した：

      - **Radix**、**Tailwind CSS**、再利用可能な hooks による共有 primitives
      - **Storybook**、**Fumadocs**、MDX における例とガイダンス
      - critical journeys 向けの **Cypress** カバレッジ

      SST は build および deployment 時間を **50% 以上** 短縮した。15 以上の
      applications はポートフォリオの文脈であり、design-system の影響力の証明ではない。それには
      adoption、duplication、onboarding、regression metrics が必要だ。

## 「Senior」の意味（今の私にとって）

- **ユーザー journey** を測る。component render time だけではない。
- **アーキテクチャをボトルネックに合わせる。** frontend repository の外にあっても。
- cache を後追いで足すのではなく、**freshness と ownership** をモデル化する。
- リリース後も、実際の reliability signals でプロダクトを**運用**する。
- 共有基盤、tests、より安全な delivery を通じて、**次の engineer** の道を良くする。
