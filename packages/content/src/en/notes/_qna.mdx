## API Design

<Accordion type="multiple">
  <AccordionItem value="api-restful">
    <AccordionTrigger>1. What makes an API "RESTful"? Which REST constraints do teams most often violate in practice?</AccordionTrigger>
    <AccordionContent>

      An API is not RESTful merely because it returns JSON over HTTP with noun-shaped URLs. REST is Fielding's constraints: **client-server**, **stateless**, **cacheable**, **layered**, optional **code-on-demand**, and a **uniform interface**. Uniform interface is the one that actually bites: identify resources, manipulate them through representations, send self-descriptive messages, and — the part almost nobody does — drive application state with hypermedia.

      Teams most often violate three things. First, **statelessness**: server-side conversational state that a later request must resume. Second, **cacheability**: every response is marked uncacheable, or GET has side effects so intermediaries cannot cache. Third, **uniform interface** and method semantics: verbs in paths, RPC-shaped bodies, and GET endpoints that write — that last one is a **safety** violation, not a REST-statelessness one. **HATEOAS** is the constraint people skip on purpose for internal product APIs; that is the honest statement rather than pretending the constraint is followed.

      The production default is a resource-oriented HTTP API that is stateless, uses cache headers where GET is safe, and keeps a consistent error envelope. Full hypermedia is not worth the investment unless the client is a generic agent. The common pitfall is labeling a POST-everything RPC "REST" and then being surprised when retries, caches, and gateways behave badly.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-idempotent-methods">
    <AccordionTrigger>2. Which HTTP methods are idempotent, and why does idempotency matter for retry-safe clients?</AccordionTrigger>
    <AccordionContent>

      **Idempotency** is a property of the method's effect on server state: repeating the same request N times leaves the resource in the same state as doing it once. The response body can still differ — a second DELETE may return 404 after the first returned 204 — and that is still idempotent. **Safe** methods are a stricter subset: the client is not requesting a resource change. Incidental logging or metering is allowed; a GET that creates an order is not.

      By spec, GET, HEAD, PUT, DELETE, OPTIONS, and TRACE are idempotent. POST is not. PATCH is not required to be; a JSON Merge Patch of the same document can be, a JSON Patch that `add`s to an array's `/-` path is not. That distinction is the interviewer's real test.

      It matters because clients, proxies, and meshes retry. A mobile app times out on create-payment and retries. A gateway retries a POST after a 502. Without idempotency the result is a double-charge or double-book. Clients should retry rather than lose the request, so the server must make that safe.

      The production default is GET cacheable and side-effect free, PUT and DELETE as true replacements and removals, and never assuming POST is retry-safe without an idempotency key. The common pitfall is a PUT that appends to a collection or a DELETE that decrements a counter — same method name, not idempotent.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-idempotency-keys">
    <AccordionTrigger>3. How would you implement idempotency keys for a POST endpoint that creates a payment or order?</AccordionTrigger>
    <AccordionContent>

      The **idempotency key** is a first-class part of the write path, not a cache. The client generates a UUID per user intent — tap Pay once — and sends it on `Idempotency-Key`. The server persists that key with a hash of the canonical request body, the resulting status, and the response payload, scoped to the tenant and the endpoint. A replay with the same key and the same body returns the stored response, including the original 201. Same key, different body is a 409. Keys expire after something like twenty-four hours, long enough for retries, short enough not to become a second database of orders.

      **Concurrency** is the hard part. Two in-flight POSTs with the same key must not create two payments. Insert a row with status pending under a unique constraint on tenant plus key, and let the loser wait or get a 409 until the winner commits. Do not process the payment before the row exists. If the process crashes after the processor charges but before the response is stored, a naive retry charges again — so pass the **same idempotency key to the provider**, persist their operation id, and reconcile pending rows instead of starting a second charge.

      The production default is to hash the body so a retried request cannot silently change amount. The common pitfall is a global key namespace: two tenants reuse a UUID and one receives the other's receipt. Always partition the uniqueness constraint by tenant.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-status-codes">
    <AccordionTrigger>4. When would you return 200 vs 201 vs 204? What about 400 vs 401 vs 403 vs 404 vs 409 vs 422?</AccordionTrigger>
    <AccordionContent>

      Pick the code that tells the client what to do next, not the code that looks fancy. **200** is a successful GET, PUT, or PATCH that returns a representation. **201** means a resource was created — usually POST, but also PUT to a new URL — and send `Location` when possible. **204** is success with no body — typically DELETE, or a PUT when the client already has the document.

      On the 4xx side keep a strict split. **400** is a malformed request: bad JSON, missing header. **415** is an unsupported media type, not a generic 400. **401** means the server does not know who the client is — missing or invalid credentials. **403** means the server knows who the client is and the client is not allowed. **404** is unknown resource; for private objects the production default is still 404 so existence is not leaked. **409** is a conflict with current state: unique constraint, stale version, idempotency key reused with a different body. **422** is well-formed JSON that fails business validation — amount negative, date in the past.

      The production default is a slightly boring 400/422 split rather than a 200 with an error flag in the JSON. The common pitfall is using 401 for authorization failures; clients then wipe the session and bounce the user to login when they simply lack a permission.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-pagination">
    <AccordionTrigger>5. Compare offset pagination and cursor-based pagination. Why does offset degrade on large, frequently-written tables?</AccordionTrigger>
    <AccordionContent>

      **Offset** pagination is page number plus page size, usually implemented as SQL `OFFSET` and `LIMIT`. It is easy to explain, lets a UI jump to page fifty, and is fine when the table is small and mostly static. **Cursor** pagination returns an opaque token for the last seen row; the next request seeks past that key on an indexed sort tuple such as `created_at` plus `id`. The client cannot jump arbitrarily, but each page is a range scan, not a discarded prefix.

      Offset degrades for two independent reasons. **Cost**: Postgres still walks the skipped rows to throw them away, so a deep page on a hot table is a large sequential read even with an index. **Correctness**: inserts and deletes shift the window. A new row at the top makes the client see a duplicate; a delete makes the client skip a row. On a frequently-written table that is not theoretical — it is the bug users describe as the list jumping.

      The production default is keyset cursors for feeds, search, and audit logs, and offset only for small admin screens where a page number is the product. The common pitfall is stuffing an offset inside a cursor string and calling it cursor pagination — the skip cost and skipped rows remain.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-error-format">
    <AccordionTrigger>6. Design a consistent error response format. Have you seen RFC 7807 (Problem Details), and would you adopt it?</AccordionTrigger>
    <AccordionContent>

      Every error should be machine-parseable without teaching each client a new shape. The envelope to ship is **RFC 9457 Problem Details** (it obsoletes RFC 7807): `type` as a stable URI for the error class, `title` as a short summary, `status` matching the HTTP code, `detail` as a human-readable instance message, and `instance` as a URI reference for this occurrence — often a request id, not a public URL. Content type is `application/problem+json`. For validation add an `errors` array of field, code, and message so a form can highlight inputs without scraping `detail`.

      Adopt 9457 for any public or partner API. Internally the same shape still applies even if the `type` URIs are never registered on the public web; the value is consistency, not the RFC stamp. A custom `code` string such as `order.already_paid` is useful for i18n and analytics; keep it in an extension member, which the RFC allows.

      The production default is to generate `instance` from a request id, log the same id, and never put stack traces or SQL in `detail`. The common pitfall is endpoints that sometimes return Problem Details and sometimes return a one-off JSON blob with `error` as a string — clients then special-case every route, which is the failure the format was meant to prevent.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-versioning">
    <AccordionTrigger>7. Compare API versioning strategies (URL path, header, query param). When is versioning actually necessary vs. avoidable with additive changes?</AccordionTrigger>
    <AccordionContent>

      Version only when a contract must break, not because a new feature shipped. **Additive** changes — new optional fields, new endpoints, new error codes — avoid a version only if clients already ignore unknown members. Version when a field is renamed or removed, a meaning changes, or pagination or auth changes in a way old clients cannot ignore.

      **Path** versioning such as `/v1/orders` is the strategy teams ship most often. It is visible in logs, trivial to route, and cache-friendly because the URI is the cache key. The cost is URL clutter and a long tail of `/v1` that never dies. **Header** versioning via `Accept` is closer to HTTP semantics and keeps paths stable; it is harder to debug in a browser, and caches will mix versions unless you send `Vary`. A **query parameter** is easy to use and easy to omit; caches will key it if configured, but it still looks optional when it is not.

      The production default is path versions for public HTTP APIs, keep v1 running until traffic dies, and put compatibility tests on the old contract. The common pitfall is minting `/v2` for additive fields and then maintaining two stacks that only differ by a key the old client would have ignored.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-rate-limiting">
    <AccordionTrigger>8. How do rate-limiting algorithms differ (fixed window, sliding window, token bucket)? What should the 429 response include?</AccordionTrigger>
    <AccordionContent>

      Rate limiting is how a shared backend is protected from a noisy or malicious client without pretending every caller is equal. **Fixed window** counts requests in a calendar bucket, say one minute. It is cheap in Redis — INCR plus EXPIRE — but it allows a double burst at the boundary: spend the quota at 00:59 and again at 01:00. **Sliding window** smooths that by weighting the previous bucket or storing timestamps; accuracy costs memory. **Token bucket** replenishes tokens at a steady rate up to a cap and **allows a bounded burst**. **Leaky bucket** drains queued work at a fixed rate and smooths bursts instead of permitting them. The production default for APIs is the token-bucket shape: a sustained rate plus a small burst for legitimate retries.

      A **429** should tell the client how to back off, not just say no. Send `Retry-After` in seconds, and expose `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` (or the IETF `RateLimit` header fields). The body should be Problem Details with a stable `type` so SDKs can branch. Scope the counter by API key or tenant, not only IP — NAT and mobile carriers otherwise punish a whole office.

      The common pitfall is a global per-IP limit on a B2B API: one corporate proxy exhausts the quota for every user behind it, and nobody gets a useful `Retry-After`.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-rest-graphql-trpc">
    <AccordionTrigger>9. REST vs GraphQL vs tRPC/RPC: give a concrete scenario where each is the right choice.</AccordionTrigger>
    <AccordionContent>

      The protocol follows from the client mix and the caching story, not from fashion. **REST** is the right default when the API is a public HTTP contract: many languages, CDNs, partners, and resources that map cleanly to URLs. A payments or billing API is the concrete case — `GET /invoices/id` is cacheable, idempotent POSTs have a story, and a Java client should not need a GraphQL runtime.

      **GraphQL** is the right choice when one product BFF serves web and mobile that need different slices of a nested graph and the cost is over-fetch and extra round trips. A dashboard that loads a project, its members, and their avatars in one query is the case to defend. Teams then own query cost, persisted queries, and authz per field.

      **tRPC** (or any typed RPC) is the right choice when the client and server are TypeScript in the same repo, the API is not a public product, and the win is shared types plus no schema duplication. An internal admin app talking to a Node API is that case.

      The production default is not to expose tRPC to third parties, and not to start a partner API in GraphQL unless the query shape is the product. The common pitfall is GraphQL as a public surface with unbounded queries and no persisted-query allowlist — one nested request becomes the N-plus-one and the outage.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-n-plus-one">
    <AccordionTrigger>10. How do you avoid N+1 queries when an endpoint returns nested resources? Embed vs. link related resources — tradeoffs?</AccordionTrigger>
    <AccordionContent>

      **N-plus-one** is one query for the parent list and then one query per row for nested data — N orders, then N customer lookups. On a 50-item page that is 51 round trips to Postgres, and it shows up as a latency cliff when the list grows. Avoid it by loading children in one query: `WHERE order_id IN (...)`, a join when cardinality is safe, or a DataLoader-style batch in the application so GraphQL resolvers or loop-in-code still collapse to one SQL statement per resource type per request.

      **Embed versus link** is the payload question after the query is fixed. Embedding related resources in the parent JSON minimizes client round trips and is the default for small, always-needed relations — an order's customer name. Linking (`customer_url` or a `relationships` object) keeps the parent cacheable and lets the client fetch the child when it needs it; it wins when the child is large, optional, or has a different cache lifetime. JSON:API-style `include` lets the caller choose.

      The production default is to cap what can be embedded and never embed an unbounded collection such as all events for an order. The common pitfall is a join that multiplies rows — one order with 200 line items duplicated across a customer join — then mapping in memory and calling it one query while allocating a huge result set.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-auth-s2s">
    <AccordionTrigger>11. Compare API keys, OAuth 2.0 client credentials, and JWT bearer tokens for server-to-server APIs.</AccordionTrigger>
    <AccordionContent>

      For server-to-server what matters is rotation, blast radius, and whether a user belongs in the token. **API keys** are a shared secret the client sends on every call, usually `Authorization: Bearer` or a custom header. They are easy to issue and easy to get wrong: long-lived, often logged, painful to rotate, no standard scopes. They remain appropriate for a simple partner integration or a webhook receiver where the other side cannot speak OAuth. Store only a hash, bind the key to a tenant, and support rotation with two active keys.

      **OAuth 2.0 client credentials** is a **grant**, not a token format. The client authenticates with `client_id` and `client_secret`, gets a short-lived access token — often a JWT — and the server enforces scopes. Revocation and rotation are the authorization server's job. That is the production default when the caller is another company.

      A **JWT bearer** token is the **format**: signed claims the resource server can validate locally with JWKS — signature, issuer, audience, expiry, and an explicit algorithm allowlist. That skips an introspection hop inside a mesh. Revocation is the weakness unless tokens are short or a denylist is kept. Client credentials can issue that JWT; a static JWT in a config file is a different, worse pattern.

      The common pitfall is a static API key in a query string — it lands in access logs and browser history — or a 24-hour JWT with no revoke path after a service account leaks.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-webhooks">
    <AccordionTrigger>12. Design a webhook delivery system: signing, retries with backoff, ordering guarantees, and idempotent receivers.</AccordionTrigger>
    <AccordionContent>

      Design webhooks as **at-least-once** delivery of signed events, and tell subscribers they must be idempotent. Each event gets a stable `event_id`. The body is JSON plus a timestamp. Sign `timestamp + body` with HMAC-SHA256 and send `X-Webhook-Signature` and `X-Webhook-Timestamp`. A stale timestamp only **narrows the replay window**; durable `event_id` dedup is what handles a replayed delivery. Secrets are rotated with a dual-key window.

      Retries use **exponential backoff** with jitter. Retry timeouts, **408**, **429** (honoring `Retry-After`), and retryable 5xx, then stop after a budget — say a dozen attempts over twenty-four hours — and land in a dead-letter queue. A 2xx ends the cycle. Global ordering is not promised. If order matters, partition by resource id so events for one invoice are serial, and include `sequence` or `updated_at` so the receiver can drop older state.

      The receiver should upsert on `event_id` and treat duplicates as success. The production default also defends the outbound worker: user-supplied URLs are SSRF risks, so block private CIDRs and require HTTPS.

      The common pitfall is retrying a handler that already returned 200 because the worker timed out reading the response — without idempotent receivers the result is double-provision. Document that, and include `event_id` in every payload.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-long-running">
    <AccordionTrigger>13. How do you expose a long-running operation over HTTP (e.g., a report generation)? Compare 202 + status polling vs. webhooks vs. WebSockets.</AccordionTrigger>
    <AccordionContent>

      HTTP is request-response; a report that takes minutes should not occupy that socket. Accept the job, persist an operation record, and return **202** with `Location` pointing at `/operations/id` (and often `Retry-After`). GET on that URL returns `pending`, `running`, `succeeded`, or `failed`, plus a result URL when done. That is firewall-friendly, works with every HTTP client, and scales because workers are a queue, not open connections. The cost is polling. Mitigate with a sensible interval, `Retry-After`, and a TTL so abandoned jobs die.

      A **webhook** is better when the caller is another server that can expose an HTTPS endpoint. The server pushes once on terminal state and still keeps the operation resource for audit. **WebSockets** (or SSE) are for a human UI that wants progress percent. They add connection state, sticky load balancing, and reconnect logic that should not be the only completion path.

      The production default is 202 plus polling as the source of truth, an optional webhook, and SSE for the dashboard. The common pitfall is a synchronous POST that sits on a 60-second gateway timeout — the client retries, the server enqueues twice, and nobody has an operation id to look up.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-put-patch">
    <AccordionTrigger>14. PUT vs PATCH: what's the semantic difference, and how do JSON Patch and JSON Merge Patch differ?</AccordionTrigger>
    <AccordionContent>

      **PUT** replaces the resource. The body is the new complete representation; omitted fields are gone or reset. That is why PUT is idempotent: sending the same document twice yields the same stored state. PUT is the method when the client has the full record — a settings document, a file blob.

      **PATCH** applies a delta. The method is not required to be idempotent. PATCH is the method when the client should change one field without accidentally wiping others it never fetched.

      **JSON Patch** (RFC 6902) is an array of operations — add, remove, replace, move, copy, test — aimed at a JSON pointer. It can express incrementing a counter poorly, but it can remove a single array element. It is powerful and easy to get wrong; a `remove` on the wrong pointer deletes data. **JSON Merge Patch** (RFC 7396) is a partial object: present keys overwrite, `null` deletes, omitted keys stay. Arrays are replaced as a whole, which is the usual complaint. Merge Patch is the production default for simple resource APIs because humans can read it.

      The production default is to require `If-Match` with an ETag on both PUT and PATCH so two tabs do not last-write-win. The common pitfall is documenting merge semantics while implementing PUT replacement — a partial body then silently **clears** omitted fields.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-conditional">
    <AccordionTrigger>15. How do ETag, Last-Modified, and Cache-Control enable conditional requests and bandwidth savings?</AccordionTrigger>
    <AccordionContent>

      Conditional requests let the client ask for the body only if it changed. An **ETag** is an opaque version of the representation — often a hash or a row version. On GET the client sends `If-None-Match`. If it matches, the server returns 304 with no body; caches and mobile radios skip the payload. On writes the client sends `If-Match`; if it does not match, the server returns 412 and refuses to clobber. That is optimistic concurrency and bandwidth saving from the same header pair.

      **Last-Modified** plus `If-Modified-Since` is the older, weaker form. Timestamp granularity can miss two updates in the same second, and clock skew across app servers makes it brittle. It is still emitted for dumb clients, but ETag is the real validator.

      **Cache-Control** tells intermediaries what they may store: `max-age` for freshness, `private` so a CDN does not serve one user's data to another, `no-store` for secrets. `must-revalidate` means a stale response must be successfully revalidated before reuse — not specifically "issue a conditional GET."

      The production default is a **strong** ETag only when equal tags mean byte-identical representations. A row version alone is not enough if the JSON shape can change. Otherwise send a weak validator. The common pitfall is a weak ETag on a PUT path, or sending `Cache-Control: public` on a tenant-scoped response — the CDN then leaks data across tenants.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-file-transfer">
    <AccordionTrigger>16. How would you design file upload/download in an API — multipart uploads vs. presigned S3 URLs? What changes at 5MB vs 5GB?</AccordionTrigger>
    <AccordionContent>

      Keep the API out of the byte path as the file grows. At about **5MB**, a `multipart/form-data` upload to the API is acceptable if the bytes need inspection — virus scan, EXIF strip, image transcode — and the app server can stream to object storage without buffering the whole file. A single presigned PUT is also fine at that size: the client asks the API for a URL, PUTs to S3, then confirms. Presign is the preference when the API does not need the bytes.

      At **5GB**, the app server must not proxy the object. Use S3 multipart upload with presigned part URLs, a part size around 50 to 100MB, and S3's **full-object checksums** (CRC/SHA-256), then verify size and checksum **server-side** before marking the upload ready. A client "complete" callback is not proof of integrity. `Content-MD5` is not a full-object checksum for multipart. Timeouts and body limits on the API still assume small JSON.

      Download is a short-lived presigned GET, or a signed CDN URL, never a public bucket. The API authorizes, then hands out a URL that expires in minutes.

      The common pitfall is `fs.readFile` or buffering `req` into memory on a 5GB upload — the process OOMs. Stream or presign; allowlist content types; scan asynchronously after the object lands.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-multi-tenant">
    <AccordionTrigger>17. In a multi-tenant API, where should tenant identity come from (subdomain, header, JWT claim), and how do you guarantee cross-tenant requests are rejected?</AccordionTrigger>
    <AccordionContent>

      Tenant identity must come from something the client cannot forge. The authenticated principal is the source of truth: a JWT claim such as `tenant_id`, or a session record the auth layer already bound to a tenant. A **subdomain** (`acme.api.example.com`) is a good routing hint and a good place to select a database or brand, but still resolve it to an internal tenant id and check it against the token. A client-supplied **header** such as `X-Tenant-Id` is acceptable only as a selector for platform admins who already passed a stronger check; for ordinary users it is spoofable and is not trusted.

      Cross-tenant rejection is defense in depth. The handler reads tenant from the auth context, never from the body. Every query includes that predicate. Postgres **RLS** is the backstop so a missing `WHERE` still returns zero rows — but only if the runtime role is **not** the table owner, does not have `BYPASSRLS`, and `FORCE ROW LEVEL SECURITY` is set. Tenant context is `SET LOCAL` so a pooled connection cannot keep the previous tenant. If a path id belongs to another tenant, return 404, not 403. Isolation is covered in [Building a Multi-Tenant Backend with Hono, Better Auth, Drizzle, and Postgres RLS](/notes/multi-tenant-backend-drizzle-hono-better-auth).

      The common pitfall is an endpoint that accepts `tenant_id` in JSON for convenience and a header that overrides the JWT. One crafted request and the result is a cross-tenant read.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-design-first">
    <AccordionTrigger>18. Design-first (OpenAPI spec) vs code-first: tradeoffs, and how does contract testing fit in?</AccordionTrigger>
    <AccordionContent>

      **Design-first** means the OpenAPI document is the contract teams review before writing handlers. That is the right call when the API has multiple consumer teams, generated SDKs, or a partner program. Status codes can be bikeshedded in a PR on YAML instead of after a mobile freeze. The cost is ceremony and drift: if CI does not fail when the server disagrees with the spec, the YAML becomes fiction.

      **Code-first** means the implementation is the source and OpenAPI is emitted from types or annotations. That is faster for an internal API in one repo, and the spec cannot silently omit a route that exists. The cost is that consumers see the contract after the code exists, and it is easy to leak internals into the public shape.

      **Contract testing** sits between them. Run schema validation of real responses against the spec in CI, and for mobile clients consumer-driven contracts (Pact or similar) fit: the consumer publishes the requests it will send, the provider verifies them on every build. That catches breaking changes even when OpenAPI was updated correctly in a way the app does not understand.

      The production default is design-first for public HTTP, code-first for tRPC-style internal apps, and never generating a spec that is not tested. The common pitfall is a beautiful OpenAPI site and a server that returned a different JSON last Tuesday.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-evolve-clients">
    <AccordionTrigger>19. How do you evolve an API without breaking existing mobile clients that may never update?</AccordionTrigger>
    <AccordionContent>

      Assume a fraction of mobile clients will never update. That means the server must stay compatible with the oldest build still allowed in the store, not with last week's app. The rule is **additive change**: new optional fields, new endpoints, new error codes the old client ignores. Never reuse a field name for a new meaning, never change a type, and never make a previously optional field required. Enums are a footgun — old clients crash or drop unknown values — so treat unknown enum members as ignore in the app and add new variants only when old builds can survive them.

      When a break is required, add a new resource or a path version and keep the old one until traffic is gone. Advertise deprecation with `Sunset` and `Deprecation` headers and in-app messaging, but do not rely on users updating. Feature flags on the server can hide new behavior from old `app-version` headers.

      The production default is a contract test suite that replays fixtures from old app versions. The common pitfall is tightening validation — rejecting extra fields or requiring a new header — which turns a never-update install into an instant outage even though the change looked like being strict.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="api-design-audit-log">
    <AccordionTrigger>20. Design exercise: a paginated, filterable audit-log API for a multi-tenant healthcare SaaS where auditors must only see their own tenant's data.</AccordionTrigger>
    <AccordionContent>

      This is an append-only, tenant-scoped read API, not a general search engine. Constraints to lock first: every event is immutable, every row has `tenant_id`, auditors authenticate as users in that tenant with an `auditor` role, and the API never accepts tenant as a filter the client chooses. Healthcare means the log is treated as PHI-adjacent — access to the log is itself logged.

      Shape: `GET /v1/audit-events` with a keyset cursor on `(occurred_at, id)`, page size cap of 100, and filters that all hit indexes: `actor_id`, `action`, `resource_type`, `resource_id`, `from`, `to`. Response is a list plus `next_cursor`. Offset pages are not offered. A single-event `GET /v1/audit-events/id` exists for deep links and still enforces tenant.

      Authz: tenant from the JWT claim, role check, then RLS as the backstop so a missing predicate still returns empty. Cross-tenant ids return 404. Isolation is covered in [Building a Multi-Tenant Backend with Hono, Better Auth, Drizzle, and Postgres RLS](/notes/multi-tenant-backend-drizzle-hono-better-auth).

      Failure modes: using offset on a hot events table; filtering in memory after a wide select; writing request logs that duplicate the audit payload and leak into a shared log vendor; an export endpoint that streams another tenant because `tenant_id` was taken from query. Refuse that parameter even for super-admin unless it is a separate break-glass service with its own audit trail.

  <AccordionItem value="be-event-loop">
    <AccordionTrigger>1. Walk through the Node.js event loop phases. Where do setTimeout, setImmediate, process.nextTick, and resolved promises run?</AccordionTrigger>
    <AccordionContent>

    Node is not the browser. The walk is not HTML’s task, microtask, then render. Node is **libuv phases**. One iteration is roughly **timers**, pending callbacks, idle/prepare, **poll**, **check**, then close callbacks. `setTimeout` and `setImmediate` sit on phases. `process.nextTick` and resolved Promises sit on extra queues that drain **after the current operation**, between those phases — not as a phase of their own.

    - **`setTimeout` / `setInterval`**: **timers** phase, once the delay has elapsed. The delay is a lower bound, not a promise of “now.”
    - **`setImmediate`**: **check** phase, after **poll**.
    - **`process.nextTick`**: drains **before** Promise jobs, after the current operation. Higher priority than Promise `.then`. A nextTick loop **starves I/O** the way a browser microtask loop starves rendering.
    - **Promise `.then` / `queueMicrotask`**: microtask queue **after** `nextTick`.

    From the main module, `setTimeout(fn, 0)` versus `setImmediate` is famously unordered. From an I/O callback, `setImmediate` usually wins because check follows poll in the same iteration.

    ```
    process.nextTick(() => console.log("nextTick"))
    Promise.resolve().then(() => console.log("promise"))
    setImmediate(() => console.log("immediate"))
    setTimeout(() => console.log("timeout"), 0)
    ```

    In production, `nextTick` is never spun to “yield.” A Promise or `queueMicrotask` is the after-this-stack choice without jumping the Promise queue. The common pitfall is porting a browser ordering puzzle to Node and trusting the log. Full map: [The JavaScript Event Loop in Depth](/notes/javascript-event-loop-in-depth).

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-nodejs-wrong">
    <AccordionTrigger>2. When is Node.js the wrong choice? How do you handle CPU-bound work in a Node service?</AccordionTrigger>
    <AccordionContent>

    Node is a strong default for **I/O-bound** APIs: many open sockets, JSON in and out, waiting on Postgres and HTTP. Node is the wrong default when the **event-loop thread** is the product. One hot `while`, a sync hash, a huge JSON parse, or an in-process image pipeline stalls **every** connection on that process. Extra replicas do not fix a handler that pegs a core; they multiply the bill. If the domain is CPU-first — transcode, ML inference, tight crypto, bulk transforms — the production choice is a runtime or a worker fleet that matches, rather than hiding a thread pool behind an Express facade.

    CPU-bound work **inside** a Node service:

    - keep HTTP handlers **short** and I/O-ish; accept, persist, return
    - **`worker_threads`** or a child process for bounded in-process CPU, with a **pool cap**
    - better: **enqueue** the job and let workers own it — often not Node: Go, a native addon, or a managed transcode API
    - watch **event-loop delay**, not only request rate

    Production looks like “202 and a job id,” not “await the pixels in the POST.” `async` does not make arithmetic concurrent. The common pitfall is shipping CPU as `await tightLoop()` and calling it scalable because the framework is async. Health checks on that process lie until the loop runs again. If the stack must stay on Node, isolate CPU so a crashed worker is not the API process.

    </AccordionContent>

  <AccordionItem value="be-stateless">
    <AccordionTrigger>3. What does "stateless service" mean, and why does it matter for horizontal scaling behind a load balancer?</AccordionTrigger>
    <AccordionContent>

    A **stateless service** means any replica can handle any request without local memory of the last one. Session, uploads, cart, job progress — those live in **Postgres, Redis, S3, or the token**, not in the process. The process still has RAM: JIT, connection pools, LRU. That memory must be **discardable**. If this instance dies, the user is not stuck on a machine that no longer exists.

    It matters behind a load balancer because the fleet can **scale out** with round-robin, replace tasks on deploy, and skip sticky sessions. Sticky sessions are a confession that something was stored on the box. Horizontal scaling is then a lie: a task cannot drain without dropping people, and capacity cannot be added without hashing users to new empty memory.

    In production, sessions live in Redis or a signed JWT, files in object storage, rate-limit counters in Redis, and WebSocket fan-out on a pub/sub backplane. Local cache is a performance hint, not a source of truth. The design is that a replica can vanish mid-flight and the next request still has enough durable state to continue.

    The common pitfall is half-stateless: auth in Redis, but uploads in `/tmp`, or in-memory maps of socket ids. It works on one ECS task and breaks at two. Another: sticky sessions that hide the bug until the balancer drains a task mid-session and “random” users log out.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-async-queue">
    <AccordionTrigger>4. When should a request be handled asynchronously via a queue instead of synchronously in the request cycle?</AccordionTrigger>
    <AccordionContent>

    Work comes off the request cycle when the **HTTP response does not need the finished result**, or when the work is slow, bursty, or must **retry after this process is gone**. Email, outbound webhooks, thumbnails, invoices, search indexing, anything that talks to a flaky third party — that is a **queue**. The request authenticates, authorizes, **persists the intent**, enqueues, and returns **202** with an id the client can poll. The load balancer’s timeout is no longer the workflow timeout.

    It stays synchronous when the user cannot continue without the answer: password check, a price that must be correct on screen, a payment **authorization** the UI is about to display. Even then the handler stays thin. A five-step saga does not fold into one POST just because it is easier to read in one file.

    Production rules: an **idempotency key** on the enqueue, a worker that can fail loudly, and a status row the user can read. Timeouts and backoff belong to the worker. If it must happen even when the queue is down, the **database write in the request** is the source of truth; the queue is a relay.

    The common pitfall is **sync-over-async**: enqueue then block the socket until the worker finishes. The broker was paid for and the connection is still held. The other is queueing work that has not been durably recorded — crash equals lost intent. If the business said it happened, it hit disk in the request, then the queue.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-delivery-semantics">
    <AccordionTrigger>5. Explain at-least-once vs at-most-once delivery. How do you build an idempotent consumer given at-least-once semantics?</AccordionTrigger>
    <AccordionContent>

    **At-most-once** means send and forget: duplicates are rare, **loss is allowed**. **At-least-once** means retry until ack: **duplicates are allowed**, loss is not. Most brokers in production are at-least-once. “Exactly-once” in application space is usually at-least-once **plus an idempotent consumer**, not a broker checkbox that can be trusted across HTTP, queues, and process crashes.

    Given at-least-once, processing twice is a no-op:

    - a stable **event id** from the producer (or a hash of a natural key)
    - an **inbox** table with a unique constraint on that id
    - **database effects and the inbox insert in one transaction**. For Stripe or email, persist an outbox/operation row and pass the provider's idempotency key **before** ack
    - side effects as **upserts** (“status is paid”) not blind increments unless the increment is keyed by the same event id
    - **ack after** that durable write

    In production, publishers stay boring: same key, same payload, **outbox** on the write side so dual-write does not happen. Consumers stay idempotent anyway, because retries still happen.

    The common pitfall is acking before the side effect, or doing the side effect without recording the id. The retry then double-charges, double-emails, or double-ships. Another: catching errors and still acking so the poison message vanishes. At-least-once only helps if failure **nacks** and success is **idempotent**. Loss and duplication are both bugs; the production choice is which one to engineer for, then the other is engineered away in the consumer.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-retry-strategy">
    <AccordionTrigger>6. Design a retry strategy for a failing worker: exponential backoff, jitter, max attempts, and dead-letter queues.</AccordionTrigger>
    <AccordionContent>

    A worker retry policy is how failure happens **without melting the dependency**. Classify first. Timeouts, 503s, lock contention, “connection reset” — **retry**. Validation errors, 400s, unknown event types — **do not retry**; they will not heal and they will occupy the consumer forever.

    Then four controls:

    - **exponential backoff**: wait `base * 2^attempt`, with a cap so attempt twenty does not sleep for hours
    - **jitter**: full jitter, so ten thousand workers do not wake on the same millisecond after an outage
    - **max attempts**: a hard ceiling so poison cannot loop all night
    - **dead-letter queue**: after the ceiling, park the payload, increment a metric, page if DLQ depth rises

    In production the retry lives in the **queue** (visibility timeout, built-in backoff) or a library with the same shape — not a `while` inside the handler. Attempt count is logged on every failure. Retry only **idempotent** handlers, because at-least-once plus retry is how double-charge happens.

    The common pitfall is retrying a non-idempotent POST, or retrying forever with no DLQ so one bad JSON sits on a hot partition. The other is backing off **without jitter** after a shared outage — that is a thundering herd scheduled by the backoff. Alerts sit on retry rate and on DLQ, not only on HTTP 500s. A silent DLQ is a lost business event with extra steps.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-caching">
    <AccordionTrigger>7. Compare cache-aside, read-through, write-through, and write-behind caching. What is cache stampede and how do you prevent it?</AccordionTrigger>
    <AccordionContent>

    The cache write path is chosen on purpose. “Put Redis in front” is not a strategy.

    - **Cache-aside**: the app reads Redis, on miss loads the DB and fills the cache. This is the usual production choice. The app owns TTL and invalidation.
    - **Read-through**: the cache library loads on miss. Convenient, less control, same stampede risk.
    - **Write-through**: every write hits cache and DB before success is returned. The cache stays warm; write latency includes both.
    - **Write-behind**: write the cache, flush the DB later. Fast writes; **durability** is the trade. A crash can lose dirty data.

    **Cache stampede** is a hot key expiring and a thousand requests missing together, all hitting Postgres. It looks like a periodic CPU cliff at TTL boundaries. Prevention: **singleflight** or a lock so one request fills and others wait; **stale-while-revalidate** so stale is served while one refresh runs; probabilistic early expiry so not every key dies at once; a tiny in-process cache in front of Redis for the hottest keys.

    In production the choice is cache-aside with explicit TTLs, versioned keys, and invalidation on write when freshness matters. A permission decision is never cached under a key that omits user or tenant.

    The common pitfall is stampede plus caching **transient failures** for a long TTL, or treating a dependency 500 as a cached “not found.” Short negative caching for a real miss can prevent penetration; caching a 500 is how an outage becomes sticky. Write-behind on money is another. Stampede is not “Redis is slow”; it is “every client was synchronized on expiry.”

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-saga-outbox">
    <AccordionTrigger>8. How do you keep state consistent across two services without distributed transactions? Explain the saga and outbox patterns.</AccordionTrigger>
    <AccordionContent>

    Distributed transactions are not run across services. Two-phase commit exists, but it **blocks on in-doubt transactions** and couples availability of every participant. Each service’s database stays transactional; coordination is with messages.

    A **saga** is a sequence of local transactions. If step three fails, **compensations** run for one and two — not a rollback of someone else’s DB. Choreography: each service emits events and the others react. Orchestration: a coordinator drives the steps and holds visible state. Choreography fits when the flow is short; orchestration when the graph is long and a dashboard of “where is this order stuck” is needed.

    The **outbox** fixes the dual-write: update the order row and publish `OrderPlaced`. Commit then publish, and the process can die and the event never leaves. Publish then commit, and consumers see an order that rolled back. Outbox: in the **same Postgres transaction**, the business row and an outbox row are written. A relay publishes outbox rows to the broker. Delivery is still at-least-once, so consumers stay idempotent.

    The common pitfall is treating compensation as undo. A payment compensation is a **refund**, with its own audit, not a time machine — and the compensation itself must be durable and retryable because it can fail. The other is skipping the outbox and hoping a send after `COMMIT` is good enough. It is not, at the first crash. Consistency here means “the system can explain and repair,” not “both DBs locked as one.”

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-eventual-consistency">
    <AccordionTrigger>9. What is eventual consistency, and how do you give users read-your-writes behavior on top of it?</AccordionTrigger>
    <AccordionContent>

    **Eventual consistency** means replicas or services **converge** if writes stop; it does not mean the next read sees the write that just landed. Cross-region replicas, search indexes, materialized views, and other services’ projections are eventually consistent. The user-facing bug is: a POST creates a resource, a GET of the list misses it, so the user clicks again and now there are two.

    **Read-your-writes** is a session guarantee on top of that, for the actor who just mutated:

    - send that user’s subsequent reads to the **primary** for a short window
    - return the written entity in the **POST response** and have the client merge it, so the UI does not need an immediate GET from a lagging replica
    - a **version** or timestamp the client sends, and the read path waits until the replica is past it
    - sticky routing to the writer when required

    In production most of the product can be slightly stale — feeds, counts, search. The person who just saved cannot be. The production choice is explicit per endpoint instead of promising “the system is consistent.”

    The common pitfall is hiding replica lag behind a spinner that refetches the **same replica**. Users duplicate orders. Another: caching the GET in front of the replica so even a primary-read fix never lands. Eventual consistency is fine if the UI does not treat a missing row as “please try the write again.”

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-locking">
    <AccordionTrigger>10. Optimistic vs pessimistic locking in application code — give a concrete case for each.</AccordionTrigger>
    <AccordionContent>

    **Optimistic locking** assumes conflict is rare. The row is read with a `version` (or `updated_at`). On write the update is only `WHERE id = $1 AND version = $2` and the version is bumped. Zero rows updated means someone else won; retry or tell the user. Concrete case: two people saving a **settings document**, or a user updating a profile. Contention is low. A database lock is not held while they stare at a form.

    **Pessimistic locking** assumes conflict is likely, or the check-then-act must be exclusive. `SELECT ... FOR UPDATE` in a transaction, then write. Concrete case: **decrementing inventory** for the last SKU, booking a unique seat, assigning a unique sequential invoice number. Two transactions cannot both believe they got the last item. The lock is the product.

    In production the default is optimistic at the application layer — a version column on editable rows — and pessimistic for a few hot invariants inside a **short** transaction. They are never mixed accidentally on the same row without knowing which one wins.

    The common pitfall: optimistic on a hot row becomes a retry storm. Pessimistic while calling Stripe inside the open transaction holds locks for hundreds of milliseconds and the pool dies. Also lock-order deadlocks: always lock rows in the same id order. A pessimistic lock is never held across an HTTP call. Locks are for the database’s truth, not for waiting on a vendor.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-connection-pool">
    <AccordionTrigger>11. How do you size a database connection pool? Why do serverless/ECS-scale-out architectures break naive pooling, and how does PgBouncer help?</AccordionTrigger>
    <AccordionContent>

    A pool is a **cap on Postgres sessions**, not a performance dial turned to 100. Sizing starts from the **database** backward: `max_connections` minus superuser headroom, divided by **how many app processes** will exist at peak, then a little for migrations and admin. Per Node process a typical start is around **10–20**. Watch pool wait time, not only query time. “Cores times two” is a rumor; the hard constraint is the server.

    **Serverless and ECS scale-out** break naive pooling because **every task or Lambda execution environment** opens its own pool. Fifty tasks times twenty connections is a thousand sessions before traffic is interesting. Lambdas make it worse: burst concurrency times pool size, then idle environments that still hold sessions. Postgres spends its time on process overhead; queries wait, then the app opens more connections to “fix” wait.

    **PgBouncer** (or RDS Proxy) sits in front and **multiplexes**. Transaction pooling: many app connections share few server connections, released at transaction end. The app still has a small pool; the bouncer absorbs fan-out.

    The common pitfall is `pool_size = 100` copied from a blog into a service that autoscales to 30. Another: transaction pooling while using session features — temp tables, `SET`, some prepared-statement modes — then mysterious cross-talk. Transactions stay short, and a connection ceiling is pinned in infra tests, not only in local Docker. The pool is a budget shared with every replica.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-graceful-shutdown">
    <AccordionTrigger>12. What happens during a graceful shutdown? How do you drain in-flight requests and queue consumers on SIGTERM?</AccordionTrigger>
    <AccordionContent>

    **Graceful shutdown** is: stop being handed **new** work, finish **in-flight** work, close resources, then exit. On ECS or Kubernetes, **SIGTERM** arrives, then a grace period, then **SIGKILL**. If SIGTERM is ignored, the process is killed mid-query and mid-response.

    On SIGTERM:

    - mark **not ready** so the load balancer detaches the instance
    - stop the HTTP server listening; wait for open requests with a **deadline** shorter than the grace period
    - queue consumers: **stop fetching**, let current messages finish, **nack** if the deadline hits so they redeliver
    - close the DB pool last
    - prefer letting the event loop empty; force `process.exit` only if something hung past the deadline

    In production the deadline is explicit, logged, and less than `terminationGracePeriodSeconds`. The test is SIGTERM in staging, not only SIGINT on a laptop.

    The common pitfall is exiting on SIGTERM immediately: in-flight POSTs die, brokers redeliver, users see 502. The other is draining HTTP but **keeping consumers running** until kill — those offsets are a mess. Also: readiness never goes false, so the balancer keeps sending while the process is closing. SIGTERM is wired first, then the rest, with enough seconds for the slowest in-flight request still allowed.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-observability">
    <AccordionTrigger>13. Explain the three pillars of observability. How do correlation IDs work across services and queue hops?</AccordionTrigger>
    <AccordionContent>

    The three pillars in interviews: **logs**, **metrics**, and **traces**. Logs are events that can be grepped. Metrics are cheap aggregates for SLOs and alerts. Traces are the request as a tree of spans across services. All three are required: metrics wake the on-call, traces show where, logs show why. Profiling is a useful fourth when CPU is the mystery, but it is not the interview lead.

    A **correlation id** is a string born at the edge — or taken from an inbound header — and copied everywhere that request goes. Every log line includes it. Every outbound HTTP call sends it. Every queue message puts it in **attributes**, not only in a JSON body someone might strip. **W3C `traceparent`** is the structured form: the same idea, with span parentage so a trace UI can draw the tree across hops.

    In production, generate if missing, never trust it for auth, and index it. A user’s “it failed at 14:02” jumps from the gateway span through the worker that handled the SQS hop.

    The common pitfall is HTTP-only ids: the consumer logs a new uuid and the trail dies at the queue. Also putting **user ids on metric labels** — cardinality explosion — or putting payloads with PII in trace attributes. Correlation is a header **propagated on purpose**, including through brokers, not a field the next service is hoped to invent.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-probes">
    <AccordionTrigger>14. Liveness vs readiness probes: what should each check, and what goes wrong if readiness checks your database?</AccordionTrigger>
    <AccordionContent>

    **Liveness** asks: should the platform **restart** this process? The check is that the event loop is alive — a cheap in-process heartbeat — not that Postgres is up. A deadlocked loop or a wedged runtime is a liveness failure. A database blip is not. Restarting every pod will not heal the database and will make the blip worse.

    **Readiness** asks: should the balancer **send traffic**? The check is that the process is listening, warmed, and not shutting down. A cheap DB ping is reasonable **only** if the pod cannot serve useful traffic without that database, with hysteresis so a blip does not empty the fleet. Optional dependencies — email, a search sidecar — stay out of readiness and **never** go in liveness. If every pod requires a shared DB that is down, marking the fleet unready is honest; looping restarts is not.

    The common pitfall is one `/health` used for both probes. Slow DB then looks like a dead process; kube kills healthy replicas during a blip — a **restart storm**. Liveness stays dumb and local, readiness about **this process’s ability to accept work it can actually do**, and dependency health on dashboards and SLOs.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-cron-once">
    <AccordionTrigger>15. You run a nightly cron job across 4 ECS tasks — how do you ensure it runs exactly once?</AccordionTrigger>
    <AccordionContent>

    Four ECS tasks and a nightly cron **inside the app** means four runs unless it is prevented. Four invoices, four charge sweeps, four “delete expired tokens” are the failure mode. Web fleets are for request fan-out. Schedules are not.

    **One successful execution** — schedulers are usually **at-least-once**, so “start one task” is not enough:

    - **best**: do not cron in the web fleet. EventBridge, a CloudWatch rule, or a Kubernetes `CronJob` starts a dedicated worker. Desired count of that worker is 1, and the **effect** is still idempotent.
    - a durable `job_runs` row with a unique key on `(job_name, scheduled_period)` so a second starter fails the insert and exits
    - if the job must live in the API image: **leader election** with a Redis lease that heartbeats, or a Postgres **advisory lock**, plus fencing so a stolen expired lease cannot commit

    In production the preference is the external scheduler. Locks are the fallback when deploy shape cannot change. Alerts fire when **zero** runs happened for the day, not only when one threw.

    The common pitfall is all four firing at midnight with no lock. The other is a lock **without TTL**: the leader dies, the lock stays, and the job never runs again. TTL sits past the expected duration, with a heartbeat if the job is long, and the unique run row still matters so a lock slip cannot double-charge. “Exactly once” is **one successful execution**, not one attempt that crashed after the side effect.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-secrets">
    <AccordionTrigger>16. How should secrets and config be managed and rotated in production? Why are plain env vars sometimes insufficient?</AccordionTrigger>
    <AccordionContent>

    Secrets are **credentials that rotate**; config is **behavior that deploys**. Secrets are not baked into images, git, or AMI snapshots. In production the choice is a manager — Secrets Manager, SSM, Vault — and **IAM roles** so the task does not start with a long-lived cloud key at all. RDS IAM auth or short-lived tokens beat a password in the environment rotated by editing a task definition by hand.

    Rotation: change the secret in the manager, then **recycle** tasks so they fetch the new value. For DB passwords, dual-value rotation — accept old and new for a window — then drop the old. Audit who read the secret. Non-secret config (`NODE_ENV`, log level, public URLs) can live in env or a config service; it still stays out of the image when it changes per environment.

    Plain **env vars** are insufficient for secrets because they leak: same-user `/proc` and crash dumps, debug “print env,” child-process inheritance, CI logs, ECS task-definition diffs copied into tickets. No versioning, no fine-grained access, no forced rotation. A casual `ps` listing does not print env; a compromised peer on the box can.

    The common pitfall is `DATABASE_URL` with a password in plaintext env, or rotating Secrets Manager while **never restarting** the process so it holds the old password until 3 a.m. Another: committing `.env` because local DX was convenient. Config in env, secrets in a manager, roles over keys, recycle on rotate.

    </AccordionContent>

  <AccordionItem value="be-testing">
    <AccordionTrigger>17. Describe your backend testing strategy: what belongs in unit vs integration vs e2e tests, and where do you draw mocking boundaries?</AccordionTrigger>
    <AccordionContent>

    Tests lock **behavior that would be dangerous to refactor**, not a coverage percentage.

    - **Unit**: pure domain — pricing rules, state machines, mapping, policy. No I/O. Fast enough to run on every save. Mock **time** and randomness, not the module’s own getters.
    - **Integration**: this process against a **real Postgres** (testcontainers) and maybe a real Redis. This is where SQL, transactions, migrations, and unique constraints fail. Mock **third-party HTTP** at the adapter boundary, not the repository.
    - **E2E**: a small set of journeys through HTTP as a client: signup, a money path, a permission denial. Slow, flaky if overused, invaluable if few.

    Mocking boundary: **process edges** — network, clock, vendor SDKs — not every internal function. The ORM is not mocked for the test that exists to catch a wrong column. Stripe is mocked. If a bug would only appear in SQL, the test must speak SQL.

    In production CI: unit always, integration on PR with a real DB, e2e on main or nightly. The pyramid is a budget: many cheap tests, few expensive ones.

    The common pitfall is a suite that is 90 percent mocked units and still cannot catch a missing `WHERE tenant_id`. The other is e2e for every branch, forty minutes, nobody runs it. Mocks are for things the service does not own. The database it does.

    </AccordionContent>

  <AccordionItem value="be-multi-tenancy">
    <AccordionTrigger>18. Compare shared-schema (tenant_id column), schema-per-tenant, and database-per-tenant multi-tenancy. What breaks operationally at 1,000 tenants?</AccordionTrigger>
    <AccordionContent>

    Three models, increasing isolation and ops cost:

    - **Shared schema, `tenant_id` column**: one DB, one migration train, every tenant-owned row tagged. Fastest to run. Isolation is a discipline plus **Postgres RLS** so a missed `WHERE` does not leak. This is the production model with Hono, Better Auth organizations, and Drizzle — [Building a Multi-Tenant Backend with Hono, Better Auth, Drizzle, and Postgres RLS](/notes/multi-tenant-backend-drizzle-hono-better-auth).
    - **Schema-per-tenant**: `tenant_abc.orders`. Stronger isolation, **N migrations**, `search_path` games, connection routing per request.
    - **Database-per-tenant**: stronger isolation and noisy-neighbor control; **N backups, N failovers, N connection setups**. Separate logical databases on one cluster still share compute and failure domains; strongest isolation is separate infrastructure when a tenant pays for it.

    At **1,000 tenants**, schema-per-tenant and database-per-tenant become an **operations product**: migration fan-out, pool explosion if pooling is per tenant, provisioning time, monitoring cardinality, “which tenant is on which host.” Shared schema still works if indexes lead with `tenant_id`, jobs always carry tenant context, and quotas exist so one tenant cannot eat the CPU.

    The common pitfall is shared schema **without** RLS and a background worker that forgets the tenant filter — that is a data leak, not a style issue. The other is opening a pool per tenant at 1,000 and discovering `max_connections` first. Shared schema is the default until compliance forces a step up, then isolate the few tenants who pay for a dedicated database.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-realtime-fanout">
    <AccordionTrigger>19. WebSockets vs SSE vs long polling — tradeoffs, and how do you broadcast events across multiple server instances?</AccordionTrigger>
    <AccordionContent>

    All three keep an HTTP conversation open. They differ in **direction and operational cost**.

    - **Long polling**: client asks, server waits, client asks again. Easy behind vanilla HTTP and load balancers. Wasteful; latency is one round trip per message; still used for stubborn clients and old proxies.
    - **SSE**: server-to-client stream over HTTP. Auto-reconnect, simple, good for notifications. **One-way**. Proxies sometimes buffer; disable buffering and send heartbeats.
    - **WebSockets**: bidirectional, lowest overhead once up. Heartbeats, backpressure, and **stateful connections** sit on the server. Harder to put behind naive Layer-7 timeouts.

    Broadcast across **multiple instances**: a connection lives on **one** process. Instance A cannot write to instance B’s sockets. Events publish to **Redis pub/sub** (or NATS, or a dedicated bus). Every instance subscribes and forwards to **its** local connections. Presence maps are local; the bus is global. Sticky sessions help reconnects; they are not a substitute for the bus.

    In production the preference is SSE if the client only listens; WebSockets if both sides speak. Cap per-instance connections and scale the fleet.

    The common pitfall is emitting only in-process: it works on one box, silent on the other three. Also no ping so the load balancer kills idle sockets, or storing fan-out in local memory with no bus. Scale-out without pub/sub is a demo.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="be-design-webhook-ingest">
    <AccordionTrigger>20. Design exercise: a webhook ingestion endpoint that must survive a 10x traffic spike without losing events or falling over.</AccordionTrigger>
    <AccordionContent>

    Thesis: **acknowledge fast, persist durable, process async**. The ingest endpoint is a shock absorber, not the business workflow. A 10x spike is a queue problem that should already exist, not a reason to make the POST smarter.

    Design:

    - `POST /webhooks/:source` verifies the **signature** first; unknown senders never touch storage
    - treat the provider’s **delivery id** as an idempotency key
    - in the request the **raw body** is written to something durable — SQS, Kinesis, or a `webhook_events` row — **then** return **2xx**
    - workers parse, validate, apply, and mark processed; retries are at-least-once so apply is **idempotent**
    - on a 10x spike, ingest scales horizontally and the **queue** absorbs; workers scale on queue depth, not inbound RPS. The HTTP tier stays cheap: auth, write, ack
    - backpressure workers, not the provider, when possible; if the provider retries on 5xx, a falling-over app becomes a **retry storm**

    Fail closed if the durable write itself is down: return 503 so the provider retries later, never 200 on an in-memory buffer.

    The common pitfall is returning 200 **before** persist — crash equals lost events. The other is doing CRM sync, emails, and domain workflows **in the request** so the spike takes down the API and the provider’s retries amplify it. Ingest is a write-ahead log. Everything else is a consumer.

    </AccordionContent>

    <AccordionTrigger>1. What triggers a re-render in React? Explain reconciliation and why key choice matters in lists.</AccordionTrigger>
    <AccordionContent>

      A re-render is React asking a component for a new **description**, not the DOM updating. An update is scheduled when `state`, `props`, or `context` change, when a parent renders and this child is not bailed out, or when something like `useSyncExternalStore` reports a new snapshot. Rendering can be abandoned in concurrent mode. **Committing** is the later step that mutates the host tree and runs Effects. Those two words stay separate in interviews.

      Reconciliation then matches the new elements to existing Fibers by **type**, **position**, and `key`:

      - Same type and a compatible `key`: reuse the Fiber and **preserve its state**.
      - Different type: tear the subtree down and mount a new one.
      - Different `key`: treat it as a new identity even when the type matches.
      - Index keys: safe only when identity really is position. A reorder attaches leftover local state to the wrong row.

      That is why `key` is identity, not a performance hint. In a list, a stable id among siblings is the identity. Sorting with index keys leaves the Fiber at position zero with its checkbox, and the checked row appears to jump. A `key` can also reset state on purpose — an editor keyed by document id remounts when the document changes, which is cleaner than an Effect that tries to wipe every field.

      Not every function invocation is "a re-render," including paint. Profile scheduled updates, render work, and commits separately. Model: [Understanding React in Depth](/notes/understanding-react-in-depth).

Include the input, use a functional updater, or move the work into an event handler rather than disable the lint rule.

      These do **not** belong in Effects:

      - **Derived values:** a filtered list from `query` plus `items`, or `fullName` from first and last. Compute during render.
      - **Resetting state when a prop changes:** key the subtree by document id instead of an Effect that clears fields.
      - **User actions:** form submit, "Buy," analytics on click. Those belong in the handler so they run once per intent.
      - **Copying props into state on every change:** a second source of truth that drifts.

      Effects that belong have a real external lifetime: a WebSocket keyed by `roomId`, `document.title`, a third-party widget on a ref. Fetching in `useEffect` as the default data path is the model left behind in App Router. A client Effect is still appropriate when the browser owns the credential or the socket. If it can be calculated from props and state already in hand, it is not an Effect. See [Understanding React in Depth](/notes/understanding-react-in-depth).

    <AccordionTrigger>3. When do useMemo and useCallback actually help, and when do they add cost for nothing?</AccordionTrigger>
    <AccordionContent>

      `useMemo` and `useCallback` are **performance tools, not semantic guarantees**. They skip work or keep a reference stable while dependencies stay equal. The calculation still has to be correct if React recomputes it, and the component still has to be correct if it renders again. Memoization cannot make an impure render safe.

      They actually help when:

      - The work is **measurably expensive** — a heavy filter, a large derived table model — and the inputs change less often than the parent renders.
      - A child wrapped in `memo` would otherwise see a new object or function identity every time and skip its bailout.
      - A hook dependency would churn: a callback passed into `useEffect` that should not re-subscribe every render.

      They add cost for nothing when every literal and every click handler is wrapped "just in case." Each hook still allocates, compares dependencies, and occupies a Hook slot. Cheap work is often cheaper than the bookkeeping. Nested `useMemo` that returns a new object because of a spread into it is an empty win. Memoization also cannot hide a render that mutates.

      The **React Compiler** can auto-memoize eligible components, which raises the bar for hand-written memo. It does not replace Server Components, cache policy, or a `key` mistake. The questions that still matter: was an update scheduled, which components rendered, and which host changes committed? Wrapping `useCallback` around a handler does not answer that. Redux still earns its keep for complex client workflows, undo, or a domain model that is not a remote resource.

  <AccordionItem value="fe-waterfalls">
    <AccordionTrigger>7. What are request waterfalls, and how do you parallelize or hoist data fetching to eliminate them?</AccordionTrigger>
    <AccordionContent>

      A **request waterfall** is latency that exists only because work waited to **start**. The network round trips are independent, but the code made them sequential. Users feel the sum, not the max.

      On the server the classic shape is sequential awaits in a Server Component: wait for the product, then start inventory, then start recommendations. Start independent promises first, then `await Promise.all`, or put sibling fetches in sibling components each under `Suspense` so they stream without a parent await gating the next constructor. If inventory truly needs the product row, that dependency is real. If it exists only because the parent awaited one child before creating the next, that waterfall is architectural.

      On the client the waterfall is worse: render, hydrate, `useEffect` fetch, then a child mounts and fetches again. Hoist to a Server Component, or start both queries in the parent so the child does not wait on "enabled when parent data exists" unless the id is actually unknown.

      How to eliminate them:

      - Kick off independent `fetch` or loader calls **before** the first await.
      - Deduplicate with request-scoped memoization; do not confuse that with a persistent cache.
      - Do not hop Server Component to this app's own Route Handler just to load page data — that adds a serial HTTP trip.
      - Prefetch on intent for the next navigation, but keep render free of mutations.

      Streaming does not fix a self-inflicted chain. Write-up: [Understanding Next.js in Depth](/notes/understanding-next-js-in-depth).

    </AccordionContent>

  <AccordionItem value="fe-optimistic">
    <AccordionTrigger>8. Implement an optimistic update: what happens on mutation failure, and how do you roll back cleanly?</AccordionTrigger>
    <AccordionContent>

      An optimistic update shows the **expected result immediately**, then reconciles with the server. It belongs only when the success shape is obvious and failure is easy to explain — marking a prescription as "in review," not deleting a legal record with no undo.

      The clean rollback is a **snapshot**, not "set loading false." Sequence with a cache like TanStack Query:

      - **`onMutate`:** cancel in-flight reads for that key, snapshot the current cache, write the optimistic value, return the snapshot in context.
      - **Mutation runs.** The UI already looks done. Disable double-submit on that row.
      - **`onError`:** restore the snapshot, show an error the pharmacist can retry, and do not leave a fake "success" chip on the row.
      - **`onSettled`:** invalidate so the server remains the authority even if another tab won.

      React 19 `useOptimistic` is the same idea tied to an Action: the optimistic value is **temporary**. When the Action finishes, React falls back to real state or props, so the source of truth still updates on success. If the Action throws, the optimistic layer drops and the previous UI returns. That is not "error handling done" — the failure still has to be surfaced.

      Failure modes: applying the optimistic patch twice, rolling back the wrong key, and ignoring a 409 when the server rejected a stale version. Mutations should be **idempotent** where possible, so a retry after rollback does not create a second order. Destructive actions get a confirm, not an optimistic disappear.

    </AccordionContent>

    <AccordionTrigger>9. Controlled vs uncontrolled form inputs: tradeoffs, and how do you keep a 50-field clinical form performant?</AccordionTrigger>
    <AccordionContent>

      **Controlled** means React state is the source of truth: `value` plus `onChange` on every keystroke. That yields instant validation, field-level disable, and a single submit snapshot. The cost is a re-render of whoever owns that state, which at fifty clinical fields is a real budget if one parent object updates on every character.

      **Uncontrolled** means the DOM holds the value until it is read through a ref or `FormData`. `defaultValue` paints the initial HTML. That yields cheaper typing and native browser features. The cost is that the React tree can disagree with what is on screen unless discipline is strict.

      For a 50-field clinical form, do **not** keep one giant controlled object at the page root. Prefer:

      - Default to **uncontrolled fields** with React Hook Form, which reads via refs and re-renders the field that changed.
      - Validate on blur and submit, not every keypress, except safety-critical fields like dose.
      - Isolate expensive widgets — allergy search, a signature pad — behind their own state.
      - Persist a versioned draft on the **authenticated server**. Browser `sessionStorage` is XSS-readable and is a poor place for PHI; if a local draft exists at all it is minimized, encrypted at rest by the OS if possible, expired, and wiped on logout.
      - Key the form by `encounterId` so switching patients remounts instead of leaking values.

      Accessibility stays first-class: labelled inputs, error text tied with `aria-describedby`, a submit error summary. Missing a keystroke of live validation is better than dropping frames while a pharmacist enters a dose.

    <AccordionTrigger>13. What does accessibility mean beyond ARIA? Cover semantic HTML, keyboard navigation, and focus management in modals.</AccordionTrigger>

The first pass is semantics, keyboard, and focus. A `div` with `role="button"` that is not in the tab order and has no Enter/Space handler is worse than a real `button`.

      - Headings in order, one `h1` for the page job, landmarks (`header`, `nav`, `main`).
      - `button` for actions, `a` for navigation, `label` tied to inputs, `table` for tabular data.
      - Visible name that matches the accessible name so voice control works.

      - Move focus into the dialog when it opens, preferably the title or the first field.
      - **Trap focus** inside; background gets `inert` so Tab cannot reach it.
      - Restore focus to the trigger on close.
      - Use `role="dialog"`, `aria-modal`, and labelled-by the title. The user must be able to close from the keyboard.

  <AccordionItem value="fe-tokens">
    <AccordionTrigger>14. Where should auth tokens live — localStorage vs httpOnly cookies? Connect your answer to XSS and CSRF risk.</AccordionTrigger>
    <AccordionContent>

      Session credentials belong in an **`HttpOnly` + `Secure` + `SameSite` cookie** set by the server, not in `localStorage`. Any script on the origin can read Web Storage. That includes XSS. Stealing a long-lived bearer token is enough to replay it from another machine. `HttpOnly` means `document.cookie` and the Cookie Store API cannot read the value. `Secure` keeps it on HTTPS. `SameSite=Lax` or `Strict` is the default for a first-party app. Authenticated **cross-site** POSTs need `SameSite=None; Secure` **plus** CSRF tokens and Origin checks — Lax and Strict will not send the cookie on those POSTs.

      The classic SPA pattern — JWT in `localStorage`, send `Authorization` by hand — often **skips CSRF** because the browser will not auto-attach that header on a cross-site form. The trade is that **XSS becomes a full session steal**. That is not a security win. Prefer taking CSRF seriously on a cookie session — SameSite, anti-CSRF on state-changing routes, origin checks — and keep the token out of JavaScript.

      `localStorage` is still right for a theme, a dismissed banner, a draft that is not a credential. `sessionStorage` is the same XSS story with a shorter lifetime; it is not a safer vault. Cookies that are not `HttpOnly` are readable by scripts and still go out on matching requests, which is the worst mix.

      Do not put PHI or refresh tokens in Web Storage "because it is easier for Axios." The server owns the session, rotates it, and expires it. Practical rules: [Local Storage, Session Storage, and Cookies](/notes/browser-storage-localstorage-sessionstorage-cookies).

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="fe-offline">
    <AccordionTrigger>15. How do service workers and the Cache API enable offline support? Explain stale-while-revalidate.</AccordionTrigger>
    <AccordionContent>

      A **service worker** sits between the page and the network. Once activated, it can intercept `fetch`, read and write the **Cache API**, and answer with a `Response` even when the radio is off. The Cache API is a request-to-response store keyed by URL. It is not `localStorage`. It lives off the main thread and can be versioned by cache name when a new worker ships.

      **Stale-while-revalidate** means: if a cached response exists, **return it immediately**, then fetch in the background, and if the fresh response differs, **update the cache**. The user sees last-known UI without waiting. A later visit, or a `postMessage` / query invalidation, shows the new bytes. Workbox names this strategy; it can be implemented with `caches.match` then `fetch`.

      Pair it with a policy, not one global cache:

      - App shell and hashed static assets: cache-first, versioned by build.
      - List endpoints that may be stale: stale-while-revalidate.
      - Mutations: network-first or network-only; queue POSTs only with a clear replay story.
      - Personalized PHI: do not cache across users; isolate by session.

      Offline is also UX: a banner, last-updated time, writes that do not look successful when they failed. Caching an old HTML shell forever is how a stuck app ships. Bump the cache name so tabs do not mix two versions.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="fe-boundaries">
    <AccordionTrigger>16. How do error boundaries and Suspense boundaries compose? What belongs in global error reporting?</AccordionTrigger>
    <AccordionContent>

      **Suspense** is a **pending** boundary: a child is not ready yet, so React shows the fallback. An **error boundary** is a **failed** boundary: a child threw during render, and `componentDidCatch` or Next.js `error.tsx` shows recovery UI. Wrap a Suspense island in an error boundary so a thrown fetch does not take down the dashboard, and keep a higher boundary around the route so a layout bug still has a way out.

      Order matters. If the error boundary is inside Suspense, a render throw is caught locally while siblings still stream. One root-only error boundary turns a bad widget into a full-page crash. App Router `error.tsx` and `loading.tsx` are the same two concepts, file-system shaped.

      Error boundaries do **not** catch event-handler errors, `setTimeout` failures, or a rejected promise that never re-enters render. Rethrow into the tree or handle those at the call site.

      Global reporting gets **unexpected** failures: render throws, unhandled rejections, server 500s, with request ids. Scrub PHI and tokens. Do **not** report every 404 or failed validation. Those are product states. A boundary that swallows and never reports is how a white screen arrives from a pharmacist, not from telemetry.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="fe-testing">
    <AccordionTrigger>17. What do you test at each level — unit (Vitest), component (Testing Library), e2e (Playwright) — and what do you deliberately not test?</AccordionTrigger>
    <AccordionContent>

      Test by **blast radius**, at the cheapest layer that still proves the behavior. Do not chase coverage on chrome.

      - **Unit, Vitest:** pure functions — query-key builders, dose parsers, reducers, URL helpers, the fetch state union. Fast, no DOM. If it is a formula, it is a unit test.
      - **Component, Testing Library:** user-observable contracts. Query by role and name, `userEvent`, assert the next thing the user can see. "Keeps draft when network fails" beats "sets `isError`." Mock the network at the boundary (MSW), not by poking internal store fields.
      - **E2E, Playwright:** journeys that need a real browser, real navigation, cookies, and a running app: login, tenant isolation, submit a prescription, pay. One path per critical risk, not a screenshot of every story.

      Deliberately do **not** test: implementation details (function names, CSS class lists, Redux action types), third-party library internals, every presentational tweak, or the same fact at all three layers. Do not snapshot a whole page to "lock the design." Do not unit-test that React's `useState` works.

      The published playbook on this site uses Cypress for the e2e slot; Playwright fills the same job here. Name tests after the regression they protect. If a real browser is required to trust the result, go e2e. Otherwise stay in Vitest. Details: [Frontend Regression Tests](/notes/frontend-regression-test).

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="fe-design-system">
    <AccordionTrigger>18. Design a component API for a shared design system: props vs compound components, theming via tokens, versioning across teams.</AccordionTrigger>
    <AccordionContent>

      A shared kit is **behavior plus tokens**, not a dump of screenshots. The API question is who owns composition.

      - **Variant props** (`variant`, `size`, `tone`) for small leaves: Button, Badge, Input. A finite union, defaults that match the product, no boolean soup like `isPrimary` plus `isLarge` plus `isDanger`.
      - **Compound components** for widgets with slots and focus: `Dialog.Root`, `Trigger`, `Content`, `Title`. Teams can order the header and inject a form without a new `renderFooter`. This is the Radix pattern already wrapped.
      - Avoid a mega-prop `config` object that cannot be typed or changelogged.

      Theming is **tokens**, not a `theme="pharmacyBlue"` prop on every leaf. Color, space, radius, and type live as CSS variables or a typed theme. Products map brand to tokens; components consume tokens. Dark mode is a token set, not a second component library. Do not expose raw hex in app code.

      Versioning across teams is where design systems die. Practice:

      - Semver: visual tweaks patch, new optional props minor, removed props and changed defaults **major**.
      - Ship a **codemod** and a deprecation window on a rename.
      - One package version in the monorepo; no silent "just copy Button into the app."
      - Storybook and MDX as the contract, plus a11y checks on the primitives.

      If fifteen apps fork the button, there was no system. Adoption and regression metrics matter more than component count. A small, boring API that versions cleanly beats a clever render-prop maze nobody can upgrade.

    </AccordionContent>

  <AccordionItem value="fe-fetch-state">
    <AccordionTrigger>19. Show how you'd use TypeScript generics and discriminated unions to model a fetch state machine (idle | loading | success | error) safely.</AccordionTrigger>
    <AccordionContent>

      Model fetch as a **discriminated union**, not as independent booleans. `isLoading` plus `isError` plus optional `data` lets TypeScript accept `data` on the error branch and `error` while idle. One `status` field is the tag; a generic `TData` is the success payload. Say this out loud as four mutually exclusive states, then show the type:

      ```ts
      type FetchState<TData> =
        | { status: "idle" }
        | { status: "loading" }
        | { status: "success"; data: TData }
        | { status: "error"; error: Error }

      function readData<TData>(state: FetchState<TData>): TData | undefined {
        if (state.status === "success") return state.data
        return undefined
      }
      ```

      Narrowing is the point. After `state.status === "success"`, `state.data` exists and `state.error` does not. After `"error"`, a prescription cannot be rendered from `undefined`. `idle` versus `loading` keeps "not asked yet" distinct from "the spinner should show," which matters for skip buttons and for SSR hydration.

      Do not add `data` as optional on every branch "for convenience." That convenience is the bug. For mutations, use a second union, or keep the last successful payload in a parent cache and let the mutation machine be pending or failed. An exhaustive `switch` with a `never` default makes a new status a compile error. TanStack Query already encodes this; if a store is hand-rolled, this is the type to reach for first.

    </AccordionContent>

  </AccordionItem>

On `visibilitychange`, reconnect when the tab is alive. Multiple instances need **pub/sub** behind the socket so a change on node A reaches the pharmacist on node B.

      Tenancy: every query key and channel includes `tenant_id`; the server checks the session. Error and Suspense boundaries wrap the live table. Do not put the session JWT in `localStorage` to "make the socket auth easier."

  <AccordionItem value="db-btree">
    <AccordionTrigger>1. How does a B-Tree index work internally, and why does it make equality and range lookups fast?</AccordionTrigger>
    <AccordionContent>
      A B-Tree is the thing to name first, because "it's logarithmic" is not an
      answer. In Postgres the default index is a **B-Tree**: a balanced tree of
      pages, usually 8KB. Internal pages hold separator keys and child pointers.
      Leaf pages hold the indexed values plus heap tuple pointers, and those leaves
      are linked in key order so a range can walk forward without climbing back to
      the root.

      That shape is why **equality** and **range** are both fast.

      - **Equality.** Descent from the root, one page per level, until the leaf
        that contains the key. Fanout is large, so height is usually three
        or four even on a big table — a handful of page reads, not a heap scan.
      - **Range.** Find the first matching leaf the same way, then follow
        sibling links. `BETWEEN`, ordered inequality, `ORDER BY` on the indexed
        column, and `LIMIT` can ride that walk.
      - **What it is not.** It is not a hash index. Hash helps equality only. It is
        also not free: inserts, key updates, and deletes maintain the tree.

      The production practice is to prove the access path with `EXPLAIN`. A
      B-Tree does not help if the column is wrapped in a function, if the type does
      not match, or if the predicate skips the leftmost columns of a composite key.
      How the planner chooses an index versus a sequential scan is in [Core SQL
      Concepts](/notes/core-sql-concepts).
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-composite-index">
    <AccordionTrigger>2. For a composite index on (tenant_id, status, created_at), which queries can use it? Explain leftmost-prefix matching.</AccordionTrigger>
    <AccordionContent>
      `(tenant_id, status, created_at)` is one sorted key, not three
      independent indexes. **Leftmost-prefix matching** means the planner can walk
      the tree only while the predicate is a prefix of that key, with equality on
      the earlier columns before a range on a later one.

      Queries that can use it:

      - **Equality on `tenant_id`.** `WHERE tenant_id = $1` is a prefix. The index
        is a per-tenant directory even if the query never mentions `status`.
      - **`tenant_id` plus `status`.** `WHERE tenant_id = $1 AND status = $2` is a
        tighter prefix.
      - **All three.** Equality on `tenant_id` and `status`, then a range or sort
        on `created_at` — `created_at >= $3`, `ORDER BY created_at`, keyset
        pagination. The range is valid **only** because the prior columns are
        equality.
      - **What is inefficient without a prefix.** Skipping `tenant_id` and filtering only `status` is not a contiguous slice. Postgres 18 **skip scan** can still probe a B-Tree when a leading column is omitted, but only when that column has **low cardinality** — it is not a substitute for putting `tenant_id` first. A range on `created_at` without equality on the columns before it is also not a tight slice.
      - **Keyset pagination.** Duplicate `created_at` values skip or repeat unless the cursor includes a unique tail — `(tenant_id, status, created_at, id)`.

      In a multi-tenant app that is why `organization_id` or `tenant_id` goes
      first: almost every hot query already equals that column. `EXPLAIN` still
      has to show the condition as an `Index Cond`, not a filter after a
      scan. The same leftmost-prefix idea shows up in [Core SQL
      Concepts](/notes/core-sql-concepts) on `(customer_id, created_at, id)`.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-seq-scan">
    <AccordionTrigger>3. Read this query plan: when is a sequential scan actually the right choice over an index scan?</AccordionTrigger>
    <AccordionContent>
      A plan that says `Seq Scan on orders` with a
      `Filter` is not a bug by default. The planner is
      cost-based. A sequential scan is the right choice when reading the heap in
      order is cheaper than bouncing through an index and then to random heap
      pages.

      **Row counts** matter, not the node name.

      - **Small table.** A few pages of heap plus an index is extra work.
      - **Low selectivity.** If the predicate matches most rows — `status = 'active'`
        at 90% — an index scan becomes a random read of nearly the whole table.
        Sequential I/O wins.
      - **The query already needs most of the table.** Aggregations without a
        selective `WHERE`, or a report that returns a large fraction of rows, often
        should seq-scan. A bitmap heap scan is the middle ground when the index
        finds many pages and Postgres wants to visit them in heap order.
      - **Stale stats.** `ANALYZE` lag can make a seq scan look "wrong" when the
        index would win, or the reverse. `EXPLAIN (ANALYZE, BUFFERS)` is checked
        against production-like counts, not a fixture of 50 rows.

      `SET enable_seqscan = off` is not a production fix. The
      predicate, the index shape, or the correlation of the column is what to fix. [Core SQL
      Concepts](/notes/core-sql-concepts) is explicit: guessing from local data is
      how a seq scan ships, but a seq scan on purpose is still a valid plan.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-ignored-index">
    <AccordionTrigger>4. Give four reasons Postgres ignores your index (function on column, type mismatch, low selectivity, leading-wildcard LIKE).</AccordionTrigger>
    <AccordionContent>
      The index can be present and the planner still seq-scans for four boring
      reasons, and those four come before anyone talks about "tuning
      random_page_cost."

      - **Function on the column.** `WHERE lower(email) = $1` cannot use a B-Tree
        on `email`. The stored keys are the raw values; an expression is applied at
        query time. The fix is an expression index on `lower(email)`, or store
        the canonical form and compare equality. Same trap with wrapping a
        timestamp in `date_trunc` or casting in the `WHERE`.
      - **Type mismatch.** Keep the parameter type aligned with the column. The
        usual miss is `id::text = $1` (function on the indexed side) versus
        `$1::uuid`. An unknown literal is often coerced; a real type mismatch
        on the column is what skips the index.
      - **Low selectivity.** An index on `status` where 95% of rows are `'active'`
        is a directory to almost the whole heap. The planner correctly prefers a
        sequential scan. Partial indexes — `WHERE status = 'open'` — are how to
        index the rare slice.
      - **Leading-wildcard `LIKE`.** `LIKE '%acme%'` cannot walk a B-Tree on the
        column. `LIKE 'acme%'` can, with a compatible collation or
        `text_pattern_ops`. For contains-search the tools are `pg_trgm` and a GIN
        index.

      `EXPLAIN` proves it. If the predicate is a `Filter` and not an
      `Index Cond`, the index is decoration.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-gin">
    <AccordionTrigger>5. When do you reach for a GIN index instead of B-Tree — e.g., JSONB containment or full-text search?</AccordionTrigger>
    <AccordionContent>
      **GIN** is the index when the lookup is "does this value contain this key,"
      not "walk this ordered column." A B-Tree stores sortable scalars. GIN is an
      inverted index: each token, array element, or JSONB key points at the rows
      that contain it. That is a different access path and a heavier write.

      Cases that use it:

      - **JSONB containment.** `WHERE metadata @> $1::jsonb` is the textbook GIN
        query. `jsonb_ops` is the default; `jsonb_path_ops` is
        smaller if only containment is needed. B-Treeing the whole JSONB
        document and hoping is not the path.
      - **Full-text search.** `to_tsvector(...) @@ to_tsquery(...)` wants a GIN
        (or GiST) on the `tsvector`. A B-Tree on the raw text does not tokenize.
      - **Arrays.** Overlap and membership — `tags && ARRAY['rx']` — are GIN
        territory.
      - **Trigram contains.** Leading-wildcard `LIKE` and fuzzy match with
        `pg_trgm` are GIN (or GiST), which is how the B-Tree `LIKE '%x%'`
        failure from the previous question is fixed.

      The trade-off to name: GIN updates are more expensive, they do not
      give `ORDER BY` on the document, and they bloat if JSONB churns. For a
      tenant-scoped JSONB column `tenant_id` still belongs in a B-Tree for the hot
      equality path, with GIN added only for the containment predicate. GIN does not
      replace `(tenant_id, created_at)`. Ordered pagination stays on a
      B-Tree.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-normalization">
    <AccordionTrigger>6. Explain 1NF–3NF briefly, then give a case where deliberate denormalization is the right call.</AccordionTrigger>
    <AccordionContent>
      The three forms are constraints on what a row is allowed to mean,
      and 3NF is the default for OLTP, not a religion.

      - **1NF.** Atomic cells, no repeating groups. Three NDCs do not belong in
        one text column split in the app. A line-item table is the
        repeating group done properly.
      - **2NF.** Non-key attributes depend on the **whole** composite key. If the
        key is `(order_id, sku)` and `customer_email` lives on the line, that
        email depends only on the order, not on the sku — it belongs on `orders`.
      - **3NF.** No transitive dependence. `department_id` determines
        `department_name`; the name is not copied onto every order unless there is
        a reason. (ZIP does **not** uniquely determine city — that example is
        folklore.)

      **Deliberate denormalization** is right when the read path is the incident.
      A pharmacy dashboard that shows fills-per-day per tenant should not join
      `prescription_fills` to `prescriptions` to `patients` on every page load. A
      `fill_stats_daily` row keyed by `(organization_id, day)` is kept and updated
      from the write path or a job. Same idea as storing `total_cents` on an
      order so every list view does not re-sum line items.

      The update anomaly is accepted and the write is owned: trigger, one transaction
      that updates both, or a rebuild job that can be rerun. Denormalize when
      `EXPLAIN` says the join is the product, and keep the normalized tables as
      the source of truth.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-isolation">
    <AccordionTrigger>7. Walk through the four isolation levels and the read phenomena (dirty, non-repeatable, phantom) each prevents. What does Postgres default to?</AccordionTrigger>
    <AccordionContent>
      The three **read phenomena** come first, then the levels, because the
      names are easy to mix up.

      - **Dirty read.** Another transaction's uncommitted write is visible. If it
        rolls back, the reader acted on data that never existed.
      - **Non-repeatable read.** A row is read, another transaction commits an
        update to that row, a second read shows the values changed.
      - **Phantom.** A predicate is re-run — `WHERE tenant_id = $1 AND status = 'open'`
        — and new rows appear that were not in the first result.

      Classic SQL:

      - **Read Uncommitted** allows all three.
      - **Read Committed** prevents dirty reads only.
      - **Repeatable Read** prevents dirty and non-repeatable; **phantoms still
        allowed** in the textbook definition.
      - **Serializable** prevents all three.

      **Postgres default is Read Committed.** Two Postgres-specific points:
      it will not actually dirty-read — `READ UNCOMMITTED` is treated
      as Read Committed because of MVCC. And **Postgres Repeatable Read is
      snapshot isolation**, so rows that committed after the
      snapshot are not visible. That blocks the textbook phantom-read case. It does **not** block
      write skew. **Serializable** uses SSI: it watches for a cycle and aborts one
      session with a serialization failure that must be retried.

      In production the usual stance is Read Committed for most request transactions, a
      single atomic `UPDATE` for inventory, and Serializable only for short
      transactions that would otherwise write-skew.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-long-tx">
    <AccordionTrigger>8. What makes long-running transactions dangerous in production (lock contention, vacuum bloat)?</AccordionTrigger>
    <AccordionContent>
      A long transaction is not "a slow query." It is **locks plus, at
      Repeatable Read or Serializable, a held snapshot** until `COMMIT`. At
      **Read Committed** the snapshot is statement-scoped; the danger is still
      an `idle in transaction` session holding locks or an assigned XID.
      That combination is how a reporting job takes down OLTP.

      Two production failures to name:

      - **Lock contention.** `UPDATE`, `SELECT ... FOR UPDATE`, and some
        `ALTER`s hold row or table locks for the life of the transaction. Other
        sessions queue. The queue looks like "the database is stuck" when the
        actual problem is one session that started a transaction, then waited on
        a downstream HTTP call, a user prompt, or a giant batch. `idle in transaction`
        is the smoking gun in `pg_stat_activity`.
      - **VACUUM bloat.** Autovacuum cannot reclaim dead tuples that are still
        visible to some transaction's snapshot. The oldest `xmin` horizon holds
        the garbage. Tables and indexes grow, cache hit ratio drops, and the
        same queries get slower even after the long transaction finally ends,
        because the bloat remains until vacuum can actually run. On a replica,
        `hot_standby_feedback` can create the same horizon from a long read-only
        query.

      The production practice: keep transactions tiny, never wait on the network inside one,
      batch updates in separate commits, set a statement timeout and an idle-in-
      transaction timeout, and watch `n_dead_tup` plus the age of the oldest
      transaction. A long `BEGIN` is a production incident with a delayed fuse,
      not a style choice.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-deadlocks">
    <AccordionTrigger>9. How do deadlocks occur between two transactions, and what coding practices prevent them?</AccordionTrigger>
    <AccordionContent>
      A deadlock is two sessions waiting on each other, and neither can make
      progress.

      Transaction A updates row 1, then waits for row 2. Transaction B already
      updated row 2, then waits for row 1. Each holds a lock the other needs.
      Postgres detects the cycle and aborts one transaction with `40P01`. The
      loser must retry. That is not a crash; it is the database picking a victim
      so the other can finish.

      It is not only two rows. A deadlock can involve a foreign-key check, a
      unique index insert, or a lock on a parent order while another session
      locks the child fill first. The shape is the same: **inconsistent lock
      order**.

      Practices that prevent them:

      - **Lock rows in a stable order.** Sort ids and update lowest-to-highest
        every time, in every code path, including triggers.
      - **Keep the transaction short.** Take locks, write, commit. Do not call
        Stripe or wait on a user inside `BEGIN`.
      - **Prefer one statement.** `UPDATE inventory SET qty = qty - 1 WHERE ...`
        grabs the row once. Read-compute-write with two statements widens the
        deadlock window.
      - **`FOR UPDATE SKIP LOCKED`** for work queues so workers do not wait on
        the same batch of rows.
      - **Retry on `40P01`** with backoff. Deadlock prevention reduces the rate;
        it does not make the error impossible.

      If two features touch overlapping rows, lock order is part of the
      API, the same way unique constraints are.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-n-plus-one">
    <AccordionTrigger>10. How do you detect and fix N+1 queries — joins, batching, DataLoader-style patterns?</AccordionTrigger>
    <AccordionContent>
      N+1 is one query for the parent list, then one query per row for children.
      Twenty prescriptions on a page become twenty-one round trips.

      **Detection.** The query log, `pg_stat_statements`, or an APM
      trace that shows a fan-out of identical `SELECT ... WHERE patient_id = $1`
      under one request. ORMs hide it: a loop of `prescription.patient` looks
      like a field access. If request latency grows linearly with page size,
      assume N+1 until traces **count** the queries. `EXPLAIN` then tells
      whether each of those queries is cheap — it cannot prove the request only
      ran one of them. DataLoader caches are **per request and per tenant**.

      **Fixes**, in this order:

      - **A join.** One statement: prescriptions plus patients in a single
        `FROM` / `JOIN`, or `SELECT` with a nested relation if the ORM can do it
        without exploding cardinality. For "has at least one" use `EXISTS`,
        not a join plus `DISTINCT` — that is the [Core SQL
        Concepts](/notes/core-sql-concepts) version of the same bug.
      - **Batching.** Load the page of prescriptions, collect patient ids, then
        `WHERE id = ANY($1)` or `inArray` once. Stitch in memory. That is the
        DataLoader pattern: coalesce keys in one tick, issue one `IN` query,
        memoize.
      - **Not a cache of the world.** Caching each child row still does N lookups
        on a cold path. Batch first.

      In GraphQL, DataLoader keeps resolvers from accidentally N+1. In Hono
      handlers the join or the `inArray` is written directly. Turning up the pool
      is not a fix for N+1.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-for-update">
    <AccordionTrigger>11. Compare SELECT ... FOR UPDATE with a version-column optimistic lock. Which fits a high-contention inventory decrement?</AccordionTrigger>
    <AccordionContent>
      Both are answers to lost updates. They fail in different traffic shapes.

      **`SELECT ... FOR UPDATE`** is pessimistic. The row is read, a lock is held
      until commit, then written. Another session that wants that row waits. It
      is the right tool when several rows must be read and computed — reserve
      two SKUs, or lock a prescription and its fills together. `SKIP LOCKED` is
      the variant for queues: do not wait, take the next free row.

      **A version column** is optimistic. Read `version`, write
      `WHERE id = $1 AND version = $2`, and bump the version. Zero rows updated
      means someone else won; retry. Under low contention that is fewer locks
      and nicer to replicas. Under high contention it becomes a retry storm:
      everyone fails, everyone rereads, CPU goes to retries instead of decrements.

      **High-contention inventory decrement** is not a good optimistic-lock
      problem. Read-then-`FOR UPDATE`-then-subtract in the
      app is also the weaker path if it can be avoided. One atomic statement is the fit:

      `UPDATE inventory SET qty = qty - 1 WHERE sku = $1 AND qty >= 1 RETURNING qty`

      A returned row means the decrement happened. No row means
      out of stock. No separate read, no version dance, no retry loop except for
      deadlocks. `FOR UPDATE` still wins when the business rule cannot be
      expressed as that `WHERE`. Optimistic versioning wins on documents that
      rarely collide. Inventory at flash-sale traffic is the pessimistic or
      atomic-update case.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-pooling">
    <AccordionTrigger>12. Why does connection pooling matter, and how do PgBouncer's transaction vs session modes differ?</AccordionTrigger>
    <AccordionContent>
      A Postgres connection is a **backend process**, not a cheap socket. Memory
      and process table grow with each one. An app fleet of 40 tasks times 20
      connections is 800 backends before a traffic spike. The database falls
      over on connection count while CPU is idle. **Pooling** multiplexes many
      client sessions onto fewer server connections.

      **PgBouncer session mode** pins a server connection to the client for the
      whole client session. Session features work: prepared statements, session
      `SET`, temp tables, session-level advisory locks, `LISTEN`. It caps
      connection storms but it does not reuse a backend between clients until
      disconnect. Useful for a few long-lived clients; not why most production
      setups run PgBouncer.

      **Transaction mode** returns the server connection at `COMMIT` or
      `ROLLBACK`. That is the mode that actually **reuses** backends under fan-out
      — it does not magically multiply throughput; excess demand queues. It also
      breaks anything that assumes session affinity:

      - **SQL `PREPARE`**, session `SET`, temp tables, and **session advisory
        locks** leak or vanish. Protocol-level named prepares can work in
        transaction mode if PgBouncer's `max_prepared_statements` is on (1.21+);
        that is not the same as session-scoped SQL `PREPARE`.
      - **`SET LOCAL`** and transaction-scoped `set_config(..., true)` are safe
        because they die at commit — that is why RLS tenant context belongs
        inside the transaction, not on the session.

      The production practice is transaction mode, tenant GUCs kept transaction-local,
      and no open transaction that then waits on the network while holding
      a borrowed backend.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-zero-downtime">
    <AccordionTrigger>13. Design a zero-downtime migration: adding a NOT NULL column with a default to a 100M-row table. Why CONCURRENTLY for indexes?</AccordionTrigger>
    <AccordionContent>
      Adding a default does not always rewrite the table. That is the
      pre-11 story.

      In modern Postgres, `ALTER TABLE ... ADD COLUMN ... DEFAULT` with a
      **non-volatile** constant is a **catalog change**. The default is stored
      in metadata and applied when old rows are read. New rows get it on insert.
      `now()` is **STABLE**, not VOLATILE, and can still use that fast-default
      path. `gen_random_uuid()` is volatile and rewrites, so it is not the
      fast-path default on 100M rows.

      **`NOT NULL` still needs a rollout.** A catalog default does not mean
      `NOT NULL` belongs in the same statement on a huge table as a walk-away change.
      For stored values, backfill in **batches**, each its own
      transaction, then `CHECK (col IS NOT NULL) NOT VALID`, `VALIDATE CONSTRAINT`,
      then `SET NOT NULL`. On Postgres 12+ a validated check can skip a second
      full verification.

      **`CREATE INDEX CONCURRENTLY`** is the index counterpart. A plain
      `CREATE INDEX` takes a lock that **blocks writes** for the whole build. On 100M rows that
      is an outage. `CONCURRENTLY` uses weaker locks and two scans. It cannot
      run inside a transaction, and it can fail leaving an invalid index that must
      be dropped.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-offset">
    <AccordionTrigger>14. Why does OFFSET 100000 get slow, and how does keyset (cursor) pagination fix it at the SQL level?</AccordionTrigger>
    <AccordionContent>
      `OFFSET 100000` is slow because Postgres still **finds and discards** those
      100000 rows. The `LIMIT` applies after. Page 500 is not a seek to a
      bookmark; it is "walk the ordered result until you have thrown away
      100000, then return the next 20." Cost grows with page number. Deep pages
      also go weird under concurrent inserts: rows shift, you skip or repeat.

      **Keyset pagination** seeks to the last row already returned. The sort
      key must be unique — `(created_at, id)` — or two rows with the same
      timestamp will skip or duplicate. SQL looks like:

      `WHERE (created_at, id) < ($cursor_created_at, $cursor_id) ORDER BY created_at DESC, id DESC LIMIT 20`

      That tuple comparison is the cursor. With an index on
      `(created_at DESC, id DESC)`, or a tenant-scoped
      `(tenant_id, created_at DESC, id DESC)`, this is an index range starting
      **after** the cursor, not a walk from the beginning of the table.

      `OFFSET` "just for page numbers" does not belong on a hot path. If the UI
      needs page 7 of 200, the options are keyset with a "load more" cursor or
      precomputed ranks in a table. [Core SQL Concepts](/notes/core-sql-concepts)
      uses the same `(created_at, id)` seek on `orders`. The planner should show
      an `Index Cond` on that tuple, not a `Seq Scan` plus a huge offset.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-replication">
    <AccordionTrigger>15. How does streaming replication work, and what bugs does read-replica lag cause for read-your-writes?</AccordionTrigger>
    <AccordionContent>
      Streaming replication is WAL shipping. The primary writes changes to the
      write-ahead log. A WAL sender streams those records to the replica. The
      replica replays them into its own data files. In the usual **asynchronous**
      setup, `COMMIT` on the primary returns before the replica has flushed or
      replayed that commit. Synchronous replication waits for a replica to
      **confirm** — `remote_write` or flush is not the same as **`remote_apply`**.
      Only replay acknowledgement means a following read on that replica can see
      the write. Sync commit buys durability; it does not automatically bound
      query-visible lag.

      The replica is a **replay machine**, not a second primary. It is great for
      read-mostly traffic and failover. It is a bad place to send a read that
      must see the write just committed.

      **Read-your-writes bugs** from lag:

      - An `INSERT` of a prescription on the primary, then the next `GET` redirected to a
        replica, returns 404. The user thinks save failed and retries.
        Duplicate submits follow.
      - Inventory is decremented on the primary, then stock is listed from the replica
        and the old quantity shows. The UI flickers backwards.
      - Uniqueness and existence checks against the replica are stale: "email
        is free" on a replica while the primary already committed it.

      The production practice: **session stickiness** to the primary for the request that
      mutated, or a "read your writes" rule — after a write in this session, go
      to the primary for a short window. The check-then-insert of a
      unique email does not belong on a replica. Lag is not a bug in Postgres; it is the
      contract of async replication, and the application has to honor it.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-partition-shard">
    <AccordionTrigger>16. Partitioning vs sharding: what problem does each solve, and when is a table "big enough" to partition?</AccordionTrigger>
    <AccordionContent>
      The words need separating because people say "shard" when they mean a
      partitioned table in one cluster.

      **Partitioning** is still one Postgres. A table is split into child
      partitions — range on `created_at`, list on a status, hash on
      `organization_id` — and the parent is what the app queries. The win is
      operational: autovacuum per partition, drop a month of fills with `DROP TABLE`
      instead of a 100M-row `DELETE`, **partition pruning** so a
      date-bounded query does not touch old partitions. Constraint exclusion is
      the older planner path; declarative partitioning uses pruning. The failure
      domain is still one primary, one WAL stream, one backup story.

      **Sharding** is multiple databases. Routing is by a key — tenant, or hash of
      patient id — to different primaries. That is how **writes and
      storage** scale past one machine. Cross-shard joins, unique constraints, and
      transactions become application problems. Sharding is not the move because a table
      is "a bit large." Sharding is the move when one primary cannot take the write load or
      the disk, and a key exists that almost never needs cross-shard work.

      **Big enough to partition** is not a row-count slogan. Partition when
      vacuum, bloat, or bulk delete is the incident, and a **stable
      partition key** exists that queries actually constrain — usually time. Tens of
      millions of narrow rows can be fine unpartitioned. A billion-row fill
      history that everyone queries by month is the partition case. A 2M-row
      patients table is not partitioned "for scale." Indexes
      and archival come first.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-oltp-olap">
    <AccordionTrigger>17. OLTP vs OLAP: why would you pipe Postgres data into Redshift rather than running analytics on the primary?</AccordionTrigger>
    <AccordionContent>
      **OLTP** is the primary's job: many small reads and writes, indexed point
      lookups, short transactions, normalized tables. **OLAP** is the opposite:
      scan a large slice, aggregate, group, maybe hash-join facts to dimensions.
      Row-store Postgres can do that work. That work still does not belong on the
      primary.

      Why the pipe into **Redshift** (or another warehouse) instead of
      `SELECT date_trunc, count(*)` on production:

      - **Buffer cache.** A sequential scan of fills evicts the hot OLTP pages.
        Checkout queries start hitting disk because a dashboard warmed the cache
        with last year's rows.
      - **CPU and I/O.** Hash aggregates and sorts compete with `UPDATE inventory`.
        Tail latency on the API is the bill.
      - **Snapshots.** A 20-minute report is a long-running transaction in
        spirit: it holds a snapshot, delays vacuum, and bloats the same tables
        checkout needs. That is the long-tx problem wearing a BI tool.
      - **Shape of the data.** Warehouses are columnar, compressed, and built
        for wide scans. Postgres is built for the row just written.

      A **read replica** is a middle ground for light operational reports. It
      still replays every primary write and still uses a row store. It fits
      "fills today for this tenant," not last-year SKU affinity. CDC or a
      nightly unload into Redshift isolates analytics hardware from the OLTP
      commit path. The primary stays boring on purpose.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-rls">
    <AccordionTrigger>18. Compare Postgres Row-Level Security with application-level tenant filtering. What are the failure modes of each?</AccordionTrigger>
    <AccordionContent>
      Application filtering is `WHERE organization_id = $1` on every query.
      **RLS** is the same rule attached to the table, enforced by Postgres for
      the role the app connects as. **Both** belong together. RLS is defense in depth; it
      is not a license to write ambient queries. That is the contract in
      [Building a Multi-Tenant Backend with Hono, Better Auth, Drizzle, and
      Postgres RLS](/notes/multi-tenant-backend-drizzle-hono-better-auth).

      **App-level failure modes.** Someone ships a new list endpoint and forgets
      the filter. An admin script or a JOIN uses the wrong alias. A background
      job has no session and loads by primary key across tenants. The bug is
      silent: another tenant's rows are returned.

      **RLS failure modes** — the ones that show up in an interview:

      - **Table owner bypass.** Owners skip RLS unless `FORCE ROW LEVEL SECURITY`.
        The migration role used as the runtime user is a leak.
      - **`SECURITY DEFINER`** functions run as the owner and can bypass
        policies unless written carefully.
      - **Missing tenant GUC.** Policies that use `current_setting('app.organization_id')`
        fail closed only if written that way — `current_setting(..., true)`
        returning NULL should match no rows. If the policy treats a missing
        setting as "allow," forgetting `set_config` is fail-open.
      - **`BYPASSRLS`**, superuser, and `TRUNCATE` (RLS does not apply). Unique
        and FK checks also bypass row filters, so unique indexes are still scoped
        by tenant.

      The `WHERE` is still written in Drizzle. Forgetting a filter must not become
      a cross-tenant incident; RLS is how that sentence stays true.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-soft-delete">
    <AccordionTrigger>19. Soft delete vs hard delete: implications for unique constraints, indexes (partial indexes), and data-retention compliance.</AccordionTrigger>
    <AccordionContent>
      **Soft delete** is `deleted_at timestamptz` (or a flag) and every read adds
      `WHERE deleted_at IS NULL`. **Hard delete** is `DELETE` and the row is
      gone.

      **Unique constraints.** A unique index on `email` still sees soft-deleted
      rows. A patient who leaves cannot re-register with the same email until a
      purge. The fix is a **partial unique index**: unique on
      `(organization_id, email) WHERE deleted_at IS NULL`. The live slice stays
      unique; historical rows can share the email. Forgetting the partial
      predicate is how "deleted" users lock a unique key forever.

      **Indexes.** A full B-Tree on a table full of tombstones wastes space and
      cache on rows the app never reads. **Partial indexes** cover the hot
      path — `WHERE deleted_at IS NULL` — and a separate index if the admin
      undelete UI actually queries the deleted slice.

      **Retention and compliance.** Soft delete is not erasure. GDPR-style
      deletion, pharmacy record retention, and legal hold are different clocks.
      If the requirement is "remove personal data," a `deleted_at` flag fails
      the requirement until a purge job hard-deletes or anonymizes, and backups
      still hold the old row. If the requirement is "keep the prescription for
      N years," nothing in that window is hard-deleted and the audit trail
      belongs on an append-only table. `deleted_at` is not
      a compliance strategy. It is a product undo. Retention is a purge
      policy plus backups.
    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="db-design-pharmacy">
    <AccordionTrigger>20. Design exercise: schema for a multi-tenant pharmacy system — prescriptions, an immutable audit trail, and fast per-tenant reporting.</AccordionTrigger>
    <AccordionContent>
      The isolation contract starts from [Building a Multi-Tenant Backend
      with Hono, Better Auth, Drizzle, and Postgres RLS](/notes/multi-tenant-backend-drizzle-hono-better-auth):
      shared schema, `organization_id` on every tenant-owned row, RLS plus
      explicit filters, runtime role not the table owner, `FORCE RLS`.

      **Core tables.** `organization` and membership stay global. Tenant-owned:
      `patients`, `prescribers`, `medications`, `prescriptions`,
      `prescription_fills`. Every one has `organization_id NOT NULL`, FKs, and
      tenant-scoped uniqueness — `(organization_id, mrn)` for patients,
      `(organization_id, rx_number)` for prescriptions. Hot indexes are
      leftmost-prefix: `(organization_id, status, created_at)` for work queues,
      `(organization_id, patient_id, created_at)` for charts.

      **Prescriptions** are a state machine (`draft`, `signed`, `voided`), not a
      mutable Word doc. A signed Rx is not silently overwritten; an amendment is
      a new row or an event. Fills are append-only facts: who dispensed what,
      `qty`, `filled_at`. Inventory decrement is the atomic
      `UPDATE ... WHERE qty >= 1`, not a version column.

      **Immutable audit.** `audit_events`: `organization_id`, `actor_id`,
      `action`, `entity_type`, `entity_id`, `payload` JSONB, `created_at`. Grant
      `INSERT` and `SELECT` only — no `UPDATE` or `DELETE` for `app_user`. That
      is append-only **for that role**, not physics: the table owner, a
      superuser, or DDL can still rewrite. For tamper-evidence add a separate
      writer role, hash chaining or WORM export, and no ORM update path. B-Tree
      on `(organization_id, created_at)`; GIN on `payload` only if searches go
      inside it.

      **Fast per-tenant reporting.** Fills are not aggregated on the primary for
      dashboards. `fill_stats_daily (organization_id, day, fill_count, ...)` is
      the denormalized read model, maintained in the same transaction as a fill
      or by a job that can be rebuilt. Heavy analytics go to a replica or a warehouse.
      Partition fills by month only when vacuum or drop-old-data is the
      incident, not because the table exists.
    </AccordionContent>

  <AccordionItem value="sec-sqli">
    <AccordionTrigger>1. Explain how SQL injection works and why parameterized queries fix it. Where can ORMs still leave you exposed?</AccordionTrigger>
    <AccordionContent>

      SQL injection is an interpreter mix-up, not a database feature. It
      happens when untrusted input is concatenated into a query string so the
      database parses part of that input as SQL. The attacker goal is to change
      what the statement means: extra rows, a widened predicate, or a write the
      handler never intended. Sample queries are not walked through. The failure
      is mixing data into syntax.

      Parameterized queries fix it because they send values out of band from the
      statement. The SQL text is a constant the application owns. The user string
      is bound as data. In this stack that is Drizzle's `eq` helpers, the same
      pattern as [Web Security and the OWASP Top
      10](/notes/web-security-owasp-top-10). A query builder is not magic. It is
      that separation, enforced.

      ORMs still leave you exposed:

      - **Raw fragments.** A tagged raw API may still **parameterize** values.
        The leak is interpolating a request field into the SQL **text**, not
        every `.execute()` that happens to say raw.
      - **Identifiers.** Parameters bind values, not table or column names.
        Dynamic sort fields are still injection if you interpolate them.
      - **Second-order data.** A value stored last week can be concatenated next
        week in a different statement.
      - **Missing tenant filters.** The ORM will happily return another
        organization's row if the clause never mentions `organizationId`. That is
        access control, not injection.

      Shape is still validated with Zod. A valid string is still data. It is never
      syntax. Postgres RLS is the backstop when a filter is missing — if tenant
      context is transaction-scoped and the app role cannot bypass RLS.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-xss">
    <AccordionTrigger>2. Compare stored, reflected, and DOM-based XSS. What does React escape by default, and when is dangerouslySetInnerHTML acceptable?</AccordionTrigger>
    <AccordionContent>

      XSS is injection into the HTML or JavaScript context of the origin.
      Once hostile script runs there, the browser treats it as the site: it can
      read the DOM, `localStorage`, and any cookie that is not `HttpOnly`. The
      attacker goal is to execute in the victim's origin, usually to steal a
      session or act as the user. **Stored** and **reflected** describe how the
      payload is delivered. **DOM-based** describes a browser-side source-to-sink
      path and can overlap either.

      - **Stored XSS** persists in a database or CMS field and is served to other
        users later. One write, many victims.
      - **Reflected XSS** comes back in the response to the request that carried
        it, typically a query string echoed into HTML.
      - **DOM-based XSS** never needs the server to echo markup. Client script
        reads the URL, storage, or postMessage data and writes it into an unsafe
        sink. The server log may look clean.

      React escapes **text children** and typical string attributes into text.
      It does not make every URL safe. A user-controlled `href`, `src`, or
      `router.push` target can still be a dangerous URL scheme. Hydration is not
      a sanitizer.

      `dangerouslySetInnerHTML` is acceptable only when the product truly must
      render markup — CMS HTML, a Markdown pipeline — and a maintained library
      has already sanitized it on the **server**. CSP still sits behind it. The
      name is the warning. That is the stance in [Frontend Security in Next.js
      and React Native](/notes/frontend-security-nextjs-react-native).

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-csrf">
    <AccordionTrigger>3. How does CSRF work, and how do SameSite cookies and CSRF tokens mitigate it? Does a JWT-in-localStorage SPA need CSRF protection?</AccordionTrigger>
    <AccordionContent>

      CSRF works because the browser automatically attaches cookies to requests
      that match the cookie's site. A page on another origin can trigger a
      state-changing request to the API, and the victim's session cookie goes
      along. The attacker goal is not to read the response. It is to make the
      already-authenticated browser **do something**: change email, create an
      invite, transfer. Same-origin policy blocks reading the result. It does
      not block sending the cookie.

      **SameSite** cuts a lot of that auto-attach behavior. `Lax` sends the
      cookie on top-level GET navigations and same-site requests, not on
      cross-site POSTs. `Strict` withholds it on all cross-site requests.
      `None` is for deliberate cross-site widgets and requires `Secure`.
      SameSite is still not the whole control. Older browsers and some
      WebView clients need more.

      **CSRF tokens** bind the request to a secret the attacking origin cannot
      read. The handler rejects mutations that lack the server-issued value.
      Origin checks are a useful extra signal on cookie-authenticated APIs.

      A JWT-in-`localStorage` SPA does **not** have classic cookie CSRF, because
      the browser will not attach that token by itself. The SPA must put it on
      an `Authorization` header. That is still not "no CSRF work."
      XSS can read `localStorage`. If a cookie-based refresh token is also
      present, CSRF returns. The production default is an `HttpOnly; Secure;
      SameSite` session cookie plus a mutation check, as in [Local Storage,
      Session Storage, and
      Cookies](/notes/browser-storage-localstorage-sessionstorage-cookies).

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-sessions-jwt">
    <AccordionTrigger>4. Sessions vs JWTs: how do you handle logout and revocation with stateless tokens? Explain refresh token rotation.</AccordionTrigger>
    <AccordionContent>

      The distinction starts from what each actually stores. A **server session**
      is an opaque id in a cookie plus a record that can be deleted. Logout is a
      row delete or a `revoked` flag. Every request checks that record, so
      revocation is immediate. A **stateless JWT access token** carries claims
      and a signature. The API can verify it without a lookup, which is the appeal
      and the problem: until it expires, there is no handle to kill it.

      Logout with stateless tokens cannot be "just delete a cookie on the
      client." Production picks one of these, and says so:

      - **Short access tokens**, minutes not hours, so stolen tokens die
        quickly.
      - **A denylist or version check** keyed by `jti` or a user token-version
        in Redis. That is a session store with extra steps.
      - **Revoke the refresh token** and accept that access tokens already
        issued live until expiry.

      **Refresh token rotation** is how a long login is kept without a
      long-lived access token. The refresh token is an **opaque value the client
      holds** — often an `HttpOnly` cookie — and a **hashed family** stored
      server-side. Each refresh issues a new refresh token and invalidates the
      previous one **atomically**. Legitimate concurrent refreshes need a grace
      window; a confirmed reuse of an already-rotated token is theft: the whole
      family is revoked, not just the one handle.

      In production the preference is Better Auth's opaque session cookie for
      the web app. Mobile gets a short access token in memory and a refresh
      token in the OS secret store.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-passwords">
    <AccordionTrigger>5. How should passwords be stored? Why bcrypt/argon2 over SHA-256, and what are salt and pepper?</AccordionTrigger>
    <AccordionContent>

      Passwords are never stored reversibly, and a naked SHA-256 of the
      password is never stored. The stored value is a **slow, salted, one-way
      hash** from a password hashing function, and a maintained library owns
      the parameters. Application code should not roll a homemade construction.

      **SHA-256** is a general-purpose digest. It is fast on purpose. GPUs can
      try enormous numbers of candidates per second, which is exactly what a
      stolen hash dump invites. The attacker goal after a database leak is
      offline guessing against reused and weak passwords. `bcrypt` and
      `argon2` exist to make that guessing expensive. They are deliberately
      slow, and Argon2id is memory-hard so the attack does not map cleanly onto
      cheap parallel hardware. The work factor is set so it hurts a bit at login
      and hurts a lot at brute force.

      - **Salt** is a per-password random value stored with the hash. Two users
        with the same password do not produce the same hash, and precomputed
        tables stop working. Modern password hashes generate and embed the salt
        for you. A global salt is not reused.
      - **Pepper** is an application-level secret, not stored in the same row,
        mixed in before hashing. If the table leaks but the pepper stays in
        KMS or an SST Secret, the dump is not immediately guessable. Pepper
        rotation is awkward, so it is treated as defense in depth, not the main
        control.

      Hashing is necessary. It is not sufficient if the login endpoint has no
      throttling.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-oauth-pkce">
    <AccordionTrigger>6. Walk through the OAuth 2.0 authorization code flow with PKCE. Why is the implicit flow deprecated?</AccordionTrigger>
    <AccordionContent>

      OAuth is delegated authorization, not "login with a popup."
      OpenID Connect layers identity on top. The **authorization code flow with
      PKCE** is what production ships for a public client — a SPA or a native
      app — where a client secret cannot be hidden.

      The sequence, conceptually:

      - The client generates a high-entropy **code verifier** and derives a
        **code challenge** from it, usually a SHA-256 digest encoded for the
        wire.
      - It sends the user to the authorization server with the challenge, the
        client id, redirect URI, and scopes. The verifier never goes on that
        first request.
      - The user authenticates at the authorization server. On mobile that
        should be the system browser, not a scriptable WebView.
      - The authorization server redirects back with a short-lived
        **authorization code**.
      - The client exchanges the code **and the verifier** at the token
        endpoint. The server recomputes the challenge. If they do not match,
        there is no token.

      PKCE's job is to stop an attacker who intercepted the code — a malicious
      app on the same custom-scheme redirect, a leaked query log — from
      exchanging it. They do not have the verifier.

      **Implicit flow** is deprecated because it delivered access tokens in the
      front channel with no client authentication and no one-time code. Tokens
      land in browser history and in any client that logs the full redirect URL.
      Fragments are **not** sent in `Referer` to other sites — that claim is a
      common mix-up. RFC 9700 (OAuth 2.0 Security BCP) discourages implicit;
      the **OAuth 2.1 draft** omits it and requires authorization code plus
      PKCE (S256) for public clients. A new product is not designed on
      implicit even if an IdP still offers it.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-idor">
    <AccordionTrigger>7. What is IDOR (broken object-level authorization), and why is it the classic multi-tenant vulnerability? How do you test for it?</AccordionTrigger>
    <AccordionContent>

      IDOR is **broken object-level authorization**: the route exists for this
      user, but the object belongs to someone else. The handler trusts an id
      from the URL, body, or header and loads that row globally. Authentication
      succeeded. Authorization never asked whether this identity may touch this
      row. The attacker goal is a confused deputy. They already have some
      legitimate access. They want another organization's project, invoice, or
      export.

      It is the classic multi-tenant bug because every SaaS API looks like
      `/organizations/:orgId/prescriptions/:id`. Sequential integers make
      guessing trivial. UUIDs make guessing harder and still are **not** access
      control. A leaked link or a log line is enough. The failure is the missing
      membership check, not the id format. [Building a Multi-Tenant Backend with
      Hono, Better Auth, Drizzle, and Postgres
      RLS](/notes/multi-tenant-backend-drizzle-hono-better-auth) is the path
      described: identity from the session, organization from verified
      membership, row loaded inside that tenant, RLS as the second gate.

      How to test: automated **negative authorization** coverage on every object
      action, using synthetic isolated tenants the team owns. A caller with a
      valid session must be denied — 404 or 403, never another tenant's payload,
      and preferably without confirming that the id exists. UUID opacity is not
      treated as the control. A random id that still returns another tenant's
      document is a failed test.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-rbac-abac">
    <AccordionTrigger>8. RBAC vs ABAC: model permissions for a pharmacy app where pharmacists, admins, and auditors share endpoints.</AccordionTrigger>
    <AccordionContent>

      Neither model is used alone. **RBAC** answers "what kind of
      user is this?" **ABAC** answers "in this context, on this record, is that
      enough?" A pharmacy app shares endpoints — the same `GET` and `POST` on a
      prescription — so the route list is a terrible permission model. The
      object and the purpose change the decision.

      Roles shipped as RBAC:

      - **Pharmacist** — review, dispense, counsel, and apply an e-signature
        inside their pharmacy.
      - **Admin** — roster, inventory, and configuration. Not a silent
        super-pharmacist unless that is explicitly granted.
      - **Auditor** — read-only access for compliance review. Cannot dispense,
        cannot sign, cannot alter the audit trail.

      Shared endpoints then check role **and** attributes:

      - **Tenant** — `organizationId` is this pharmacy, from membership, never
        from a client header.
      - **Assignment** — this pharmacist is on duty for this prescription's
        location.
      - **Minimum necessary** — an auditor sees what the review requires, not
        every clinical note by default.
      - **Purpose and time** — treatment versus operations versus break-glass,
        logged and time-boxed; a signature cannot be applied after the order
        was voided.

      RBAC alone fails when two pharmacists share a role and one should not see
      another store's queue. ABAC alone becomes an unreadable forest of flags.
      A small role set is kept, then tenant, resource, and purpose are encoded
      as attributes. The API still fail-closes if the policy engine times out.
      Hiding a button in React is not the control.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-cors">
    <AccordionTrigger>9. What does CORS actually protect (and not protect)? Explain preflight and common misconfigurations like reflecting Origin with credentials.</AccordionTrigger>
    <AccordionContent>

      CORS is a **browser reading rule** for the calling page. It tells the
      browser which other origins may read this response, and which extra
      headers and methods they may use. It is not a server access-control list.
      A mobile app, `curl`, or a server-side fetch will not obey it. If the API
      is reachable, every request is still authenticated and authorized. That is
      said first because interviewers fish for "CORS is security." It is not,
      not by itself.

      Simple requests — some `GET`s and `POST`s with a small header set — go
      straight to the server. The browser then decides whether JavaScript on
      the calling origin may read the body. **Preflight** is an `OPTIONS`
      request the browser sends first when the real request is non-simple: a
      custom header such as `Authorization`, a JSON content type, or a method
      like `PUT`. The server answers with which origin, methods, and headers it
      will allow, and whether credentials may be included.

      Common misconfigurations:

      - **Reflecting `Origin` with credentials.** Echoing whatever `Origin`
        arrived, plus `Access-Control-Allow-Credentials: true`, lets any website
        that can cause the victim's browser to call the API also **read** the
        authenticated response.
      - **Wildcard origin with credentials.** Browsers reject that combination.
        Teams then "fix" it by reflecting Origin, which is worse.
      - **Allowing the `null` origin** or an unbounded header list with
        credentials.

      The production default names the app origin explicitly. CORS does not stop
      CSRF on cookie mutations. It stops the attacker page from **reading** the
      result.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-csp">
    <AccordionTrigger>10. How does a Content Security Policy stop XSS? Nonce vs hash strategies, and how do you roll CSP out with report-only first?</AccordionTrigger>
    <AccordionContent>

      CSP is a **backup** for XSS, not a substitute for treating untrusted
      strings as data. It tells the browser which script, style, image, and
      frame sources this document may load. If a stored comment tries to run a
      script the policy did not allow, the browser blocks it. The attacker goal
      is still to execute in the origin. CSP raises the cost when an escaping
      hole exists. It does not make `dangerouslySetInnerHTML` safe.

      A useful policy starts locked down: `default-src 'self'`, `object-src
      'none'`, `base-uri 'self'`, `frame-ancestors 'none'`. The hard part is
      `script-src`, because `'unsafe-inline'` undoes the XSS protection. One of
      two ways allows the scripts the app actually ships:

      - **Nonce.** Each HTML response gets a fresh random nonce. Script elements
        that carry that nonce may run. An injected script does not have it. The
        nonce is regenerated per request and is not cached across users.
      - **Hash.** The digest of each inline script's exact bytes is listed. Any
        change to the script breaks the hash. This fits small, stable inline
        snippets and is painful if the bytes change every build.

      Nonces are preferred for a Next.js app with a changing bundle, and
      third-party tags stay on an explicit host allowlist.

      Rollout is **report-only first**.
      `Content-Security-Policy-Report-Only` ships with a report endpoint, what
      would have broken is watched, then the policy is tightened and switched
      to enforcing. Enforcing CSP is not turned on on a Friday only to discover
      the checkout script was inline.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-secret-leaks">
    <AccordionTrigger>11. How do secrets leak into client bundles and logs, and what processes/tooling prevent it?</AccordionTrigger>
    <AccordionContent>

      Secrets leak when a **client module graph** or a **log line** is treated as
      a private place. They are not. Anything that crosses `'use client'` in
      Next.js can appear in a browser chunk. Anything prefixed `NEXT_PUBLIC_`
      is inlined into those assets at build time. React Native is stricter: the
      Metro bundle on the device is extractable, so an HMAC or a Stripe secret
      in `app.json` is a public constant. The attacker goal is credentials that
      were never supposed to leave the build laptop.

      Logs are the second dump. A debug 500 that prints the connection string,
      a request logger that records `Authorization`, or source maps on a public
      path all turn observability into a second breach.

      What production actually runs:

      - **`server-only` imports** so a client import fails the build instead of
        shipping the database URL.
      - **Runtime secrets** from SST Secrets or the function environment, never
        `NEXT_PUBLIC_*`, never committed `.env` files.
      - **Secret scanning** in git and CI, plus pre-commit hooks so the leak
        never reaches main.
      - **Log redaction** as policy: no cookies, tokens, passwords, or full
        PAN. Structured events with ids, not bodies.
      - **Bundle review** on a release candidate: grep the client artifact for
        credential-shaped strings before it is public.

      Process matters more than a scanner. A PR checklist that asks "does this
      module run in the browser?" catches the Next.js graph mistake. Mobile
      public tokens get URL restrictions; they are still not secrets.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-login-defense">
    <AccordionTrigger>12. Design login defenses against brute force and credential stuffing: throttling, lockout, MFA, breached-password checks.</AccordionTrigger>
    <AccordionContent>

      Brute force is guessing. **Credential stuffing** is reused passwords from
      other breaches, tried at scale with valid-looking usernames. The attacker
      goal is to become the user without touching the hash. The login
      endpoint is designed as a rate-limited, multi-factor decision, not as
      "check the hash and issue a cookie."

      - **Throttling.** Attempts are limited per account **and** per IP or device
        cluster, with jittered backoff. Per-account only lets an attacker
        spread across many users. Per-IP only lets them rotate addresses on one
        target.
      - **Lockout** is a blunt tool. A long lock after five failures becomes an
        account-denial weapon against a known email. Temporary cooldown and a
        step-up after a threshold are preferred over a hard freeze. If lockout
        is used, the real user is notified out of band and a generic error is
        still returned to the caller.
      - **MFA** is the control that survives a stuffed password. A
        phishing-resistant factor is preferred where the product can bear it —
        passkeys or WebAuthn — and "remember this device forever" is not
        allowed to skip it. Recovery codes are secrets; they are hashed like
        passwords.
      - **Breached-password checks** at signup and at password change, using a
        k-anonymity prefix protocol against a known-breach corpus. Passwords
        that already appear in dumps are rejected. The attacker is not told
        which users exist.

      Same error for unknown user and wrong password. Session rotation on
      success. Logging of success, failure, and MFA challenge — without logging
      the password. Hashing is necessary. It does not stop stuffing.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-encryption">
    <AccordionTrigger>13. Encryption at rest vs in transit: where does TLS terminate in your architecture, and when is field-level encryption of PHI warranted?</AccordionTrigger>
    <AccordionContent>

      **In transit** is TLS on the path. **At rest** is encryption of bytes on
      disk, in backups, and in object storage. They answer different thefts. In
      transit stops a network observer. At rest stops a stolen volume or
      snapshot. Neither is authorization. A decrypted connection that returns
      the wrong tenant's row is still a breach.

      TLS belongs on every hop, including app to Postgres, Redis, and S3.
      Internal networks are not a cryptographic boundary. Each HTTPS-facing
      managed service **terminates TLS** and re-establishes it on the next
      supported hop. Lambda invocation is not an application-managed TLS
      socket. If someone says "we terminate TLS at the load balancer, so the
      VPC is plaintext," that is a threat to name: anyone on that network path,
      plus debug proxies.

      **Field-level encryption of PHI** is warranted when disk encryption is
      not enough for the people who can already read the database: operators,
      analytics extracts, or backups that leave the production IAM world, and
      clinical columns whose leak is the incident. Those columns are encrypted
      with a data key wrapped by KMS, envelope style, keys per tenant when
      possible. The cost is accepted: plaintext cannot be naively searched.
      Application code does not invent the cipher. Field-level crypto without
      key custody and rotation is theater. TLS plus disk encryption plus access
      control remains the default.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-ssrf">
    <AccordionTrigger>14. Explain SSRF and why the AWS metadata endpoint (169.254.169.254) is the classic target. How do you mitigate it?</AccordionTrigger>
    <AccordionContent>

      SSRF is **broken access control on the network side**. A handler fetches a
      URL the caller supplied — a webhook target, an image to proxy, a link to
      unfurl — and the **server** becomes the client. The attacker goal is a
      confused deputy: reach an address the caller's browser could not, using
      the server's network, DNS, and IAM role. Private RFC1918 hosts, internal
      admin ports, and cloud metadata are the usual destinations. The failure
      is described. A fetch recipe is not walked through.

      `169.254.169.254` is the classic target because it is the **instance
      metadata service** on AWS and other clouds: a link-local address only the
      instance can see, holding temporary credentials for the instance role.
      If the application can be made to request that host, the attacker goal is
      those credentials, then whatever the role can read or write. Naming the
      address is enough. The product mistake is "fetch this URL for me" with no
      allowlist.

      Mitigations actually shipped:

      - **Prefer not to fetch caller-supplied URLs at all.** Store a webhook id
        the product owns, not a free-form URL, when the product allows it.
      - **Allowlist schemes and hosts.** `https` only, named hosts, no IP
        literals if they can be avoided.
      - **Block link-local, loopback, metadata, and private ranges**, and
        re-check after DNS. The first lookup is not the last hop.
      - **Do not follow redirects** to a destination that has not been
        re-validated.
      - **IMDSv2** plus least-privilege instance roles, and egress policy so the
        function cannot speak to the metadata hop unless it must.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-file-upload">
    <AccordionTrigger>15. Secure a file-upload feature end to end: type validation, storage isolation, malware scanning, presigned URLs, safe content disposition.</AccordionTrigger>
    <AccordionContent>

      Upload is an untrusted blob entering the origin, the bucket, and
      later someone else's browser. The attacker goals are executing in the
      origin, storing malware for others, and reading another tenant's file by
      id. User files are not served from the app origin.

      End to end:

      - **Type validation** is an allowlist, not the client `Content-Type`.
        Size, extension, and sniffed magic bytes are checked, then images are
        re-encoded when the product only needs pixels. That strips leftover
        metadata that should not be parsed.
      - **Storage isolation.** Random object keys, never the user filename.
        Separate bucket or prefix per tenant, encryption at rest, no public
        listing. Authorization on download is the same IDOR test as any other
        row.
      - **Malware scanning** in quarantine before the object becomes
        downloadable. Async, fail closed if the scanner is down.
      - **Presigned URLs** for PUT and GET so the browser talks to object
        storage, not to the Lambda body limit. A presigned **PUT does not
        enforce size by itself**. A presigned **POST policy** with a
        content-length range, an upload proxy, or post-upload size checks is
        used while the object is still quarantined. Short TTL, method bound.
        They are issued only after authn/authz. A presigned URL is a
        capability. Logs must not leak it.
      - **Safe content disposition.** Downloads go as `attachment` with
        `X-Content-Type-Options: nosniff` and a boring content type. The
        browser is not allowed to sniff a file into script. Inline preview is a
        sanitized path on a **separate** origin, not the default.

      SVG and HTML uploads are script-in-disguise if they are ever served
      inline. If the product needs images only, those types are not accepted.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-supply-chain">
    <AccordionTrigger>16. How do you manage supply-chain risk in npm dependencies — lockfiles, audits, typosquatting, SBOMs?</AccordionTrigger>
    <AccordionContent>

      Supply-chain failure is running code that was not intended to run. The
      attacker goal is execution on a laptop with production secrets or in CI
      that publishes the app. A malicious maintainer, a compromised publisher, a
      poisoned Action, or a package whose name looks like the project's are all
      the same category in OWASP 2025.

      What production actually does:

      - **Lockfiles.** The lockfile is committed. CI installs with `npm ci` or
        `pnpm install --frozen-lockfile`. A pipeline that mutates the lockfile
        is not reproducing the tree the PR reviewed. Production images are
        built from that same lockfile, not from `latest` on the server.
      - **Audits.** `npm audit` is a signal, not a score. Triage is by whether
        the vulnerable path is reachable. Dependabot PRs get the same review as
        application code when they touch install scripts.
      - **Typosquatting.** Lookalike names, a new publisher on a package
        already in use, a dependency that was not added. Installs come from the
        lockfile. Brand-new packages that match a typo of a popular one are
        treated as suspicious. `ignore-scripts` is a reasonable default when
        compile-at-install is not needed.
      - **SBOMs.** A CycloneDX or SPDX bill is generated from the resolved
        lockfile at release, stored with the artifact, and used when a CVE
        lands so the question "are we on that graph?" can be answered.

      GitHub Actions are also pinned to a full commit SHA. Tags move. The
      artifact that runs in production should be the artifact the pull request
      described.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-headers">
    <AccordionTrigger>17. What do HSTS, frame-ancestors, and Referrer-Policy headers each defend against?</AccordionTrigger>
    <AccordionContent>

      These are **browser policy that cannot be enforced in application code
      after the response is gone**. They each close a different trust-boundary
      leak. None of them replaces authentication.

      - **HSTS** (`Strict-Transport-Security`) tells the browser that this host
        must be reached over HTTPS for a max-age window, including subdomains
        if the header says so, and optionally to preload. It defends against
        **SSL stripping**: a network attacker rewriting `http` links and
        collecting sessions. After the browser has seen HSTS, it will not send
        that plaintext request. The first visit is still unprotected unless the
        site is preloaded. It is shipped only on the real HTTPS origin, with a
        long max-age once that is sure.

      - **`frame-ancestors`** is the CSP directive that names who may embed
        this document in a frame. `'none'` is the default. The attacker goal is
        **clickjacking**: overlay the authenticated UI in a transparent frame
        and steal clicks — transfer, approve, sign. `X-Frame-Options` is the
        older, coarser header. `frame-ancestors` is the one set alongside
        `object-src 'none'`.

      - **`Referrer-Policy`** controls how much of the current URL is sent in
        the `Referer` header to other origins. URLs contain tokens, reset
        paths, and record ids. The attacker goal is **leakage through logs and
        outbound links**. `strict-origin-when-cross-origin` is a sane default:
        full URL same-origin, origin-only on HTTPS cross-origin, nothing when
        downgrading.

      Headers are cheap. They are also easy to forget on an error response or a
      CDN path. They belong on every response, including 4xx and 5xx.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-hipaa-audit">
    <AccordionTrigger>18. For HIPAA-style compliance, what must an audit log capture, and how do you make it tamper-evident?</AccordionTrigger>
    <AccordionContent>

      HIPAA does not hand out a universal field list. The following is treated
      as a **risk-based baseline** that can answer who touched which patient's
      PHI, when, from where, and whether it succeeded — including administrators
      — plus authn events, authorization changes, and config changes, with
      retention from policy and contract, not from a blog post.

      What is captured:

      - **Actor** — user id, role, acting organization, and whether this was
        break-glass or a support impersonation.
      - **Patient / record** — the PHI subject id, not the whole payload.
      - **Action** — view, create, update, export, print, e-sign, disclose.
      - **When** — a trusted server timestamp, request id, and session id.
      - **From where** — IP, user agent, and the route, enough to join app,
        gateway, and database logs.
      - **Outcome** — success, denial, not found. Denials matter as much as
        hits. **Purpose** when ABAC has one.

      Passwords, full tokens, cookie headers, and entire clinical notes are
      **not** logged. The log store must not become a second chart system.

      Tamper-evidence:

      - **Append-only** storage with a separate account the app role can write
        but not delete or overwrite.
      - **Hash chaining** or a signed batch so a hole or an edit is visible.
      - **WORM / object lock** on the archive.
      - **Alerts** on log deletion, policy change, or a burst of break-glass.

      A warehouse nobody pages is not a control. Integrity of the trail is part
      of the product, the same as RLS.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-cross-tenant">
    <AccordionTrigger>19. Name three subtle cross-tenant data leaks beyond SQL: shared caches, queue messages, search indexes. How do you isolate each?</AccordionTrigger>
    <AccordionContent>

      SQL `WHERE organization_id = ?` is the leak everyone rehearses. Production
      leaks the same way in **every other store that forgot the tenant**. The
      attacker goal is still another organization's PHI or files.

      - **Shared caches.** Redis or Next.js `cache` keyed only by user id or
        path will serve tenant A's JSON to tenant B. Isolation is the key:
        `organizationId` is part of every cache key, and authenticated
        responses are never cached as public. If it would be wrong to show user
        A's page to user B, it does not belong in a shared cache.

      - **Queue messages.** A worker that processes "generate invoice" without
        the tenant on the message **and** a membership check at consume time
        will write into whichever database connection it happens to hold.
        Isolation: every message carries `organizationId` from the verified
        request, the consumer opens the RLS transaction for that org, and
        tenant is not taken from the job payload alone if a client could
        enqueue it.

      - **Search indexes.** A shared OpenSearch or Pinecone corpus with only a
        metadata filter is one forgotten filter away from another tenant's
        documents. Isolation is a **server-side filter derived from trusted
        identity**, or a namespace the caller cannot name. A per-org index is
        one isolation tactic, not a required one. The wrapper must not accept
        another tenant from the client.

      The invariant: every store — cache, queue, index — scopes by identity the
      server already verified. RLS does not follow you into Redis.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="sec-threat-model">
    <AccordionTrigger>20. Threat-modeling exercise: an e-signature feature for prescriptions — identify the top five threats and a mitigation for each.</AccordionTrigger>
    <AccordionContent>

      The threat model is the **ceremony**, not the canvas widget. A
      prescription e-signature is a legally and clinically loaded write: it
      asserts that this pharmacist approved this exact order for this patient
      in this pharmacy. Attacker goals: sign as someone else, swap the
      document, or deny the act later.

      Five threats:

      - **Stolen or confused session.** A leftover pharmacist session signs an
        order the attacker queued. Mitigation: step-up authentication at sign
        time, a short-lived signing challenge, and role plus tenant checks. A
        button behind a logged-in cookie is not a signature.
      - **Document substitution.** Preview shows order A; the bytes that get
        signed are order B. Mitigation: bind a one-time signing challenge to an
        **immutable server-side document version and digest**, show the
        authoritative human-readable summary, and revalidate version, signer,
        tenant, and policy in the same transaction that commits. Showing users
        a hash is not enough if the client still supplies the bytes.
      - **Replay of a completed ceremony.** A captured signing token or a
        retried POST reapplies an old approval. Mitigation: one-time server
        nonce, short expiry, and an idempotency key so a double submit cannot
        become two legal acts.
      - **Cross-tenant retrieval of the signed artifact.** A guessed id on the
        PDF or audit endpoint. Mitigation: the same object-level control as
        IDOR — membership, row in tenant, RLS — and signed URLs that expire.
      - **Repudiation and a writable audit trail.** The signer later claims it
        was not them, or an admin edits the log. Mitigation: append-only,
        hash-chained events with actor, patient, payload digest, time, and
        outcome. The ceremony fail-closes if policy times out.

    </AccordionContent>
