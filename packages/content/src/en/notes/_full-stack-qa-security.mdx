## Security

<Accordion type="single" collapsible>
  <AccordionItem value="sec-sqli">
    <AccordionTrigger>1. Explain how SQL injection works and why parameterized queries fix it. Where can ORMs still leave you exposed?</AccordionTrigger>
    <AccordionContent>

      - SQL injection is an interpreter mix-up: untrusted input is concatenated into a query string so the database parses part of that input as SQL. The attacker goal is to change what the statement means. The failure is mixing data into syntax.
      - Parameterized queries send values out of band from the statement. The SQL text is a constant the application owns. In this stack that is Drizzle's `eq` helpers, the same pattern as [Web Security and the OWASP Top 10](/notes/web-security-owasp-top-10). A query builder is that separation, enforced.
      - ORMs still leave you exposed: interpolating a request field into the SQL **text** of a raw fragment; **identifiers** — parameters bind values, not table or column names; **second-order data** stored last week and concatenated next week; **missing tenant filters** — that is access control, not injection.
      - Shape is still validated with Zod. A valid string is still data. It is never syntax. Postgres RLS is the backstop when a filter is missing — if tenant context is transaction-scoped and the app role cannot bypass RLS.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-xss">
    <AccordionTrigger>2. Compare stored, reflected, and DOM-based XSS. What does React escape by default, and when is dangerouslySetInnerHTML acceptable?</AccordionTrigger>
    <AccordionContent>

      - XSS is injection into the HTML or JavaScript context of the origin. Once hostile script runs there, the browser treats it as the site: it can read the DOM, `localStorage`, and any cookie that is not `HttpOnly`. **Stored** and **reflected** describe how the payload is delivered. **DOM-based** describes a browser-side source-to-sink path and can overlap either.
      - **Stored XSS** persists in a database or CMS field and is served to other users later. **Reflected XSS** comes back in the response to the request that carried it. **DOM-based XSS** never needs the server to echo markup — client script reads the URL, storage, or postMessage data and writes it into an unsafe sink.
      - React escapes **text children** and typical string attributes into text. It does not make every URL safe. A user-controlled `href`, `src`, or `router.push` target can still be a dangerous URL scheme. Hydration is not a sanitizer.
      - `dangerouslySetInnerHTML` is acceptable only when the product truly must render markup — CMS HTML, a Markdown pipeline — and a maintained library has already sanitized it on the **server**. CSP still sits behind it. Stance: [Security in Next.js](/notes/security-in-next-js).

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-csrf">
    <AccordionTrigger>3. How does CSRF work, and how do SameSite cookies and CSRF tokens mitigate it? Does a JWT-in-localStorage SPA need CSRF protection?</AccordionTrigger>
    <AccordionContent>

      - CSRF works because the browser automatically attaches cookies to requests that match the cookie's site. A page on another origin can trigger a state-changing request to the API, and the victim's session cookie goes along. The attacker goal is to make the already-authenticated browser **do something**. Same-origin policy blocks reading the result. It does not block sending the cookie.
      - **SameSite** cuts a lot of that auto-attach behavior. `Lax` sends the cookie on top-level GET navigations and same-site requests, not on cross-site POSTs. `Strict` withholds it on all cross-site requests. `None` is for deliberate cross-site widgets and requires `Secure`. Older browsers and some WebView clients need more.
      - **CSRF tokens** bind the request to a secret the attacking origin cannot read. Origin checks are a useful extra signal on cookie-authenticated APIs.
      - A JWT-in-`localStorage` SPA does **not** have classic cookie CSRF, because the browser will not attach that token by itself. XSS can still read `localStorage`. If a cookie-based refresh token is also present, CSRF returns. The production default is an `HttpOnly; Secure; SameSite` session cookie plus a mutation check, as in [Local Storage, Session Storage, and Cookies](/notes/browser-storage-localstorage-sessionstorage-cookies).

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-sessions-jwt">
    <AccordionTrigger>4. Sessions vs JWTs: how do you handle logout and revocation with stateless tokens? Explain refresh token rotation.</AccordionTrigger>
    <AccordionContent>

      - A **server session** is an opaque id in a cookie plus a record that can be deleted. Logout is a row delete. Revocation is immediate. A **stateless JWT access token** carries claims and a signature. Until it expires, there is no handle to kill it.
      - Logout with stateless tokens cannot be "just delete a cookie on the client." Production picks: **short access tokens**; a **denylist or version check** keyed by `jti` or a user token-version in Redis; **revoke the refresh token** and accept that access tokens already issued live until expiry.
      - **Refresh token rotation:** the refresh token is an **opaque value the client holds** — often an `HttpOnly` cookie — and a **hashed family** stored server-side. Each refresh issues a new refresh token and invalidates the previous one **atomically**. Legitimate concurrent refreshes need a grace window; a confirmed reuse of an already-rotated token is theft: the whole family is revoked.
      - In production the preference is Better Auth's opaque session cookie for the web app. Mobile gets a short access token in memory and a refresh token in the OS secret store.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-passwords">
    <AccordionTrigger>5. How should passwords be stored? Why bcrypt/argon2 over SHA-256, and what are salt and pepper?</AccordionTrigger>
    <AccordionContent>

      - Passwords are never stored reversibly, and a naked SHA-256 of the password is never stored. The stored value is a **slow, salted, one-way hash** from a password hashing function. Application code should not roll a homemade construction.
      - **SHA-256** is a general-purpose digest. It is fast on purpose. GPUs can try enormous numbers of candidates per second. `bcrypt` and `argon2` exist to make that guessing expensive. They are deliberately slow, and Argon2id is memory-hard so the attack does not map cleanly onto cheap parallel hardware.
      - **Salt** is a per-password random value stored with the hash. Two users with the same password do not produce the same hash, and precomputed tables stop working. A global salt is not reused. **Pepper** is an application-level secret, not stored in the same row, mixed in before hashing. If the table leaks but the pepper stays in KMS, the dump is not immediately guessable. Pepper rotation is awkward, so it is defense in depth, not the main control.
      - Hashing is necessary. It is not sufficient if the login endpoint has no throttling.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-oauth-pkce">
    <AccordionTrigger>6. Walk through the OAuth 2.0 authorization code flow with PKCE. Why is the implicit flow deprecated?</AccordionTrigger>
    <AccordionContent>

      - OAuth is delegated authorization, not "login with a popup." The **authorization code flow with PKCE** is what production ships for a public client — a SPA or a native app — where a client secret cannot be hidden. The longer reading is [OAuth 2.0 and OIDC Explained](/notes/oauth-2-and-oidc-explained).
      - The client generates a high-entropy **code verifier** and derives a **code challenge** (usually SHA-256). It sends the user to the authorization server with the challenge; the verifier never goes on that first request. The user authenticates (system browser on mobile, not a scriptable WebView). The server redirects back with a short-lived **authorization code**. The client exchanges the code **and the verifier** at the token endpoint.
      - PKCE's job is to stop an attacker who intercepted the code from exchanging it. They do not have the verifier.
      - **Implicit flow** is deprecated because it delivered access tokens in the front channel with no client authentication and no one-time code. Tokens land in browser history and in any client that logs the full redirect URL. Fragments are **not** sent in `Referer` to other sites — that claim is a common mix-up. RFC 9700 discourages implicit; the **OAuth 2.1 draft** omits it and requires authorization code plus PKCE (S256) for public clients.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-idor">
    <AccordionTrigger>7. What is IDOR (broken object-level authorization), and why is it the classic multi-tenant vulnerability? How do you test for it?</AccordionTrigger>
    <AccordionContent>

      - IDOR is **broken object-level authorization**: the route exists for this user, but the object belongs to someone else. The handler trusts an id from the URL, body, or header and loads that row globally. Authentication succeeded. Authorization never asked whether this identity may touch this row.
      - It is the classic multi-tenant bug because every SaaS API looks like `/organizations/:orgId/prescriptions/:id`. Sequential integers make guessing trivial. UUIDs make guessing harder and still are **not** access control. The failure is the missing membership check, not the id format. Path: [Building a Multi-Tenant Backend with Hono, Better Auth, Drizzle, and Postgres RLS](/notes/multi-tenant-backend-drizzle-hono-better-auth).
      - How to test: automated **negative authorization** coverage on every object action, using synthetic isolated tenants the team owns. A caller with a valid session must be denied — 404 or 403, never another tenant's payload, and preferably without confirming that the id exists. A random id that still returns another tenant's document is a failed test.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-rbac-abac">
    <AccordionTrigger>8. RBAC vs ABAC: model permissions for a pharmacy app where pharmacists, admins, and auditors share endpoints.</AccordionTrigger>
    <AccordionContent>

      - **RBAC** answers "what kind of user is this?" **ABAC** answers "in this context, on this record, is that enough?" A pharmacy app shares endpoints — the same `GET` and `POST` on a prescription — so the route list is a terrible permission model.
      - Roles: **Pharmacist** — review, dispense, counsel, e-signature inside their pharmacy. **Admin** — roster, inventory, configuration. Not a silent super-pharmacist unless that is explicitly granted. **Auditor** — read-only for compliance review. Cannot dispense, cannot sign, cannot alter the audit trail.
      - Shared endpoints then check role **and** attributes: **tenant** from membership, never from a client header; **assignment** — this pharmacist is on duty for this prescription's location; **minimum necessary**; **purpose and time** — treatment versus operations versus break-glass, logged and time-boxed.
      - RBAC alone fails when two pharmacists share a role and one should not see another store's queue. ABAC alone becomes an unreadable forest of flags. A small role set, then tenant, resource, and purpose as attributes. The API still fail-closes if the policy engine times out. Hiding a button in React is not the control.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-cors">
    <AccordionTrigger>9. What does CORS actually protect (and not protect)? Explain preflight and common misconfigurations like reflecting Origin with credentials.</AccordionTrigger>
    <AccordionContent>

      - CORS is a **browser reading rule** for the calling page. It tells the browser which other origins may read this response. It is not a server access-control list. A mobile app, `curl`, or a server-side fetch will not obey it. Interviewers fish for "CORS is security." It is not, not by itself.
      - Simple requests go straight to the server. The browser then decides whether JavaScript on the calling origin may read the body. **Preflight** is an `OPTIONS` request the browser sends first when the real request is non-simple: a custom header such as `Authorization`, a JSON content type, or a method like `PUT`.
      - **Reflecting `Origin` with credentials** lets any website that can cause the victim's browser to call the API also **read** the authenticated response. **Wildcard origin with credentials** is rejected by browsers; teams then "fix" it by reflecting Origin, which is worse. Allowing the `null` origin or an unbounded header list with credentials is the same class.
      - The production default names the app origin explicitly. CORS does not stop CSRF on cookie mutations. It stops the attacker page from **reading** the result.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-csp">
    <AccordionTrigger>10. How does a Content Security Policy stop XSS? Nonce vs hash strategies, and how do you roll CSP out with report-only first?</AccordionTrigger>
    <AccordionContent>

      - CSP is a **backup** for XSS, not a substitute for treating untrusted strings as data. It tells the browser which script, style, image, and frame sources this document may load. It does not make `dangerouslySetInnerHTML` safe.
      - A useful policy starts locked down: `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'`. `'unsafe-inline'` undoes the XSS protection. **Nonce:** each HTML response gets a fresh random nonce; an injected script does not have it. **Hash:** the digest of each inline script's exact bytes is listed. Nonces are preferred for a Next.js app with a changing bundle; third-party tags stay on an explicit host allowlist.
      - Rollout is **report-only first**. `Content-Security-Policy-Report-Only` ships with a report endpoint, what would have broken is watched, then the policy is tightened and switched to enforcing.
      - Enforcing CSP is not turned on on a Friday only to discover the checkout script was inline.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-secret-leaks">
    <AccordionTrigger>11. How do secrets leak into client bundles and logs, and what processes/tooling prevent it?</AccordionTrigger>
    <AccordionContent>

      - Secrets leak when a **client module graph** or a **log line** is treated as a private place. Anything that crosses `'use client'` in Next.js can appear in a browser chunk. Anything prefixed `NEXT_PUBLIC_` is inlined into those assets at build time. React Native is stricter: the Metro bundle on the device is extractable, so an HMAC or a Stripe secret in `app.json` is a public constant.
      - Logs are the second dump. A debug 500 that prints the connection string, a request logger that records `Authorization`, or source maps on a public path all turn observability into a second breach.
      - What production actually runs: **`server-only` imports** so a client import fails the build; **runtime secrets** from SST Secrets or the function environment, never `NEXT_PUBLIC_*`; **secret scanning** in git and CI; **log redaction** as policy; **bundle review** on a release candidate.
      - Process matters more than a scanner. A PR checklist that asks "does this module run in the browser?" catches the Next.js graph mistake. Mobile public tokens get URL restrictions; they are still not secrets.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-login-defense">
    <AccordionTrigger>12. Design login defenses against brute force and credential stuffing: throttling, lockout, MFA, breached-password checks.</AccordionTrigger>
    <AccordionContent>

      - Brute force is guessing. **Credential stuffing** is reused passwords from other breaches, tried at scale with valid-looking usernames. The login endpoint is a rate-limited, multi-factor decision, not "check the hash and issue a cookie."
      - **Throttling:** attempts limited per account **and** per IP or device cluster, with jittered backoff. Per-account only lets an attacker spread across many users. Per-IP only lets them rotate addresses on one target. **Lockout** is blunt — a long lock after five failures becomes an account-denial weapon. Temporary cooldown and a step-up after a threshold are preferred.
      - **MFA** is the control that survives a stuffed password. Prefer passkeys or WebAuthn. Recovery codes are secrets; they are hashed like passwords. **Breached-password checks** at signup and at password change, using a k-anonymity prefix protocol. Passwords that already appear in dumps are rejected.
      - Same error for unknown user and wrong password. Session rotation on success. Logging of success, failure, and MFA challenge — without logging the password. Hashing is necessary. It does not stop stuffing.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-encryption">
    <AccordionTrigger>13. Encryption at rest vs in transit: where does TLS terminate in your architecture, and when is field-level encryption of PHI warranted?</AccordionTrigger>
    <AccordionContent>

      - **In transit** is TLS on the path. **At rest** is encryption of bytes on disk, in backups, and in object storage. In transit stops a network observer. At rest stops a stolen volume or snapshot. Neither is authorization. A decrypted connection that returns the wrong tenant's row is still a breach.
      - TLS belongs on every hop, including app to Postgres, Redis, and S3. Internal networks are not a cryptographic boundary. Each HTTPS-facing managed service **terminates TLS** and re-establishes it on the next supported hop. If someone says "we terminate TLS at the load balancer, so the VPC is plaintext," that is a threat to name.
      - **Field-level encryption of PHI** is warranted when disk encryption is not enough for the people who can already read the database: operators, analytics extracts, or backups that leave the production IAM world, and clinical columns whose leak is the incident. Envelope encryption with a data key wrapped by KMS, keys per tenant when possible. Plaintext cannot be naively searched.
      - Field-level crypto without key custody and rotation is theater. TLS plus disk encryption plus access control remains the default.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-ssrf">
    <AccordionTrigger>14. Explain SSRF and why the AWS metadata endpoint (169.254.169.254) is the classic target. How do you mitigate it?</AccordionTrigger>
    <AccordionContent>

      - SSRF is **broken access control on the network side**. A handler fetches a URL the caller supplied and the **server** becomes the client. The attacker goal is a confused deputy: reach an address the caller's browser could not, using the server's network, DNS, and IAM role. Private RFC1918 hosts, internal admin ports, and cloud metadata are the usual destinations.
      - `169.254.169.254` is the classic target because it is the **instance metadata service**: a link-local address only the instance can see, holding temporary credentials for the instance role. Naming the address is enough. The product mistake is "fetch this URL for me" with no allowlist.
      - Mitigations: **prefer not to fetch caller-supplied URLs at all**; **allowlist schemes and hosts** (`https` only, named hosts, no IP literals if they can be avoided); **block link-local, loopback, metadata, and private ranges**, and re-check after DNS; **do not follow redirects** to a destination that has not been re-validated; **IMDSv2** plus least-privilege instance roles, and egress policy so the function cannot speak to the metadata hop unless it must.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-file-upload">
    <AccordionTrigger>15. Secure a file-upload feature end to end: type validation, storage isolation, malware scanning, presigned URLs, safe content disposition.</AccordionTrigger>
    <AccordionContent>

      - Upload is an untrusted blob entering the origin, the bucket, and later someone else's browser. The attacker goals are executing in the origin, storing malware for others, and reading another tenant's file by id. User files are not served from the app origin.
      - **Type validation** is an allowlist, not the client `Content-Type`. Size, extension, and sniffed magic bytes, then re-encode images when the product only needs pixels. **Storage isolation:** random object keys, never the user filename. Separate bucket or prefix per tenant. Authorization on download is the same IDOR test as any other row. **Malware scanning** in quarantine before the object becomes downloadable. Async, fail closed if the scanner is down.
      - **Presigned URLs** for PUT and GET so the browser talks to object storage. A presigned **PUT does not enforce size by itself**. A presigned **POST policy** with a content-length range, an upload proxy, or post-upload size checks is used while the object is still quarantined. Short TTL, method bound, issued only after authn/authz.
      - **Safe content disposition:** downloads go as `attachment` with `X-Content-Type-Options: nosniff` and a boring content type. Inline preview is a sanitized path on a **separate** origin. SVG and HTML uploads are script-in-disguise if they are ever served inline. If the product needs images only, those types are not accepted.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-supply-chain">
    <AccordionTrigger>16. How do you manage supply-chain risk in npm dependencies — lockfiles, audits, typosquatting, SBOMs?</AccordionTrigger>
    <AccordionContent>

      - Supply-chain failure is running code that was not intended to run. The attacker goal is execution on a laptop with production secrets or in CI that publishes the app. A malicious maintainer, a compromised publisher, a poisoned Action, or a package whose name looks like the project's are all the same category in OWASP 2025.
      - **Lockfiles.** Commit the lockfile. CI installs with `npm ci` or `pnpm install --frozen-lockfile`. Production images are built from that same lockfile, not from `latest`. **Audits.** `npm audit` is a signal, not a score. Triage by whether the vulnerable path is reachable.
      - **Typosquatting.** Lookalike names, a new publisher on a package already in use. Installs come from the lockfile. `ignore-scripts` is a reasonable default when compile-at-install is not needed. **SBOMs.** A CycloneDX or SPDX bill is generated from the resolved lockfile at release, stored with the artifact, and used when a CVE lands.
      - GitHub Actions are also pinned to a full commit SHA. Tags move. The artifact that runs in production should be the artifact the pull request described.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-headers">
    <AccordionTrigger>17. What do HSTS, frame-ancestors, and Referrer-Policy headers each defend against?</AccordionTrigger>
    <AccordionContent>

      - These are **browser policy that cannot be enforced in application code after the response is gone**. None of them replaces authentication.
      - **HSTS** (`Strict-Transport-Security`) tells the browser that this host must be reached over HTTPS for a max-age window. It defends against **SSL stripping**. After the browser has seen HSTS, it will not send that plaintext request. The first visit is still unprotected unless the site is preloaded. Ship it only on the real HTTPS origin, with a long max-age once that is sure.
      - **`frame-ancestors`** names who may embed this document in a frame. `'none'` is the default. The attacker goal is **clickjacking**. `X-Frame-Options` is the older, coarser header. **`Referrer-Policy`** controls how much of the current URL is sent in the `Referer` header. URLs contain tokens, reset paths, and record ids. `strict-origin-when-cross-origin` is a sane default: full URL same-origin, origin-only on HTTPS cross-origin, nothing when downgrading.
      - Headers are cheap. They are also easy to forget on an error response or a CDN path. They belong on every response, including 4xx and 5xx.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-hipaa-audit">
    <AccordionTrigger>18. For HIPAA-style compliance, what must an audit log capture, and how do you make it tamper-evident?</AccordionTrigger>
    <AccordionContent>

      - HIPAA does not hand out a universal field list. Treat this as a **risk-based baseline** that can answer who touched which patient's PHI, when, from where, and whether it succeeded — including administrators — plus authn events, authorization changes, and config changes, with retention from policy and contract.
      - Capture: **actor** (user id, role, acting organization, break-glass or impersonation); **patient / record** (the PHI subject id, not the whole payload); **action**; **when** (trusted server timestamp, request id, session id); **from where** (IP, user agent, route); **outcome** (success, denial, not found). Passwords, full tokens, cookie headers, and entire clinical notes are **not** logged.
      - Tamper-evidence: **append-only** storage with a separate account the app role can write but not delete or overwrite; **hash chaining** or a signed batch so a hole or an edit is visible; **WORM / object lock** on the archive; **alerts** on log deletion, policy change, or a burst of break-glass.
      - A warehouse nobody pages is not a control. Integrity of the trail is part of the product, the same as RLS.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-cross-tenant">
    <AccordionTrigger>19. Name three subtle cross-tenant data leaks beyond SQL: shared caches, queue messages, search indexes. How do you isolate each?</AccordionTrigger>
    <AccordionContent>

      - SQL `WHERE organization_id = ?` is the leak everyone rehearses. Production leaks the same way in **every other store that forgot the tenant**.
      - **Shared caches.** Redis or Next.js `cache` keyed only by user id or path will serve tenant A's JSON to tenant B. Isolation is the key: `organizationId` is part of every cache key, and authenticated responses are never cached as public.
      - **Queue messages.** A worker that processes "generate invoice" without the tenant on the message **and** a membership check at consume time will write into whichever database connection it happens to hold. Every message carries `organizationId` from the verified request; the consumer opens the RLS transaction for that org; tenant is not taken from the job payload alone if a client could enqueue it.
      - **Search indexes.** A shared OpenSearch or Pinecone corpus with only a metadata filter is one forgotten filter away from another tenant's documents. Isolation is a **server-side filter derived from trusted identity**, or a namespace the caller cannot name. The wrapper must not accept another tenant from the client. RLS does not follow you into Redis.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="sec-threat-model">
    <AccordionTrigger>20. Threat-modeling exercise: an e-signature feature for prescriptions — identify the top five threats and a mitigation for each.</AccordionTrigger>
    <AccordionContent>

      - The threat model is the **ceremony**, not the canvas widget. A prescription e-signature asserts that this pharmacist approved this exact order for this patient in this pharmacy. Attacker goals: sign as someone else, swap the document, or deny the act later.
      - **Stolen or confused session.** Mitigation: step-up authentication at sign time, a short-lived signing challenge, and role plus tenant checks. A button behind a logged-in cookie is not a signature. **Document substitution.** Mitigation: bind a one-time signing challenge to an **immutable server-side document version and digest**, show the authoritative human-readable summary, and revalidate version, signer, tenant, and policy in the same transaction that commits.
      - **Replay of a completed ceremony.** Mitigation: one-time server nonce, short expiry, and an idempotency key so a double submit cannot become two legal acts. **Cross-tenant retrieval of the signed artifact.** Mitigation: the same object-level control as IDOR — membership, row in tenant, RLS — and signed URLs that expire.
      - **Repudiation and a writable audit trail.** Mitigation: append-only, hash-chained events with actor, patient, payload digest, time, and outcome. The ceremony fail-closes if policy times out.

    </AccordionContent>
  </AccordionItem>
