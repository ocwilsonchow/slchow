**Regression tests** on the frontend protect behavior that users already rely on: a form that still submits, a draft that still survives a failed request, a login flow that still lands in the right place after a refactor.

<br />

- They are not about chasing a coverage percentage.
- Catch the regression at the cheapest layer that still proves the behavior — **Vitest**, **React Testing Library**, or **Cypress**.

<br />

---

## 1. What to Test and Where

Prioritize by **blast radius**, not by how easy the test is to write.

<br />

| Layer | Tool | Use when |
| --- | --- | --- |
| Unit | Vitest | Pure logic, reducers, parsers, URL/state helpers |
| Component | Vitest + React Testing Library | Interaction contracts: click → state → text/role |
| Integration-ish | Vitest + RTL + MSW | Page sections with mocked network |
| E2E | Cypress | Full critical journeys across routes and auth |

<br />

- Focus on money, auth, data-loss paths, high-traffic entry flows, and bugs that already shipped once.
- Skip one-off chrome and purely visual polish.
- Catch regressions at the **cheapest layer that still proves the behavior**.
- If a **real browser** and **real navigation** are required to trust the result, use Cypress. Otherwise stay in Vitest.
- **Failure:** proving the same fact at every layer.

<br />

## 2. Unit and Component Regressions with Vitest and RTL

For component regressions, test **user-observable outcomes**.

<br />

```tsx
import { render, screen } from "@testing-library/react"
import userEvent from "@testing-library/user-event"
import { describe, expect, it, vi } from "vitest"

import { DraftForm } from "./draft-form"

describe("DraftForm", () => {
  it("keeps draft when network fails", async () => {
    const user = userEvent.setup()
    const onSubmit = vi.fn().mockRejectedValue(new Error("network"))

    render(<DraftForm initialValue="hello" onSubmit={onSubmit} />)

    await user.clear(screen.getByRole("textbox", { name: /draft/i }))
    await user.type(screen.getByRole("textbox", { name: /draft/i }), "updated")
    await user.click(screen.getByRole("button", { name: /save/i }))

    expect(await screen.findByRole("alert")).toHaveTextContent(/could not save/i)
    expect(screen.getByRole("textbox", { name: /draft/i })).toHaveValue("updated")
    expect(screen.getByRole("button", { name: /save/i })).toBeEnabled()
  })

  it("disables save while a submit is in flight", async () => {
    const user = userEvent.setup()
    let resolveSubmit!: () => void
    const onSubmit = vi.fn(
      () =>
        new Promise<void>((resolve) => {
          resolveSubmit = resolve
        })
    )

    render(<DraftForm initialValue="hello" onSubmit={onSubmit} />)

    await user.click(screen.getByRole("button", { name: /save/i }))

    expect(screen.getByRole("button", { name: /save/i })).toBeDisabled()

    resolveSubmit()
    expect(await screen.findByRole("button", { name: /save/i })).toBeEnabled()
  })
})
```

<br />

- Query by **role** and accessible name, drive the UI with `userEvent`, and assert what the user can see or do next.
- Name the test after the regression it protects. `keeps draft when network fails` tells a future reader more than `handles error`.
- When a component becomes hard to test, extract pure logic — formatting, validation, URL building — and unit-test those functions. Keep the component test on wiring and interaction.
- **Failure:** asserting internal state, CSS class lists, or private function calls.

<br />

```ts
import { describe, expect, it } from "vitest"

import { getNextDraftStatus } from "./draft-status"

describe("getNextDraftStatus", () => {
  it("returns error without clearing the draft value", () => {
    expect(
      getNextDraftStatus({
        value: "updated",
        result: { ok: false, reason: "network" },
      })
    ).toEqual({
      value: "updated",
      status: "error",
      message: "Could not save",
    })
  })
})
```

### Testing Custom Hooks

When complex state logic does not need a UI, test the hook directly with `renderHook` and `act`.

<br />

```tsx
import { renderHook, act } from "@testing-library/react"
import { describe, expect, it } from "vitest"

import { usePagination } from "./use-pagination"

describe("usePagination", () => {
  it("advances to the next page", () => {
    const { result } = renderHook(() => usePagination({ total: 50, perPage: 10 }))

    expect(result.current.page).toBe(1)

    act(() => {
      result.current.next()
    })

    expect(result.current.page).toBe(2)
  })
})
```

<br />

- This proves state transitions without mounting unnecessary DOM.

<br />

### Type-Safe Test Data

For behavior, prefer **deterministic fixtures** over broad snapshots.

<br />

```ts
type Note = { id: string; title: string; status: "draft" | "published" }

export function buildNote(overrides?: Partial<Note>): Note {
  return {
    id: "test-id",
    title: "Default Title",
    status: "draft",
    ...overrides,
  }
}

// Usage in a test:
// const publishedNote = buildNote({ status: "published" })
```

<br />

- Snapshots are useful for some serialization cases, but they are a weak regression signal when the contract is “user can still recover from a failed save.”
- Use TypeScript's `Partial<T>` to build type-safe data factories without repeating large objects in every test.

<br />

### Test Async States Explicitly

Most data-driven components have more than a success state: initial or empty, loading, success, error, retry or recovery.

<br />

```tsx
import { HttpResponse, http } from "msw"
import { server } from "../test/server"
import type { Note } from "@/types"

it("retries after the first request fails", async () => {
  const user = userEvent.setup()
  let attempts = 0

  server.use(
    http.get("/api/notes", () => {
      attempts += 1

      if (attempts === 1) {
        return HttpResponse.json(
          { message: "Temporary failure" },
          { status: 503 }
        )
      }

      // TypeScript enforces that this matches the Note[] type
      return HttpResponse.json<Note[]>([
        { id: "1", title: "Regression playbook", status: "published" }
      ])
    })
  )

  render(<NotesList />)

  expect(await screen.findByRole("alert")).toHaveTextContent(
    /could not load notes/i
  )

  await user.click(screen.getByRole("button", { name: /retry/i }))

  expect(
    await screen.findByRole("link", { name: /regression playbook/i })
  ).toBeVisible()
})
```

<br />

- The regression often lives in the **transition** between those states.
- **MSW** keeps the test at the HTTP boundary while making each response deterministic.
- This test proves the failure is visible, retry remains possible, and a later success replaces the error — without knowing whether the component uses `fetch`, a query library, or a custom hook.

## 3. Critical-Path E2E with Cypress

Cypress is where journeys that only exist with routing, auth, and the real page shell get protected.

<br />

```ts
// cypress/support/index.d.ts
declare global {
  namespace Cypress {
    interface Chainable {
      loginAs(email: string): Chainable<void>
    }
  }
}

// cypress/support/commands.ts
Cypress.Commands.add("loginAs", (email) => {
  cy.request("POST", "/api/test/login", { email })
})
```

<br />

```ts title="cypress/e2e/create-note.cy.ts"
describe("create note", () => {
  beforeEach(() => {
    cy.loginAs("writer@example.com")
    cy.seedNotes([])
  })

  it("creates a note and lands on the detail page", () => {
    cy.visit("/notes/new")

    cy.findByRole("textbox", { name: /title/i }).type("Regression playbook")
    cy.findByRole("textbox", { name: /body/i }).type(
      "Protect high-value behavior at the cheapest reliable layer."
    )
    cy.findByRole("button", { name: /publish/i }).click()

    cy.location("pathname").should("match", /\/notes\/.+/)
    cy.findByRole("heading", { name: /regression playbook/i }).should(
      "be.visible"
    )
  })
})
```

<br />

- Keep that suite small: usually **three to seven** journeys — sign in, complete the core product task, sign out or reach a durable success state.
- Seed fixtures so the test does not depend on production content. Assert URL, heading, success message — not every CSS class along the way.
- Control **authentication** through an API or task, freeze **time** when expiry matters, wait on a named request or visible outcome, isolate records per test, prefer roles and labels (test ID only when no user-facing selector exists).
- Edge cases belong in Vitest when the UI contract can be proven without a full browser. Cypress earns its keep on paths where a false green would ship a broken product.
- **Failure:** a single test that signs in, changes settings, creates a note, searches, deletes, and signs out. Split journeys at durable boundaries. Never wait on an arbitrary timeout.

<br />

## Takeaway

Frontend regression testing works best as a **triage system**.

<br />

- Protect high-value behavior at the cheapest reliable layer, grow coverage from real failures, and keep Cypress thin enough that a red build still means something.
- When something breaks once, make sure the suite will catch it the second time — preferably with a test name that still reads like a **product promise** months later.
- **Write the failing test first** when fixing a bug, and make sure it fails for the right reason before applying the fix.
- Run focused tests locally, the unit/component suite on PRs, and critical E2E journeys before merge.
- **Failure:** normalizing flake. If a test fails randomly, quarantine it, then fix or delete it. A test that passes on its third attempt is still a flaky test. Skip pixel-perfect visual diffs, exhaustive E2E edge cases, and assertions on framework internals. Manual exploratory testing still matters.
