description: How I combine Hono, Better Auth, Drizzle, PostgreSQL, Zod OpenAPI, Scalar, SST, Lambda, and API Gateway into one type-safe backend stack
---

When I build a **backend API**, I want the path from an incoming request to a database query to stay easy to follow. I also want **validation**, **documentation**, and **infrastructure** to come from the same source code instead of becoming separate projects that slowly drift apart.

The stack I use is **Hono**, **Better Auth**, **Drizzle**, **PostgreSQL**, **Zod OpenAPI**, **Scalar**, **SST**, **AWS Lambda**, and **API Gateway**. Each tool has a narrow job, and the combination gives me a small TypeScript backend that is type-safe without hiding HTTP, SQL, or AWS behind too much abstraction.

<br />

---

## 1. The Architecture

I normally deploy one **Hono** application as an **API Lambda function** and put an **API Gateway HTTP API** in front of it. Protected routes have a second Lambda function as their authorizer. API Gateway invokes the authorizer first and invokes the Hono API Lambda only when the authorizer accepts the request.

Hono's AWS adapter translates accepted Lambda events into standard `Request` objects, runs the matching middleware and route, then translates the `Response` back for API Gateway. Inside the application, **Zod schemas** validate the request. The route handler calls a service or **Drizzle query**, **PostgreSQL** stores the data, and the result is returned through Hono.

The Lambda authorizer calls **Better Auth** to validate the incoming session before protected routes reach the API Lambda. The same route schemas also produce an **OpenAPI document**. **Scalar** reads that document and renders an interactive API reference. **SST** defines and deploys the AWS infrastructure that connects all of these pieces.

<br />

```text
Client
  → API Gateway
  → Lambda authorizer
  → Better Auth session validation
  → API Gateway authorization decision
  → Hono API Lambda
  → Hono route
  → Zod validation
  → Drizzle query
  → PostgreSQL

OpenAPI schemas
  → OpenAPI JSON
  → Scalar API reference

SST
  → provisions API Gateway and both Lambda functions
  → links secrets and other AWS resources
```

<br />

I like this separation because I can point to one responsibility for every layer:

- **API Gateway** is the public HTTP entry point.
- **Lambda authorizer** verifies protected requests before the API runs.
- **API Lambda** runs the Hono application on demand.
- **Hono** handles routing and middleware.
- **Better Auth** manages identities, accounts, and sessions.
- **Zod OpenAPI** defines the HTTP contract.
- **Drizzle** provides typed SQL and schema definitions.
- **PostgreSQL** is the durable source of truth.
- **Scalar** makes the contract readable and testable.
- **SST** defines, links, and deploys the infrastructure.

<br />

## 2. Hono as the HTTP Layer

**Hono** is small enough that the application still looks like an **HTTP server**. Routes have methods and paths, **middleware** is explicit, and handlers receive a context with the request and response helpers.

For Lambda, I export Hono through the AWS adapter:

<br />

```ts
import { OpenAPIHono } from "@hono/zod-openapi"
import { handle } from "hono/aws-lambda"

const app = new OpenAPIHono()

app.options("*", (c) => {
  return c.body(null, 204)
})

app.get("/health", (c) => {
  return c.json({ status: "ok" })
})

export const handler = handle(app)
```

<br />

I usually keep the **Lambda entry point** thin. It creates the app, mounts middleware and route modules, then exports the handler. **Business logic** does not need to know that Lambda or API Gateway exists.

Hono also uses **Web Standard** `Request` and `Response` APIs. That keeps most of the application **portable**: if I later run the same routes in Node.js, Bun, or another runtime, only the adapter and environment integration should need to change.

<br />

## 3. Defining the Contract with Zod OpenAPI

The most important part of an API is its **contract**: what a route accepts, what it returns, and how errors are represented. I define that contract with `@hono/zod-openapi`.

Here is a simplified route for creating a user:

<br />

```ts
import { createRoute, z } from "@hono/zod-openapi"
import { ErrorSchema, GatewayErrorSchema } from "./schemas"

app.openAPIRegistry.registerComponent("securitySchemes", "CookieAuth", {
  type: "apiKey",
  in: "header",
  name: "Cookie",
  description: "Better Auth session cookie",
})

const UserSchema = z
  .object({
    id: z.string().uuid(),
    email: z.string().email(),
    name: z.string(),
  })
  .openapi("User")

const CreateUserSchema = z
  .object({
    email: z.string().email(),
    name: z.string().min(1).max(100),
  })
  .openapi("CreateUser")

const createUserRoute = createRoute({
  method: "post",
  path: "/users",
  security: [{ CookieAuth: [] }],
  request: {
    body: {
      content: {
        "application/json": {
          schema: CreateUserSchema,
        },
      },
    },
  },
  responses: {
    201: {
      description: "User created",
      content: {
        "application/json": {
          schema: UserSchema,
        },
      },
    },
    400: {
      description: "Invalid request",
      content: {
        "application/json": {
          schema: ErrorSchema,
        },
      },
    },
    401: {
      description: "Authentication cookie is missing",
      content: {
        "application/json": {
          schema: GatewayErrorSchema,
        },
      },
    },
    403: {
      description: "The session is invalid or not authorized",
      content: {
        "application/json": {
          schema: GatewayErrorSchema,
        },
      },
    },
  },
})
```

<br />

The handler receives already validated input:

<br />

```ts
app.openapi(createUserRoute, async (c) => {
  const input = c.req.valid("json")
  const user = await createUser(input)

  return c.json(user, 201)
})
```

<br />

This removes three common sources of drift. The **runtime validator**, **TypeScript input type**, and **OpenAPI request schema** all come from the same definition.

I still describe **response schemas** explicitly. TypeScript can check what my handler returns while I am developing, but clients need a runtime-independent contract. The response section also forces me to decide which **status codes** are part of the API instead of returning whatever is convenient inside a handler.

## 4. Keeping Errors Consistent

Successful responses are usually easy. **Errors** are where an API becomes inconsistent unless I define a common shape early.

<br />

```ts
export const ErrorSchema = z
  .object({
    code: z.string(),
    message: z.string(),
    requestId: z.string().optional(),
    issues: z
      .array(
        z.object({
          path: z.string(),
          message: z.string(),
        })
      )
      .optional(),
  })
  .openapi("ApiError")

export const GatewayErrorSchema = z
  .object({
    message: z.string(),
  })
  .openapi("GatewayError")

const app = new OpenAPIHono({
  defaultHook: (result, c) => {
    if (!result.success) {
      return c.json(
        {
          code: "VALIDATION_ERROR",
          message: "Request validation failed.",
          issues: result.error.issues.map((issue) => ({
            path: issue.path.map(String).join(".") || "request",
            message: issue.message,
          })),
        },
        400
      )
    }
  },
})
```

<br />

I reuse the application error schema for expected `400`, `404`, and `409` responses and install one **Hono error handler** for unexpected failures. The `defaultHook` keeps request-validation failures consistent with that schema. **Validation errors** should explain what the caller can fix; **internal errors** should log the underlying exception but return a safe message.

API Gateway generates authorizer failures before Hono runs, so its `401` and `403` responses use the smaller gateway error shape instead. I document that shape rather than pretending every error comes from the application.

I also attach a **request ID** near the beginning of the middleware chain and include it in application logs and error responses. API Gateway and Lambda already expose useful request context, but having one application-level ID makes it easier to trace a request across middleware, queries, and external services.

<br />

## 5. Drizzle and PostgreSQL

I use **PostgreSQL** because its relational model, constraints, transactions, and query capabilities fit most application backends. **Drizzle** gives me TypeScript schema definitions and typed queries while keeping the **SQL model** visible.

<br />

```ts
import {
  pgTable,
  text,
  timestamp,
  uniqueIndex,
  uuid,
} from "drizzle-orm/pg-core"

export const users = pgTable(
  "users",
  {
    id: uuid("id").defaultRandom().primaryKey(),
    email: text("email").notNull(),
    name: text("name").notNull(),
    createdAt: timestamp("created_at", { withTimezone: true })
      .defaultNow()
      .notNull(),
  },
  (table) => [uniqueIndex("users_email_idx").on(table.email)]
)
```

<br />

The schema is useful application code, but the **database remains the final authority**. The **unique index** protects email uniqueness even if two Lambda invocations try to create the same user at the same time. I prefer **database constraints** over a check-then-insert sequence that can race under concurrency.

A Drizzle query remains close to SQL:

<br />

```ts
import { eq } from "drizzle-orm"

export async function findUserById(id: string) {
  const [user] = await db.select().from(users).where(eq(users.id, id)).limit(1)

  return user ?? null
}
```

<br />

For writes that must succeed or fail together, I use a **database transaction** rather than trying to coordinate multiple independent queries in application code.

## 6. Better Auth as the Authentication Service

I use **Better Auth** as the authentication service inside the Hono API. It is not a hosted identity provider by default; it is a TypeScript authentication framework that I run with the rest of the backend. It owns sign-up, sign-in, sign-out, session, and account flows while keeping the user and session data in PostgreSQL.

Better Auth has a Drizzle adapter, so it can use the same database connection and migration workflow as the application:

<br />

```ts
import { betterAuth } from "better-auth"
import { drizzleAdapter } from "better-auth/adapters/drizzle"
import { Resource } from "sst"
import { db } from "./db"

export const auth = betterAuth({
  secret: Resource.BetterAuthSecret.value,
  baseURL: process.env.BETTER_AUTH_URL,
  database: drizzleAdapter(db, {
    provider: "pg",
  }),
  emailAndPassword: {
    enabled: true,
  },
  trustedOrigins: ["https://app.example.com"],
})
```

<br />

I keep the Better Auth secret in a stage-specific **linked SST resource** and read it through `Resource.BetterAuthSecret.value`. The secret must be at least 32 characters and cryptographically random. `BETTER_AUTH_URL` contains the public API origin used for authentication. I also keep `trustedOrigins` explicit instead of accepting requests from every origin.

After configuring Better Auth or adding a plugin, I generate its Drizzle schema and include the resulting tables in the normal migration process:

<br />

```text
bunx sst shell -- npx auth@latest generate --output ./src/db/auth-schema.ts
  → review the generated Drizzle schema
  → generate and review the SQL migration
  → apply it before deploying the API
```

<br />

I include both the application schema and generated auth schema in the Drizzle Kit configuration. Running the CLI through `sst shell` makes the linked database URL and Better Auth secret available while the configuration is loaded.

I mount the Better Auth handler under a public Hono route. Sign-up, sign-in, callbacks, and session creation must remain reachable before a caller is authenticated:

<br />

```ts
app.on(["GET", "POST"], "/api/auth/*", (c) => {
  return auth.handler(c.req.raw)
})
```

<br />

Hono already exposes a Web Standard request, so Better Auth can receive the raw request directly. The same path works behind API Gateway and Lambda because Hono's AWS adapter handles the translation at the outer boundary.

For protected application routes, I use an **API Gateway Lambda authorizer**. API Gateway invokes this small function before invoking the Hono API Lambda. The authorizer rebuilds the incoming headers, asks Better Auth for the session, and returns a simple authorization decision:

<br />

```ts
import type { APIGatewayRequestSimpleAuthorizerHandlerV2WithContext } from "aws-lambda"
import { auth } from "./auth"

type AuthContext = {
  userId?: string
  sessionId?: string
}

export const handler: APIGatewayRequestSimpleAuthorizerHandlerV2WithContext<
  AuthContext
> = async (event) => {
  const headers = new Headers()

  for (const [name, value] of Object.entries(event.headers ?? {})) {
    if (value) {
      headers.set(name, value)
    }
  }

  if (event.cookies?.length) {
    headers.set("cookie", event.cookies.join("; "))
  }

  const result = await auth.api.getSession({ headers })

  if (!result) {
    return {
      isAuthorized: false,
      context: {},
    }
  }

  return {
    isAuthorized: true,
    context: {
      userId: result.user.id,
      sessionId: result.session.id,
    },
  }
}
```

<br />

API Gateway rejects an unauthorized request before the API Lambda runs. A missing cookie produces `401 Unauthorized` before the authorizer is invoked; an authorizer response with `isAuthorized: false` produces `403 Forbidden`. For an authorized request, API Gateway adds the authorizer context to the trusted Lambda event. Hono can read that identity without querying Better Auth a second time:

<br />

```ts
import type { LambdaEvent } from "hono/aws-lambda"

type Bindings = {
  event: LambdaEvent
}

type AuthContext = {
  userId: string
  sessionId: string
}

const app = new OpenAPIHono<{ Bindings: Bindings }>()

app.get("/users/me", (c) => {
  const requestContext = c.env.event.requestContext as {
    authorizer?: {
      lambda?: AuthContext
    }
  }
  const identity = requestContext.authorizer?.lambda

  if (!identity) {
    return c.json(
      {
        code: "UNAUTHORIZED",
        message: "Authentication is required.",
      },
      401
    )
  }

  return c.json({
    userId: identity.userId,
  })
})
```

<br />

I trust the authorizer context because API Gateway creates it; I never copy identity from a client-controlled header. I pass only small identifiers through the context and load current roles or permissions inside the API when an authorization decision needs them.

This keeps **authentication** separate from **authorization**. Better Auth and the authorizer prove who the caller is and validate the session. The application still decides whether that user may read a record, change a resource, or perform an administrative action.

When the frontend and API use different origins, I configure API Gateway CORS, allow credentials, and permit only the frontend origins I control. Client requests also use `credentials: "include"`. I prefer same-site custom domains such as `app.example.com` and `api.example.com`, then let Better Auth manage its secure, HTTP-only cookies instead of creating a second token system around it. If the sites are genuinely cross-site, I explicitly configure and review `SameSite=None; Secure` and account for browsers that restrict third-party cookies.

I attach the Lambda authorizer only to protected business routes. The Better Auth routes stay public, otherwise API Gateway would block sign-in before Better Auth could process it. I document both `401` and `403` responses on protected Zod OpenAPI routes so the contract matches API Gateway's behavior.

I start with authorizer caching disabled. Caching reduces database work, but a revoked Better Auth session could otherwise remain authorized until the cache entry expires. If I enable it later, I use a short TTL that matches the security requirements of the API.

## 7. Database Connections in Lambda

**Lambda** changes how I think about **database connections**. One invocation may be short-lived, but the **execution environment** can stay warm and serve more requests. I therefore create the database client outside the handler so **warm invocations** can reuse it.

<br />

```ts
import { drizzle } from "drizzle-orm/postgres-js"
import postgres from "postgres"
import { Resource } from "sst"

const client = postgres(Resource.DatabaseUrl.value, {
  max: 1,
  connect_timeout: 10,
  idle_timeout: 20,
})

export const db = drizzle(client)
```

<br />

The important caveat is that reusing one connection per warm Lambda environment is not the same as **globally pooling connections**. Both the authorizer Lambda and API Lambda can scale to many environments, and each environment can open its own connection. Unconstrained functions can therefore overwhelm a small PostgreSQL instance long before they run out of compute.

In production I account for this at the architecture level: I cap **connection usage**, set sensible **timeouts**, limit **Lambda concurrency** when necessary, and use a **database-aware proxy or pooler** when the expected scale requires one. If the connection goes through a transaction-mode pooler, I also check whether prepared statements are supported and disable them with `prepare: false` when required.

This is one area where a serverless API still needs **capacity planning**. Lambda removes server management; it does not remove the PostgreSQL connection limit.

## 8. Migrations Are a Deployment Step

**Drizzle Kit** generates **SQL migrations** from schema changes, but I keep the generated SQL in **version control** and review it before applying it.

<br />

```ts
import { defineConfig } from "drizzle-kit"
import { Resource } from "sst"

export default defineConfig({
  dialect: "postgresql",
  schema: ["./src/db/schema.ts", "./src/db/auth-schema.ts"],
  out: "./drizzle",
  dbCredentials: {
    url: Resource.DatabaseUrl.value,
  },
})
```

<br />

My normal sequence is:

<br />

```text
change the Drizzle schema
  → generate a migration
  → review the SQL
  → test it against a disposable database
  → apply it before code depends on the new shape
```

<br />

I avoid running migrations inside the **Lambda request path**. Multiple **cold starts** can happen concurrently, and an API request should not become responsible for coordinating schema changes.

For changes that cannot be deployed atomically, I use an **expand-and-contract migration**: add the new structure first, deploy code that can work with both versions, backfill data, switch reads and writes, then remove the old structure in a later deployment.

<br />

## 9. OpenAPI and Scalar

Once the routes are registered, `OpenAPIHono` can expose the generated OpenAPI document:

<br />

```ts
app.doc("/openapi.json", {
  openapi: "3.0.0",
  info: {
    title: "Example API",
    version: "1.0.0",
  },
})
```

<br />

I then point Scalar at that endpoint:

<br />

```ts
import { Scalar } from "@scalar/hono-api-reference"

app.get(
  "/docs",
  Scalar({
    url: "/openapi.json",
    theme: "kepler",
  })
)
```

<br />

This gives me an **API reference** that is useful during development and for consumers of the API. A developer can inspect schemas, see status codes, and send test requests without me maintaining a separate documentation site.

The **OpenAPI document** is also more valuable than the UI alone. I can use it in CI, generate **typed clients**, or compare contracts for **breaking changes**. Scalar is the presentation layer; the OpenAPI document is the portable artifact.

For a **private API**, I do not assume that documentation should be public just because the endpoint is easy to add. I protect or disable `/docs` as appropriate, and I make sure examples never expose real credentials or customer data.

## 10. Deploying with SST

**SST** lets me define the **AWS infrastructure in TypeScript** next to the application. A simplified configuration creates the API Lambda, the Better Auth authorizer Lambda, and an API Gateway HTTP API. The authentication endpoints use the API Lambda without an authorizer, while the catch-all business route requires one:

<br />

```ts
export default $config({
  app(input) {
    return {
      name: "example-api",
      home: "aws",
      removal: input?.stage === "production" ? "retain" : "remove",
      protect: input?.stage === "production",
    }
  },
  async run() {
    const databaseUrl = new sst.Secret("DatabaseUrl")
    const betterAuthSecret = new sst.Secret("BetterAuthSecret")
    const api = new sst.aws.ApiGatewayV2("Api", {
      domain: "api.example.com",
      cors: {
        allowOrigins: ["https://app.example.com"],
        allowMethods: ["GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"],
        allowHeaders: ["Content-Type", "Authorization"],
        allowCredentials: true,
      },
    })

    const apiFunction = new sst.aws.Function("ApiFunction", {
      handler: "src/index.handler",
      link: [databaseUrl, betterAuthSecret],
      environment: {
        BETTER_AUTH_URL: api.url,
      },
    })

    const authorizerFunction = new sst.aws.Function("AuthorizerFunction", {
      handler: "src/authorizer.handler",
      link: [databaseUrl, betterAuthSecret],
      environment: {
        BETTER_AUTH_URL: api.url,
      },
    })

    const authorizer = api.addAuthorizer({
      name: "BetterAuthAuthorizer",
      lambda: {
        function: authorizerFunction.arn,
        identitySources: ["$request.header.Cookie"],
        payload: "2.0",
        response: "simple",
      },
    })

    api.route("ANY /api/auth/{proxy+}", apiFunction.arn)
    api.route("OPTIONS /{proxy+}", apiFunction.arn)

    api.route("$default", apiFunction.arn, {
      auth: {
        lambda: authorizer.id,
      },
    })

    return {
      api: api.url,
    }
  },
})
```

<br />

The explicit public `OPTIONS /{proxy+}` route is important. A `$default` route also catches browser preflight requests, and applying the authorizer to those requests would reject them before CORS could succeed. The Hono application answers `OPTIONS` with `204`, while API Gateway adds the configured CORS headers.

**Linked SST resources** are available to both Lambda functions through the generated `Resource` interface:

<br />

```ts
import { Resource } from "sst"

const databaseUrl = Resource.DatabaseUrl.value
```

<br />

I pass that value into the database module rather than scattering environment access throughout the application. This keeps configuration at the edge of the codebase and makes the modules underneath easier to test.

SST also gives me **stage-specific deployments**. A personal or preview stage can have its own API URL and secrets, while production resources can be protected from accidental removal. During local development, `sst dev` connects the local process to deployed resources, so I can run the real Hono handler without manually reproducing every AWS integration.

## 11. Why One API Lambda

API Gateway can route every endpoint to a different Lambda function, but I normally start with one **Hono API Lambda** behind a catch-all route. The Lambda authorizer stays separate because it is an infrastructure security boundary that must run before the API function.

Keeping the business routes in one API Lambda puts middleware, error handling, OpenAPI generation, and database setup in one place. It also avoids turning every small endpoint into an infrastructure decision.

I split functions when there is an **operational reason** to do so: different permissions, memory or timeout requirements, independent scaling behavior, asynchronous workloads, or a security boundary. I do not split them only because the URL paths are different.

The result is still **serverless**. API Gateway invokes the authorizer Lambda first, then scales the Hono API Lambda only for accepted requests. Hono provides the internal router inside the API function.

## 12. The Request Lifecycle

For a `POST /users` request, the complete path looks like this:

1. **API Gateway** receives the HTTPS request.
2. API Gateway invokes the **Lambda authorizer** with the request headers and cookies.
3. The authorizer asks **Better Auth** to resolve and validate the session.
4. A missing cookie produces `401`; an invalid session denied by the authorizer produces `403`. Neither case invokes the API Lambda.
5. A valid session returns the user and session IDs in the authorizer context.
6. API Gateway invokes the **Hono API Lambda** through the catch-all route.
7. **Hono's Lambda adapter** creates a Web Standard request.
8. **Middleware** adds request context and logging.
9. **Zod** validates the JSON body against the route schema.
10. The handler calls the user service with typed input.
11. **Drizzle** sends a parameterized query to PostgreSQL.
12. **PostgreSQL** enforces constraints and returns the inserted row.
13. **Hono** serializes the `201` response.
14. The adapter returns the result through API Gateway to the client.

The route schema used in step 9 is also present in `/openapi.json`, and Scalar turns it into the documentation shown at `/docs`.

That closed loop is the main reason I use this stack. The code that accepts a request, the code that validates it, and the document that explains it all describe the same contract.

## 13. What I Test

I keep most tests below the Lambda adapter. Because Hono can handle standard requests, **route tests** can call the application directly without deploying AWS infrastructure. For protected routes, I pass a mock Lambda event binding containing the authorizer context:

<br />

```ts
const env = {
  event: {
    requestContext: {
      authorizer: {
        lambda: {
          userId: "f7e81d3c-98f6-4d68-a102-739ff4104a63",
          sessionId: "test-session",
        },
      },
    },
  },
} as unknown as Bindings

const response = await app.request(
  "/users",
  {
    method: "POST",
    headers: {
      "content-type": "application/json",
    },
    body: JSON.stringify({
      email: "person@example.com",
      name: "Example Person",
    }),
  },
  env
)

expect(response.status).toBe(201)
```

<br />

I use a **real disposable PostgreSQL database** for query and migration tests. A mock can verify that a function was called, but it cannot reliably reproduce constraints, transactions, indexes, SQL syntax, or PostgreSQL behavior.

I reserve **deployed integration tests** for the boundaries that local route tests do not cover: public auth routes, Lambda authorizer decisions, authorizer context propagation, API Gateway configuration, Lambda permissions, linked resources, domains, and AWS-specific request behavior.

## 14. The Trade-offs

This stack is not free of complexity. **OpenAPI response definitions** add some repetition. **Lambda cold starts** still exist. **PostgreSQL connections** need deliberate limits. AWS logs and local logs are not identical, and distributed systems become harder to debug as more services are added.

There is also a **boundary to type safety**. TypeScript types disappear at runtime, which is why **Zod validation** and **PostgreSQL constraints** still matter. An inferred type improves the development experience, but it cannot make an untrusted request valid or prevent two concurrent writes from violating a rule.

I accept those trade-offs because each layer remains replaceable. Scalar can be replaced without changing routes. PostgreSQL can move between providers without changing the HTTP contract. Hono can run outside Lambda. SST can change the infrastructure without becoming the business logic.

<br />

## Final Thoughts

What I want from a backend stack is not the largest collection of features. I want a short path from contract to implementation:

<br />

```text
API Gateway
  → Lambda authorizer
  → validated Better Auth session
  → Hono API Lambda
  → validated Zod route
  → typed Drizzle query
  → PostgreSQL constraint
  → generated OpenAPI document
  → Scalar reference
  → SST deployment on API Gateway and both Lambda functions
```

<br />

**Hono** keeps HTTP visible. **Better Auth** manages identity and sessions. **Zod OpenAPI** makes validation and documentation agree. **Drizzle** keeps database access typed without hiding SQL. **PostgreSQL** provides the durable guarantees. **Scalar** makes the contract approachable. **SST** turns the Lambda and API Gateway setup into reviewable TypeScript.

Together, they give me a backend that is small enough to understand, explicit enough to debug, and structured enough to grow.
