## Backend Engineering

<Accordion type="single" collapsible>
  <AccordionItem value="be-event-loop">
    <AccordionTrigger>1. Walk through the Node.js event loop phases. Where do setTimeout, setImmediate, process.nextTick, and resolved promises run?</AccordionTrigger>
    <AccordionContent>

      - Node is not the browser. One **libuv** iteration is roughly **timers**, pending callbacks, idle/prepare, **poll**, **check**, then close callbacks. `process.nextTick` and resolved Promises sit on extra queues that drain **after the current operation**, between those phases.
      - **`setTimeout` / `setInterval`**: **timers** phase, once the delay has elapsed — a lower bound, not "now." **`setImmediate`**: **check** phase, after **poll**. **`process.nextTick`**: drains **before** Promise jobs; a nextTick loop **starves I/O**. Promise `.then` / `queueMicrotask`: microtask queue **after** `nextTick`.
      - From the main module, `setTimeout(fn, 0)` versus `setImmediate` is famously unordered. From an I/O callback, `setImmediate` usually wins because check follows poll in the same iteration.
      - The production default is never spinning `nextTick` to "yield." A Promise or `queueMicrotask` is the after-this-stack choice without jumping the Promise queue.
      - **Failure:** porting a browser ordering puzzle to Node and trusting the log. Full map: [The JavaScript Event Loop in Depth](/notes/javascript-event-loop-in-depth).

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-nodejs-wrong">
    <AccordionTrigger>2. When is Node.js the wrong choice? How do you handle CPU-bound work in a Node service?</AccordionTrigger>
    <AccordionContent>

      - Node is a strong default for **I/O-bound** APIs. It is the wrong default when the **event-loop thread** is the product: a hot `while`, a sync hash, a huge JSON parse, or an in-process image pipeline stalls **every** connection on that process.
      - Extra replicas do not fix a handler that pegs a core. If the domain is CPU-first — transcode, ML inference, tight crypto — pick a runtime or worker fleet that matches, rather than hiding a thread pool behind an Express facade.
      - CPU-bound work **inside** a Node service: keep HTTP handlers **short**; use **`worker_threads`** or a child process with a **pool cap**; better, **enqueue** the job and let workers own it. Watch **event-loop delay**, not only request rate.
      - Production looks like "202 and a job id," not "await the pixels in the POST." `async` does not make arithmetic concurrent.
      - **Failure:** shipping CPU as `await tightLoop()` and calling it scalable because the framework is async. Health checks on that process lie until the loop runs again.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-stateless">
    <AccordionTrigger>3. What does "stateless service" mean, and why does it matter for horizontal scaling behind a load balancer?</AccordionTrigger>
    <AccordionContent>

      - A **stateless service** means any replica can handle any request without local memory of the last one. Session, uploads, cart, job progress live in **Postgres, Redis, S3, or the token**, not in the process. RAM for JIT, pools, LRU must be **discardable**.
      - Behind a load balancer the fleet can **scale out** with round-robin, replace tasks on deploy, and skip sticky sessions. Sticky sessions are a confession that something was stored on the box.
      - In production, sessions live in Redis or a signed JWT, files in object storage, rate-limit counters in Redis, and WebSocket fan-out on a pub/sub backplane. Local cache is a performance hint, not a source of truth.
      - **Failure:** half-stateless — auth in Redis, but uploads in `/tmp`, or in-memory maps of socket ids. It works on one ECS task and breaks at two. Sticky sessions hide the bug until the balancer drains a task mid-session.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-async-queue">
    <AccordionTrigger>4. When should a request be handled asynchronously via a queue instead of synchronously in the request cycle?</AccordionTrigger>
    <AccordionContent>

      - Work comes off the request cycle when the **HTTP response does not need the finished result**, or when the work is slow, bursty, or must **retry after this process is gone**. Email, outbound webhooks, thumbnails, invoices, search indexing, flaky third parties — that is a **queue**. Authenticate, persist the intent, enqueue, return **202**.
      - It stays synchronous when the user cannot continue without the answer: password check, a price on screen, a payment **authorization** the UI is about to display. Even then the handler stays thin.
      - Production rules: an **idempotency key** on the enqueue, a worker that can fail loudly, and a status row the user can read. If it must happen even when the queue is down, the **database write in the request** is the source of truth; the queue is a relay.
      - **Failure:** **sync-over-async** — enqueue then block the socket until the worker finishes. The other is queueing work that has not been durably recorded — crash equals lost intent. Full map: [Message Queues in System Design](/notes/message-queues-in-system-design).

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-delivery-semantics">
    <AccordionTrigger>5. Explain at-least-once vs at-most-once delivery. How do you build an idempotent consumer given at-least-once semantics?</AccordionTrigger>
    <AccordionContent>

      - **At-most-once** means send and forget: duplicates are rare, **loss is allowed**. **At-least-once** means retry until ack: **duplicates are allowed**, loss is not. Most brokers in production are at-least-once. "Exactly-once" in application space is usually at-least-once **plus an idempotent consumer**.
      - Given at-least-once: a stable **event id**, an **inbox** table with a unique constraint, **database effects and the inbox insert in one transaction**. For Stripe or email, persist an outbox/operation row and pass the provider's idempotency key **before** ack. Side effects as **upserts**, not blind increments. **Ack after** that durable write.
      - Publishers stay boring: same key, same payload, **outbox** on the write side. Consumers stay idempotent anyway, because retries still happen.
      - **Failure:** acking before the side effect, or doing the side effect without recording the id — the retry then double-charges. Catching errors and still acking so the poison message vanishes. At-least-once only helps if failure **nacks** and success is **idempotent**. Full map: [Message Queues in System Design](/notes/message-queues-in-system-design).

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-retry-strategy">
    <AccordionTrigger>6. Design a retry strategy for a failing worker: exponential backoff, jitter, max attempts, and dead-letter queues.</AccordionTrigger>
    <AccordionContent>

      - Classify first. Timeouts, 503s, lock contention, "connection reset" — **retry**. Validation errors, 400s, unknown event types — **do not retry**; they will not heal and they will occupy the consumer forever.
      - Four controls: **exponential backoff** (`base * 2^attempt`, with a cap), **jitter** so ten thousand workers do not wake on the same millisecond, **max attempts** so poison cannot loop all night, **dead-letter queue** after the ceiling with a metric and a page if DLQ depth rises.
      - The retry lives in the **queue** (visibility timeout, built-in backoff) or a library with the same shape — not a `while` inside the handler. Retry only **idempotent** handlers.
      - **Failure:** retrying a non-idempotent POST, or retrying forever with no DLQ so one bad JSON sits on a hot partition. Backing off **without jitter** after a shared outage is a thundering herd. A silent DLQ is a lost business event with extra steps. Full map: [Message Queues in System Design](/notes/message-queues-in-system-design).

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-caching">
    <AccordionTrigger>7. Compare cache-aside, read-through, write-through, and write-behind caching. What is cache stampede and how do you prevent it?</AccordionTrigger>
    <AccordionContent>

      - **Cache-aside**: the app reads Redis, on miss loads the DB and fills the cache. This is the usual production choice; the app owns TTL and invalidation. **Read-through**: the cache library loads on miss — convenient, less control. **Write-through**: every write hits cache and DB before success. **Write-behind**: write the cache, flush the DB later — fast writes; **durability** is the trade.
      - **Cache stampede** is a hot key expiring and a thousand requests missing together. Prevention: **singleflight** or a lock so one request fills; **stale-while-revalidate**; probabilistic early expiry; a tiny in-process cache in front of Redis for the hottest keys.
      - The production default is cache-aside with explicit TTLs, versioned keys, and invalidation on write when freshness matters. A permission decision is never cached under a key that omits user or tenant.
      - **Failure:** stampede plus caching **transient failures** for a long TTL, or treating a dependency 500 as a cached "not found." Write-behind on money is another. Stampede is "every client was synchronized on expiry."

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-saga-outbox">
    <AccordionTrigger>8. How do you keep state consistent across two services without distributed transactions? Explain the saga and outbox patterns.</AccordionTrigger>
    <AccordionContent>

      - Distributed transactions are not run across services. Two-phase commit **blocks on in-doubt transactions** and couples availability of every participant. Each service's database stays transactional; coordination is with messages.
      - A **saga** is a sequence of local transactions. If step three fails, **compensations** run for one and two. Choreography: each service emits events. Orchestration: a coordinator drives the steps and holds visible state — better when the graph is long and you need "where is this order stuck."
      - The **outbox** fixes the dual-write: in the **same Postgres transaction**, the business row and an outbox row are written. A relay publishes to the broker. Delivery is still at-least-once, so consumers stay idempotent.
      - **Failure:** treating compensation as undo. A payment compensation is a **refund**, with its own audit — and the compensation itself must be durable and retryable. Skipping the outbox and hoping a send after `COMMIT` is good enough fails at the first crash. Full map: [Message Queues in System Design](/notes/message-queues-in-system-design).

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-eventual-consistency">
    <AccordionTrigger>9. What is eventual consistency, and how do you give users read-your-writes behavior on top of it?</AccordionTrigger>
    <AccordionContent>

      - **Eventual consistency** means replicas or services **converge** if writes stop; it does not mean the next read sees the write that just landed. The user-facing bug is: a POST creates a resource, a GET of the list misses it, so the user clicks again and now there are two.
      - **Read-your-writes** for the actor who just mutated: send subsequent reads to the **primary** for a short window; return the written entity in the **POST response** and have the client merge it; a **version** the client sends that the read path waits on; sticky routing to the writer when required.
      - Most of the product can be slightly stale — feeds, counts, search. The person who just saved cannot be. The production choice is explicit per endpoint instead of promising "the system is consistent."
      - **Failure:** hiding replica lag behind a spinner that refetches the **same replica**. Users duplicate orders. Caching the GET in front of the replica so even a primary-read fix never lands.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-locking">
    <AccordionTrigger>10. Optimistic vs pessimistic locking in application code — give a concrete case for each.</AccordionTrigger>
    <AccordionContent>

      - **Optimistic locking** assumes conflict is rare. Read the row with a `version`, write `WHERE id = $1 AND version = $2`, bump the version. Zero rows updated means someone else won. Concrete case: two people saving a **settings document**. A lock is not held while they stare at a form.
      - **Pessimistic locking** assumes conflict is likely. `SELECT ... FOR UPDATE` in a transaction, then write. Concrete case: **decrementing inventory** for the last SKU, booking a unique seat, assigning a sequential invoice number.
      - The production default is optimistic at the application layer — a version column on editable rows — and pessimistic for a few hot invariants inside a **short** transaction.
      - **Failure:** optimistic on a hot row becomes a retry storm. Pessimistic while calling Stripe inside the open transaction holds locks for hundreds of milliseconds and the pool dies. Always lock rows in the same id order. A pessimistic lock is never held across an HTTP call.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-connection-pool">
    <AccordionTrigger>11. How do you size a database connection pool? Why do serverless/ECS-scale-out architectures break naive pooling, and how does PgBouncer help?</AccordionTrigger>
    <AccordionContent>

      - A pool is a **cap on Postgres sessions**, not a performance dial turned to 100. Size from the **database** backward: `max_connections` minus superuser headroom, divided by **how many app processes** will exist at peak. Per Node process a typical start is around **10–20**. Watch pool wait time. The hard constraint is the server.
      - **Serverless and ECS scale-out** break naive pooling because **every task or Lambda execution environment** opens its own pool. Fifty tasks times twenty connections is a thousand sessions before traffic is interesting.
      - **PgBouncer** (or RDS Proxy) **multiplexes**. Transaction pooling: many app connections share few server connections, released at transaction end.
      - **Failure:** `pool_size = 100` copied from a blog into a service that autoscales to 30. Transaction pooling while using session features — temp tables, `SET`, some prepared-statement modes — then mysterious cross-talk. The pool is a budget shared with every replica.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-graceful-shutdown">
    <AccordionTrigger>12. What happens during a graceful shutdown? How do you drain in-flight requests and queue consumers on SIGTERM?</AccordionTrigger>
    <AccordionContent>

      - **Graceful shutdown** is: stop being handed **new** work, finish **in-flight** work, close resources, then exit. On ECS or Kubernetes, **SIGTERM** arrives, then a grace period, then **SIGKILL**.
      - On SIGTERM: mark **not ready** so the load balancer detaches; stop the HTTP server listening and wait for open requests with a **deadline** shorter than the grace period; queue consumers **stop fetching**, finish current messages, **nack** if the deadline hits; close the DB pool last.
      - The deadline is explicit, logged, and less than `terminationGracePeriodSeconds`. The test is SIGTERM in staging, not only SIGINT on a laptop.
      - **Failure:** exiting on SIGTERM immediately — in-flight POSTs die, brokers redeliver, users see 502. Draining HTTP but **keeping consumers running** until kill. Readiness never goes false, so the balancer keeps sending while the process is closing.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-observability">
    <AccordionTrigger>13. Explain the three pillars of observability. How do correlation IDs work across services and queue hops?</AccordionTrigger>
    <AccordionContent>

      - The three pillars: **logs** (events that can be grepped), **metrics** (cheap aggregates for SLOs and alerts), **traces** (the request as a tree of spans). Metrics wake the on-call, traces show where, logs show why.
      - A **correlation id** is a string born at the edge — or taken from an inbound header — and copied everywhere that request goes. Every log line includes it. Every outbound HTTP call sends it. Every queue message puts it in **attributes**, not only in a JSON body someone might strip. **W3C `traceparent`** is the structured form.
      - Generate if missing, never trust it for auth, and index it. A user's "it failed at 14:02" jumps from the gateway span through the worker that handled the SQS hop.
      - **Failure:** HTTP-only ids — the consumer logs a new uuid and the trail dies at the queue. Putting **user ids on metric labels** (cardinality explosion), or payloads with PII in trace attributes.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-probes">
    <AccordionTrigger>14. Liveness vs readiness probes: what should each check, and what goes wrong if readiness checks your database?</AccordionTrigger>
    <AccordionContent>

      - **Liveness** asks: should the platform **restart** this process? The check is that the event loop is alive — a cheap in-process heartbeat — not that Postgres is up. A database blip is not a liveness failure. Restarting every pod will not heal the database.
      - **Readiness** asks: should the balancer **send traffic**? The check is that the process is listening, warmed, and not shutting down. A cheap DB ping is reasonable **only** if the pod cannot serve useful traffic without that database, with hysteresis so a blip does not empty the fleet. Optional dependencies stay out of both probes.
      - **Failure:** one `/health` used for both probes. Slow DB then looks like a dead process; kube kills healthy replicas during a blip — a **restart storm**. Liveness stays dumb and local; dependency health lives on dashboards and SLOs.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-cron-once">
    <AccordionTrigger>15. You run a nightly cron job across 4 ECS tasks — how do you ensure it runs exactly once?</AccordionTrigger>
    <AccordionContent>

      - Four ECS tasks and a nightly cron **inside the app** means four runs unless it is prevented. Web fleets are for request fan-out. Schedules are not. Schedulers are usually **at-least-once**, so "start one task" is not enough.
      - **Best**: do not cron in the web fleet. EventBridge, a CloudWatch rule, or a Kubernetes `CronJob` starts a dedicated worker with desired count 1, and the **effect** is still idempotent. Fallback: a durable `job_runs` row with a unique key on `(job_name, scheduled_period)`, or **leader election** with a Redis lease / Postgres **advisory lock** plus fencing.
      - Alerts fire when **zero** runs happened for the day, not only when one threw.
      - **Failure:** all four firing at midnight with no lock. A lock **without TTL**: the leader dies, the lock stays, and the job never runs again. "Exactly once" is **one successful execution**, not one attempt that crashed after the side effect.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-secrets">
    <AccordionTrigger>16. How should secrets and config be managed and rotated in production? Why are plain env vars sometimes insufficient?</AccordionTrigger>
    <AccordionContent>

      - Secrets are **credentials that rotate**; config is **behavior that deploys**. Secrets are not baked into images, git, or AMI snapshots. Production choice: a manager — Secrets Manager, SSM, Vault — and **IAM roles** so the task does not start with a long-lived cloud key. RDS IAM auth or short-lived tokens beat a password in the environment.
      - Rotation: change the secret in the manager, then **recycle** tasks so they fetch the new value. For DB passwords, dual-value rotation — accept old and new for a window — then drop the old.
      - Plain **env vars** leak: same-user `/proc` and crash dumps, debug "print env," child-process inheritance, CI logs, ECS task-definition diffs. No versioning, no fine-grained access, no forced rotation.
      - **Failure:** `DATABASE_URL` with a password in plaintext env, or rotating Secrets Manager while **never restarting** the process so it holds the old password until 3 a.m. Another: committing `.env` because local DX was convenient.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-testing">
    <AccordionTrigger>17. Describe your backend testing strategy: what belongs in unit vs integration vs e2e tests, and where do you draw mocking boundaries?</AccordionTrigger>
    <AccordionContent>

      - **Unit**: pure domain — pricing rules, state machines, mapping, policy. No I/O. Mock **time** and randomness, not the module's own getters.
      - **Integration**: this process against a **real Postgres** (testcontainers) and maybe a real Redis. This is where SQL, transactions, migrations, and unique constraints fail. Mock **third-party HTTP** at the adapter boundary, not the repository. **E2E**: a small set of journeys through HTTP as a client — signup, a money path, a permission denial.
      - Mocking boundary: **process edges** — network, clock, vendor SDKs — not every internal function. The ORM is not mocked for the test that exists to catch a wrong column. If a bug would only appear in SQL, the test must speak SQL.
      - **Failure:** a suite that is 90 percent mocked units and still cannot catch a missing `WHERE tenant_id`. The other is e2e for every branch, forty minutes, nobody runs it. Mocks are for things the service does not own. The database it does.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-multi-tenancy">
    <AccordionTrigger>18. Compare shared-schema (tenant_id column), schema-per-tenant, and database-per-tenant multi-tenancy. What breaks operationally at 1,000 tenants?</AccordionTrigger>
    <AccordionContent>

      - **Shared schema, `tenant_id` column**: one DB, one migration train, every tenant-owned row tagged. Fastest to run. Isolation is a discipline plus **Postgres RLS**. This is the production model with Hono, Better Auth organizations, and Drizzle — [Building a Multi-Tenant Backend with Hono, Better Auth, Drizzle, and Postgres RLS](/notes/multi-tenant-backend-drizzle-hono-better-auth).
      - **Schema-per-tenant**: `tenant_abc.orders`. Stronger isolation, **N migrations**, `search_path` games, connection routing per request. **Database-per-tenant**: stronger isolation and noisy-neighbor control; **N backups, N failovers, N connection setups**. Separate logical databases on one cluster still share compute; strongest isolation is separate infrastructure when a tenant pays for it.
      - At **1,000 tenants**, schema-per-tenant and database-per-tenant become an **operations product**: migration fan-out, pool explosion, provisioning time, monitoring cardinality. Shared schema still works if indexes lead with `tenant_id`, jobs always carry tenant context, and quotas exist.
      - **Failure:** shared schema **without** RLS and a background worker that forgets the tenant filter — that is a data leak. Opening a pool per tenant at 1,000 and discovering `max_connections` first.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-realtime-fanout">
    <AccordionTrigger>19. WebSockets vs SSE vs long polling — tradeoffs, and how do you broadcast events across multiple server instances?</AccordionTrigger>
    <AccordionContent>

      - **Long polling**: client asks, server waits, client asks again. Easy behind vanilla HTTP. Wasteful; latency is one round trip per message. **SSE**: server-to-client stream over HTTP. Auto-reconnect, simple, **one-way**. Disable proxy buffering and send heartbeats. **WebSockets**: bidirectional, lowest overhead once up. Heartbeats, backpressure, and **stateful connections**. Harder behind naive Layer-7 timeouts.
      - Broadcast across **multiple instances**: a connection lives on **one** process. Events publish to **Redis pub/sub** (or NATS). Every instance subscribes and forwards to **its** local connections. Sticky sessions help reconnects; they are not a substitute for the bus.
      - In production the preference is SSE if the client only listens; WebSockets if both sides speak. Cap per-instance connections and scale the fleet.
      - **Failure:** emitting only in-process — it works on one box, silent on the other three. No ping so the load balancer kills idle sockets. Scale-out without pub/sub is a demo.

    </AccordionContent>
  </AccordionItem>

  <AccordionItem value="be-design-webhook-ingest">
    <AccordionTrigger>20. Design exercise: a webhook ingestion endpoint that must survive a 10x traffic spike without losing events or falling over.</AccordionTrigger>
    <AccordionContent>

      - **Acknowledge fast, persist durable, process async.** The ingest endpoint is a shock absorber, not the business workflow. A 10x spike is a queue problem that should already exist.
      - `POST /webhooks/:source` verifies the **signature** first. Treat the provider's **delivery id** as an idempotency key. In the request the **raw body** is written to something durable — SQS, Kinesis, or a `webhook_events` row — **then** return **2xx**. Workers parse, validate, apply, and mark processed; apply is **idempotent**.
      - On a 10x spike, ingest scales horizontally and the **queue** absorbs; workers scale on queue depth, not inbound RPS. Fail closed if the durable write itself is down: return 503 so the provider retries later, never 200 on an in-memory buffer.
      - **Failure:** returning 200 **before** persist — crash equals lost events. Doing CRM sync, emails, and domain workflows **in the request** so the spike takes down the API and the provider's retries amplify it. Ingest is a write-ahead log. Everything else is a consumer.

    </AccordionContent>
  </AccordionItem>
