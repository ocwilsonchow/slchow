An AI agent **calls tools in a loop to achieve a goal**. That loop — and the autonomy it implies — is what separates agents from static automations and single-turn LLM calls.

Every agent shares three capabilities:

- **Perception** — ingest data from APIs, databases, or user input
- **Reasoning** — use an LLM to evaluate that data against instructions
- **Acting** — call tools or return structured output that triggers downstream effects

Agency is a spectrum: binary decision trees at the low end; memory, tool use, and retries in the middle; planning, parallel sub-agents, and self-correction at the high end.

When choosing an **agent architecture**, start from the standard taxonomy below.

---

## Types of AI Agents

These types map roughly to increasing complexity and autonomy. Most production use cases need at least goal-based reasoning; multi-agent systems help when one agent's context window becomes unwieldy.

<Accordion type="single" collapsible>
  <AccordionItem value="simple-reflex">
    <AccordionTrigger>Simple reflex agents</AccordionTrigger>
    <AccordionContent>

Map inputs to outputs using condition-action rules. No memory, no world model, no planning.

**Example:** Email spam filter, Alexa skill responding to a wake word

**When to use:** Structured, repeatable decisions where state is fully observable

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="model-based-reflex">
    <AccordionTrigger>Model-based reflex agents</AccordionTrigger>
    <AccordionContent>

Maintain an internal model of the world, updated as new data arrives. Act under partial observability.

**Example:** Warehouse robots inferring shelf contents from partial sensor data

**When to use:** Environments where you can't observe full state at each step

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="goal-based">
    <AccordionTrigger>Goal-based agents</AccordionTrigger>
    <AccordionContent>

Evaluate possible actions against a desired outcome and select the path most likely to achieve it.

**Example:** A logistics AI agent rerouting deliveries based on traffic and weather

**When to use:** Tasks with clear outcomes and multiple possible paths

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="utility-based">
    <AccordionTrigger>Utility-based agents</AccordionTrigger>
    <AccordionContent>

Assign a score to each potential outcome and optimize for the highest utility.

**Example:** Dynamic pricing systems balancing revenue, inventory levels, and competitor activity

**When to use:** Multiple paths reach the goal and you need tradeoff reasoning

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="learning">
    <AccordionTrigger>Learning agents</AccordionTrigger>
    <AccordionContent>

Improve performance over time by analyzing feedback from their own actions. Often use reinforcement learning or machine learning.

**Example:** Fraud detection agents that learn to flag new attack methods from evolving threats

**When to use:** Environments where patterns shift and the AI agent must adapt

    </AccordionContent>

  </AccordionItem>

  <AccordionItem value="multi-agent">
    <AccordionTrigger>Multi-agent systems</AccordionTrigger>
    <AccordionContent>

Multiple specialized AI agents coordinate to solve tasks no individual agent could handle. Can use hierarchical agents with a supervisor or peer-to-peer topologies.

**Example:** Orchestrated customer support, research, and sales pipelines

**When to use:** Problems that genuinely require coordination across specialized roles

    </AccordionContent>

  </AccordionItem>
</Accordion>

## Match type to complexity

| Complexity | Agent type | Example |
| --- | --- | --- |
| Fixed rules, full observability | Simple reflex | Email routing, spam filtering |
| Clear goal, multiple paths | Goal-based | Route optimization, lead scoring |
| Competing objectives | Utility-based | Dynamic pricing, resource allocation |
| Multi-domain coordination | Multi-agent | Customer lifecycle, research pipelines |

Start simple. Split when one agent becomes unwieldy. Add routing only when you have multiple agents.

## Production patterns worth noting

A few named systems that make the taxonomy concrete:

- **Uber Finch** — supervisor routes Slack questions to SQL sub-agents (multi-agent)
- **Dropbox Dash** — two-stage plan then execute for knowledge work (goal-based)
- **Ramp** — LLM + embeddings + multimodal RAG for merchant classification
- **Intercom Fin Voice** — transcription, RAG, telephony; escalate when confidence is low
- **Airtable Field Agents** — event-driven state machine for database enrichment

In production, agents need **tracing** (what tools ran?), **evals** (did quality hold?), and **guardrails** (prompt injection, output safety). Traditional test suites don't cover non-deterministic loops.

High-stakes flows keep humans in the loop: mid-execution context, draft approval, or deferred tool execution.

---

## Takeaway

Agents are not chatbots with extra steps. Match architecture to task complexity, keep context manageable, and ship one well-scoped use case before expanding.
